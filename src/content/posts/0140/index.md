DDIA 第二版 10.6.1“共识的多种形式”在四个表述中三次使用 atomic：原子 CAS、原子的取值并加一，以及分布式事务的原子提交。它们是否表达同一个意思？

**前两处约束一个操作如何与并发操作交错，第三处约束同一事务的多个参与者能否作出相互矛盾的提交决定。** 它们共享“整体”的直觉，但“哪个整体不能被怎样拆开”并不相同。[DDIA 第二版第 10 章](https://learning.oreilly.com/library/view/designing-data-intensive-applications/9781098119058/ch10.html)

本文按语义把并发、并行、分布式与存储领域常见的 atomic 用法归入五个家族。这个分类是本文的组织方式，不是某一标准的既定分类；各定义依据原始论文或规范，用中文转述。同一家族可以具有不同强度，同一机制也可以同时提供多类保证。

## 一、先问清楚：哪一部分，对谁，在什么情况下不可分

“这是原子的”不是完整的技术承诺。至少需要补上四项：**操作或状态的范围、观察者的范围、所排除的现象，以及故障与进展条件。**

| 语义家族 | 典型术语 | 不允许发生什么 | 最想强调什么 |
| --- | --- | --- | --- |
| 操作原子性 | atomic load/store、CAS、fetch-and-add、atomic register | 在规定粒度和观察范围内拆开一次操作 | 并发执行的不可分割性 |
| 失败原子性 | ACID 的 A、atomic commitment、failure/crash atomicity | 失败后留下半个已生效结果，或事务参与者作出冲突决定 | 成败结果的整体性 |
| 事务原子可见性 | atomic visibility、Read Atomic isolation | 一次读取观察到另一个事务的部分更新 | 读到的事务效果不能碎裂 |
| 原子广播 | atomic broadcast、total order broadcast | 相关节点交付的消息发生遗漏分歧或顺序冲突 | 消息交付的共同序列 |
| 写传播的原子性 | multi-copy atomicity、other-multi-copy atomicity | 一次写入以模型禁止的方式对不同观察者分阶段可见 | 跨观察者的可见性边界 |

这里不能把“原子”统一解释成“所有事情同时完成”。并发对象可以由多条指令实现，事务可以执行很久，广播可以先后抵达，磁盘恢复也可以逐页进行。被约束的是规定接口下的行为，不是物理步骤的数量。

## 二、操作原子性：一次操作不能被并发访问拆开

### 从不撕裂访问，到不可分割的读—改—写

**定义：对规定对象和观察者，一次原子访问不能表现为被其他相关访问拆开的若干部分。** C++ 工作草案明确规定：即使使用 relaxed 内存序，对一个原子对象的访问相对于该对象的其他原子访问仍必须不可分割。[C++ 工作草案，`atomics.order`](https://eel.is/c++draft/atomics.order)

这包含两个需要区分的粒度。原子 load/store 防止一次受保证的访问发生撕裂；原子 read-modify-write（RMW）则把读取、计算和写回合成一个操作。**分别原子的读取与写入，不会自动组成一次原子的更新。**

例如计数器初始为 0，两个线程分别执行原子 `load`，都读到 0，再分别原子 `store(1)`，最终可以只有 1。若两者执行 `fetch_add(1)`，且没有其他修改和溢出，返回的旧值分别为 0、1，最终为 2。

CAS 同属 RMW 家族：只有当前值等于预期值时才更新；比较与条件更新必须作为一个操作完成。DDIA 开头的 atomic CAS 与 atomic fetch-and-add，正是在这个意义上使用同一个 atomic。

### 并发对象的精确定义：线性一致性

**定义：一个并发历史是线性一致的，如果可以为它找到符合对象顺序规范的顺序历史，并保持不重叠操作的实时先后关系；未完成调用按正式定义允许补全或舍弃。** 直观上，每次生效的操作仿佛在调用与返回之间某一时刻发生。[Herlihy 与 Wing，1990，§2](https://www.cs.cmu.edu/~wing/publications/HerlihyWing90.pdf)

在经典共享寄存器与分布式对象文献中，atomic register、atomic object 常用这一语义。无论实现使用 CPU 指令、锁还是网络协议，判断对象是否原子，都看外部历史是否满足规范。

但不能把所有语言中的 `atomic` 关键字直接替换为上述完整定义。语言内存模型还规定每个对象的修改顺序、跨对象的同步关系和允许的读取结果；**`relaxed` 的不可分割访问，不提供跨对象的顺序一致性，也不自动发布旁边的普通数据。** 审查程序必须同时看原子操作和内存序。

### 并行计算没有另一套“原子加法”

GPU 的 `atomicAdd` 仍属于这一类，关键是作用域。CUDA 13.0 指南区分 block、device、system 等范围；其中传统原子函数通常具有 relaxed 内存序。一个 block 范围内的保证，不能擅自扩大为 CPU 与所有 GPU 都参与的保证。[CUDA 13.0 编程指南，Atomic Functions](https://docs.nvidia.com/cuda/archive/13.0.0/cuda-c-programming-guide/index.html#atomic-functions)

原子浮点加法也不保证每次运行得到相同的最终比特模式：并发加法的排列可以不同，浮点舍入又依赖计算顺序。它解决更新被覆盖的问题，不固定线程执行顺序。

系统调用中也有这一家族的用法。POSIX 要求不超过 `PIPE_BUF` 的管道写入不与其他写者的数据交错；这不意味着读取端一次 `read` 就得到一条完整消息。成功替换已有目标的 `rename` 提供路径替换的原子语义，也不自动保证断电后的持久保存。[POSIX `write`](https://pubs.opengroup.org/onlinepubs/9699919799/functions/write.html)、[POSIX `rename`](https://pubs.opengroup.org/onlinepubs/9799919799/functions/rename.html)

**这一类强调：不要让并发交错破坏规定的操作边界。它不自动保证持久性、无锁、无等待或执行顺序确定。**

## 三、失败原子性：不能留下半个结果

### ACID 的 A：事务修改全有或全无

**定义：事务作为一个成败单位，要么提交其全部修改，要么中止，并丢弃或撤销它已经产生的修改。** Härder 与 Reuter 的 ACID 论文把这一性质表述为 all-or-nothing；DDIA 第 8 章进一步明确区分：这里的 A 处理事务中止，并发访问的行为属于隔离性讨论。[Härder 与 Reuter，1983，§1.2](https://www.cs.princeton.edu/courses/archive/fall08/cos597B/papers/acid.pdf)、[DDIA 第二版第 8 章](https://learning.oreilly.com/library/view/designing-data-intensive-applications/9781098119058/ch08.html)

例如一次转账包含扣款和入账，不能只把扣款保留为已提交结果。这个要求从单机扩展到多分片时没有改变，只是“全部修改”的事务边界跨越了机器。

“撤销”也不要求把每一个磁盘字节恢复原样。日志、废弃版本或审计记录可以存在；关键是中止事务的修改不能作为成功的事务效果保留下来。保证只覆盖参与事务管理的资源，不会自动撤回已经发送的邮件。

### 原子提交：把同一个成败单位扩展到多个参与者

**定义：分布式原子提交要求参与者不能一个提交、另一个中止；决定作出后不能反悔，并且只有所有参与者都已具备提交条件，才允许提交。** 为排除“永远中止”这样的空洞方案，完整规范还规定无故障时的提交条件，以及适当环境下的进展条件。[Gray 与 Lamport，§2](https://arxiv.org/pdf/cs/0408036)

它与 ACID 的 A 属于同一语义家族，但不是同一层抽象：**A 是整个事务的结果承诺，atomic commitment 是协调多个参与者兑现该承诺的协议问题。** 协议决定之外，还需要本地事务、日志和恢复机制正确执行决定。

原子提交允许“A 已收到提交决定、B 仍处于未决状态”，禁止的是“A 已提交、B 已中止”。因此，客户端超时不等于事务中止，参与者等待也不等于原子性被破坏。安全性与终止性必须分别陈述。

这里还不能把“都决定一个值”当成全部定义。普通共识可以选择某个提议值；原子提交中的 commit 必须满足所有参与者准备就绪的条件。二者的关系需要转换协议与模型假设，不能只靠名字类比。

### 异常安全与崩溃原子性：同一成败结构，不同故障范围

**强异常保证的定义：操作要么成功，要么抛出异常，并使受保证的状态保持为调用前的状态。** Boost 将其称为 commit-or-rollback 语义。这是失败原子性的一个实例，却不意味着操作对其他线程不可分割，更不意味着进程崩溃或断电后可恢复。[Boost：Exception-Safety in Generic Components](https://beta.boost.org/community/exception_safety.html)

**崩溃原子写的定义：在规定的掉电或系统崩溃后，受保证的写入区域呈现完整旧数据或完整新数据，不能混合二者。** Linux ext4 的 atomic block writes 文档以此定义防撕裂写入，并明确要求相应的文件系统、设备与 I/O 条件。[Linux 内核：Atomic Block Writes](https://kernel.org/doc/html/next/filesystems/ext4/atomic_writes.html)

这也是“全有或全无”，但单位可能只是一个受支持的写入范围，并非整个文件或整个事务。CPU 的原子 store 不能直接推出掉电原子写；一个防撕裂写入也不能单独推出成功返回的数据已经持久化。

**这一类强调：在明确的失败模型下，不留下半个成功结果。必须另问能否及时得知结果，以及成功后能承受哪些故障。**

## 四、事务原子可见性：读者不能看到碎裂的事务效果

提交结果完整，不等于任意读法都能看到完整结果。这正是需要第三类定义的原因。

**定义：其他事务对一次事务更新的观察应当全有或全无，不能产生 fractured reads（碎裂读取）。** RAMP 论文用 Read Atomic（RA）隔离形式化这一要求；RA 还排除读取中止事务和事务内部的中间写入。[Bailis 等，2014，§3.1](https://www.bailis.org/papers/ramp-sigmod2014.pdf)

考虑只有一个更新事务：初始 `x=0, y=0`，事务 T 把两者都改为 1。若读取事务 R 同时读取这两个对象，原子可见性允许它读到 `(0,0)` 或 `(1,1)`，不允许读到 `(1,0)` 或 `(0,1)`。

这里的“全部”限于读取涉及的对象，并不强迫 R 把 T 修改的所有键都查询一遍。有后续覆盖写入时，也不要求永远取出 T 当时的所有原始版本；严格判定应使用论文的版本依赖定义。

**这一类强调的是读者观察到的完整性，不是提交参与者决定的完整性。** 分布式提交协议需要配合读协议、版本管理或锁，才能提供相应可见性；一次读取没有碎裂，也不意味着它足够新，更不自动意味着全部事务可串行化。

因此，“原子提交”和“原子可见性”应当分开写。某些教材或产品把二者一起称为“事务原子性”，阅读时应检查具体承诺，不能仅靠 A 这个字母推断隔离级别。

## 五、原子广播：共同交付哪些消息，以什么顺序交付

**定义：原子广播是在可靠广播基础上提供全序交付的通信抽象。** 在崩溃故障模型下，常见规范要求有效性、完整性、一致交付和全序：正确进程广播的消息最终被交付；消息不被凭空生成或重复交付；一个正确进程交付的消息最终被其他正确进程交付；正确进程共同交付的消息具有相同相对顺序。[Défago、Schiper 与 Urbán，§2.3–2.4](https://dspace.jaist.ac.jp/dspace/bitstream/10119/4883/1/defago_et_al.pdf)

文献还区分普通与 uniform 版本：后者将相关约束扩展到后来发生故障的进程，例如任一进程已经交付某消息，都要求所有正确进程最终交付它。具体证明必须采用相应版本；“所有节点”不能不加区别地替代“正确进程”。这里的交付也指协议向上层应用交付，不是网卡收到数据包。

假设广播两条命令，协议不能让一个正确副本先交付 `m1` 再交付 `m2`，另一个却反过来。但两个副本交付同一条消息的物理时间可以不同；原子广播不是同步时钟广播。

**这一类强调共同的消息序列。** 它可以作为状态机复制的基础，却不自动让应用处理产生的所有外部副作用构成事务，也不单独保证“支付只扣一次”。去重、状态持久化与外部系统的事务边界仍需设计。

DDIA 开头第二项写的是全序广播，没有出现 atomic；后文指出它也称为 atomic broadcast。于是，这四个例子实际上还通向第四种 atomic 用法，而不只是开头明写的三处。

## 六、多副本原子性：同一次写入怎样跨观察者变得可见

这个术语来自硬件内存模型，其中的“副本”通常涉及缓存和内存系统，不应直接理解成数据库复制协议。

**定义：在 Arm AMBA AXI/ACE Issue H 的 multi-copy atomicity 定义中，同一位置的写入被所有 agent 按相同顺序观察；一个写入一旦对某个 agent 可观察，也应对所有 agent 可观察。** 这是关于同一写入的传播与可见性，不只是读写数据本身是否撕裂。[Arm AMBA AXI/ACE Issue H，A7.1.1](https://developer.arm.com/-/media/Arm%20Developer%20Community/PDF/IHI0022H_amba_axi_protocol_spec.pdf)

other-multi-copy atomicity 允许写者先通过自身缓冲观察到自己的写入，但约束它对其他观察者的可见性。Arm 的相关说明明确区分这种情形，不能把 AMBA 的定义直接当作所有 Arm 架构版本的完整内存模型。[Arm：持久内存与 other-MCA](https://developer.arm.com/community/arm-research/b/articles/posts/simplifying-persistent-programming-with-microarchitectural-support)

**这一类强调传播范围上的原子性。** 它不同于单次访问不撕裂，也不自动提供跨不同地址的顺序一致性。“都可观察”是模型中的语义条件，不是所有核心必须在同一纳秒执行一次读指令。

## 七、哪些术语应当合并，哪些只能说有关联

并发算法中的 atomic snapshot 属于操作原子性：一次扫描多个位置的结果，应当对应扫描期间某个逻辑时点的整体状态。但扫描原子不意味着多个独立更新合成一个原子事务；Read Atomic 读取也不自动满足扫描的实时性要求，二者不能互换。[Afek 等：Atomic Snapshots of Shared Memory](https://groups.csail.mit.edu/tds/papers/Shavit/JACM93.pdf)

“事务内存”“原子代码块”经常同时包含多项保证：中止后撤销内存修改，以及相对于某些访问的隔离。事务内存的 strong atomicity 还要求相对于非事务访问具有原子行为；weak atomicity 通常只约束事务之间。差别在观察者范围，不能把其中的 strong 等同于强异常保证。[Khyzha 等：Safe Privatization in Transactional Memory](https://arxiv.org/abs/1801.04249)

锁保护的临界区可以实现相对于遵守同一锁协议的访问的不可分割效果，但仅有锁不会自动撤销异常前已经做出的修改。软件锁、硬件事务、日志都是机制；它们提供哪几类原子性，取决于完整协议。

| 常见推断 | 为什么不成立 |
| --- | --- |
| 每一步都是原子的，所以整体也是原子的 | 操作之间仍可能被插入其他操作；需要整体规范或组合协议 |
| 有原子提交，所以所有读者都同时看到整个事务 | 提交决定与读取可见性是不同保证 |
| 有原子操作，所以不会阻塞 | 原子性描述行为，lock-free、wait-free 描述进展 |
| 原子操作都能解决任意规模共识 | 原子对象的操作能力不同，共识数不同 |
| 有失败原子性，所以失败请求可以直接重试 | 必须先区分确定中止与结果未知；后者可能已经成功 |

最后一处与 DDIA 10.6.1 尤其相关：开头“彼此等价”的概述需要结合后文限定阅读。**在经典异步共享内存、使用原子读写寄存器并要求确定性无等待共识的模型下，fetch-and-add 的共识数是 2，CAS 是 ∞。** 同样不可分割的操作，表达能力仍然不同。[Herlihy，1991，§3](https://cs.brown.edu/~mph/Herlihy91/p124-herlihy.pdf)

CAS 可以通过重试实现 fetch-and-add 的功能，也不意味着那个重试循环自动具有无等待保证。讨论“能否互相实现”，必须同时说明功能规范、允许的辅助对象、故障模型和进展要求。

## 八、把“原子的”改写成一条可以检验的承诺

今后遇到 atomic，可以把它展开成这样一句话：

> 对于哪些操作或状态，在什么观察范围和故障条件下，系统禁止哪一种部分执行、部分结果、部分可见或交付分歧？进展另有什么条件？

据此，DDIA 开头三处 atomic 可以准确改写为：

- **CAS：**相对于同一对象的并发操作，比较与条件更新不可分割。
- **fetch-and-add：**相对于同一计数器的并发操作，取旧值与递增不可分割。
- **atomic commitment：**同一事务的参与者不能作出相互矛盾的提交／中止决定；提交条件与进展条件另须满足。

原子性最有用的含义，始终依赖那个被省略的宾语：**操作、成败结果、事务视图、消息序列，或者写入的可见性。** 把宾语和边界补全，才知道一个系统究竟保证了什么。
