DDIA 第二版 10.6.1 在介绍共识时，接连提到原子 CAS、原子的取值并加一，以及事务的原子提交。这里的 atomic 是不是同一个概念？

如果把前两个归为“操作原子性”，解释为防止其他操作插进来；把第三个归为“失败原子性”，解释为防止出错后只留下部分结果，能不能分清它们？

这个分法有个漏洞：**操作也会失败，也可以要求失败后不能留下部分结果。** “操作”说的是被保护的对象，“失败”说的是需要处理的情形，二者不能直接当作互斥类别。

要分清这些用法，需要先把对象固定下来，看同一个操作究竟可以提出哪些不同的要求。

## 同一次更新，可以要求三种不同的保证

假设文件里只有两个字段 `x`、`y`，初始都是 0。现在要执行一次更新，把它们都改为 1。内部先写 x，再写 y。

写完 x、还没写 y 时，确实存在一个“做到一半”的状态。绝大多数实现都无法避免内部经历若干步骤。问题在于，这个中间状态允许以什么方式影响外部。

**第一种要求：正常执行时，并发读者不能读到半成品。** 如果提供一个“同时读取 x、y”的接口，它只能返回 `(0,0)` 或 `(1,1)`，不能返回 `(1,0)`。这里检查的是更新与读取如何交错。

**第二种要求：操作因异常退出时，不能留下部分修改。** 假设写完 x 后发生了可处理的错误，函数返回失败，那么受保护的状态应当恢复为 `(0,0)`。这里检查的是失败返回后的结果。

**第三种要求：机器突然断电，恢复后不能留下半次更新。** 重启后应当得到完整旧值或完整新值，不能是 `(1,0)`。这里检查的是持久状态经过崩溃与恢复后变成了什么。

三个要求保护的都是同一次操作，也都可以被称为“这个操作的原子性”。但满足一个，不代表满足另外两个。

例如，写者和读者都持有同一把锁，可以在正常完成的执行中挡住中间状态。但锁本身不会撤销异常前的修改，也不会修复断电时只写了一半的文件。反过来，恢复日志可以帮助重启后撤销修改，但仅凭恢复日志，不能断定运行中的读者读不到中间状态。

这里特意说“正常完成”：如果加锁代码异常退出后释放了锁，却留下半成品，那么它就不满足“失败时也不能暴露部分修改”的更完整要求。**一个原子性承诺必须说清楚，它覆盖哪些执行，包括哪些失败。**

因此，原子性通常并不禁止内部“做到一半”。它规定的是：哪些中间步骤不能被其他操作单独观察或利用，哪些部分结果不能在失败后保留下来。

## 先确定整体，再确定怎样才算把它拆开

读到 atomic，可以先问两个问题：

1. **什么被当作一个整体？** 一次读取、一次读改写、一个事务的全部修改，还是多个参与者的提交结果？
2. **怎样才算破坏这个整体？** 并发操作插进了关键步骤，查询读到部分更新，异常后留下部分修改，还是不同节点作出了冲突决定？

然后补上具体范围：哪些读者或线程受保证，保护哪些数据，考虑哪些故障。讨论是否会等待、多久完成，则需要另外说明进展条件。

这是一种阅读方法，不是一份能替代所有规范的“原子性总定义”。atomic 在不同文献中有不同的正式含义。下面按这些问题比较，既保留共同点，也保留每种定义真正多要求的东西。

## CAS 和 fetch-and-add：把读改写当作一次操作

计数器 x 初始为 0。两个线程各加一次，如果它们都先读到 0，再分别写回 1，最后就只有 1。即使每次读取和写入都不会撕裂，整个加法仍然被拆开了。

`fetch_add(1)` 保护的是“读取旧值并递增”这个整体。没有其他修改和溢出时，两个调用分别返回 0、1，最后得到 2。

CAS 保护的整体则是“比较与条件更新”。`CAS(x, 0, 1)` 必须在同一次操作中确认当前值等于 0，并把它替换为 1，不能根据一个已经过时的检查结果直接覆盖数据。二者都属于原子读改写，也就是 atomic read-modify-write。

在经典并发对象理论中，这种行为通常通过**线性一致性**定义：一次并发执行可以解释为符合对象规范的顺序执行，并保持不重叠调用的实际先后顺序。直观上，每次完成的操作仿佛在调用和返回之间某一时刻生效；正式定义也处理尚未完成的调用。[Herlihy 与 Wing，1990，§2](https://www.cs.cmu.edu/~wing/publications/HerlihyWing90.pdf)

这个要求比“每次只读到完整旧值或完整新值”更强。假设 x 只有一次从 0 到 1 的写入：一个读取返回 1 并结束，之后才开始的读取却返回 0。两次都读到了完整的数，但无法把它们排进一个符合实时先后关系的读写顺序。

所以，**不撕裂、读改写不可分割、整个对象线性一致，不能仅凭“都没读到半个数”就认为完全相同。** 需要先说明操作是什么，再检查所有调用能否共同满足它的规范。

### 语言里的 atomic 还要看内存序

C++ 工作草案要求：即便使用 relaxed 内存序，对一个原子对象的访问相对于该对象的其他原子访问也必须不可分割。但这不会自动替不同变量之间的读写建立同步关系。[C++ 工作草案，`atomics.order`](https://eel.is/c++draft/atomics.order)

因此，不能仅凭一个“准备完成”的标志是 atomic，就断定另一个线程一定能正确读取与它配套的普通数据。也不能仅凭所有变量都声明为 atomic，就把整段程序当作一个原子操作。

GPU 的原子加法同样需要明确范围。CUDA 区分线程块、设备、系统等作用域；只在一个线程块内有效的保证，不能直接扩大到 CPU 和所有 GPU。原子浮点加法也不固定加法次序，结果仍可能因舍入而不同。[CUDA 13.0 编程指南](https://docs.nvidia.com/cuda/archive/13.0.0/cuda-c-programming-guide/index.html#atomic-functions)

这里的核心是并发调用的行为，而不是用了几条指令。锁也可以实现原子操作；是否无锁、是否无等待，属于另外的要求。

## ACID 的 A：把事务的修改当作一个成败单位

转账包含扣款和入账。如果入账失败，不能只把扣款作为成功结果保留下来。

**ACID 的原子性要求：事务要么提交全部修改，要么中止，并丢弃或撤销它已经做出的修改。** 这就是 ACID 原始论文中的 all-or-nothing。DDIA 第 8 章把这里的重点明确放在事务中止上；并发事务之间如何相互影响，则归入隔离性的讨论。[Härder 与 Reuter，1983，§1.2](https://www.cs.princeton.edu/courses/archive/fall08/cos597B/papers/acid.pdf)、[DDIA 第二版第 8 章](https://learning.oreilly.com/library/view/designing-data-intensive-applications/9781098119058/ch08.html)

这当然也是对“操作”的要求，只不过操作的单位是整个事务，考察的是成败结果。因此，“操作原子性”这个宽泛说法，并不能把 ACID 的 A 排除在外。

撤销的是这个事务的效果，不是把整个数据库倒回过去。其他事务已经提交的修改不应被一起撤销；日志和废弃版本也可以继续存在。事务系统通常也不能替你撤回已经发出去的邮件。

### 原子提交把这个要求带到多台机器上

当扣款和入账分属两台数据库，事务仍然要全有或全无。此时需要协调各个参与者的决定。

**原子提交要求参与者不能一个提交、另一个中止；决定作出后不能反悔，只有所有参与者都准备好，才允许提交。** Gray 与 Lamport 的规范还规定正常情况下应当提交的条件，以及在足够多节点恢复正常后应当取得进展的条件。[Consensus on Transaction Commit，§2](https://arxiv.org/pdf/cs/0408036)

ACID 的 A 是整个事务的要求，原子提交是实现跨参与者成败一致的协议问题。它还需要本地事务、持久化和恢复机制配合，才能把决定落实到数据上。

这里的一致不等于同步完成。一个参与者已经提交，另一个还在等决定，可以是合法的暂时状态；一个提交、另一个中止，才是冲突。客户端超时也只表示结果未知，事务可能已经提交。

原子提交与普通共识也不能只靠“大家选同一个值”来等同。原子提交的 commit 必须满足所有参与者准备就绪的条件；普通共识选择某个提议值，并没有自动包含这条规则。

### 异常与断电，是不同的失败范围

从失败后的结果看，事务、异常安全和崩溃原子写有共同结构，但它们承受的失败不同。

**强异常保证**要求操作要么成功，要么抛出异常，并使受保证的状态保持为调用前的样子。Boost 将其称为 commit-or-rollback。这里通常依赖程序继续执行清理或回滚代码，不能直接推出断电后也能恢复。[Boost：异常安全](https://beta.boost.org/community/exception_safety.html)

**崩溃原子写**要求在规定的崩溃或掉电后，受保护区域呈现完整旧数据或完整新数据，不能一半新、一半旧。Linux 的原子块写文档以此定义防撕裂写入，并要求设备、文件系统、写入大小等满足相应条件。[Linux 内核：Atomic Block Writes](https://kernel.org/doc/html/next/filesystems/ext4/atomic_writes.html)

这里的整体可能只是一个磁盘写入区域，而不是事务。允许恢复成完整旧数据，也不能单独证明成功返回的那次写入已经持久化。原子性与持久性需要分别检查。

## 原子可见性：提交完整，读到的也要完整

考虑只有一笔转账：A 的余额从 100 变成 0，B 从 0 变成 100。事务最终全部提交，但一个查询先读到了旧的 A，再读到了新的 B，于是算出总额 200。

问题不在事务只提交了一半，而在查询把同一事务的更新拆开观察了。

**事务原子可见性要求，读取不能只观察到另一个事务的部分更新。** RAMP 论文以 Read Atomic（RA）隔离形式化这种要求，并排除读取中止事务和事务内部的中间写入。[Bailis 等，2014，§3.1](https://www.bailis.org/papers/ramp-sigmod2014.pdf)

在上面的例子里，同一个读取事务可以读到 `(100,0)` 或 `(0,100)`，不能读到 `(100,100)` 或 `(0,0)`。它只约束读取涉及的数据，并不要求查询把写事务修改的所有键都取出来；存在后续覆盖写入时，还要按版本关系判断。

这与前面并发读取看不到半成品的要求有关，但规定的整体是“另一个事务的更新”。它本身不要求读取足够新，也不保证所有事务都能解释为串行执行。

所以，不能从“有原子提交协议”直接推出“读者一定看不到部分更新”。提交协议管理决定，读协议、锁和版本管理共同决定读者看到什么。一个完整的事务系统可以同时提供两项保证，但需要分别说明。

## 原子广播：还必须把消息的顺序算进去

DDIA 开头第二项写的是全序广播，后文又称它为 atomic broadcast。这里的“原子”更不能只用“失败了就全撤销”理解。

两个副本都从 x=0 开始，收到“设为 1”和“乘以 2”两条命令。一个先设值再乘，另一个反过来，最后分别得到 2 和 1。消息都收到了，顺序却让结果分叉。

**原子广播是具有全序交付保证的可靠广播。** 在常见崩溃故障模型下，正确进程应最终交付相同的消息，并对共同交付的消息保持相同相对顺序；规范还要求有效性、无伪造和无重复。交付指协议交给上层程序，不是网卡收到数据包。[Défago 等，§2.3–2.4](https://dspace.jaist.ac.jp/dspace/bitstream/10119/4883/1/defago_et_al.pdf)

普通版本与 uniform 版本对故障进程的要求不同。例如 uniform agreement 要求：任一进程已交付某消息，都应使所有正确进程最终交付它。不能把“正确进程”不加区别地替换成“所有节点”。

原子广播要求消息交付的一致和有序，却允许不同副本先后交付。它也没有要求上层应用发生故障时自动撤销外部操作。要理解这个术语，必须保留可靠性与顺序这两部分，不能只提炼出“整体”两个字。

## 用同一组问题整理常见用法

下面不是把所有 atomic 分成互斥的几类，而是把它们放到同一组问题下比较。关注点相同的放在一起；一个系统可以同时提供多行保证。

| 关注什么 | 常见名称 | 把什么当作整体 | 主要禁止什么 |
| --- | --- | --- | --- |
| 单次访问 | 原子 load/store、不撕裂访问 | 规定大小的一次访问 | 把一次读写拆成可被相关访问区分的部分 |
| 并发调用的行为 | 原子 RMW、原子寄存器、线性一致对象 | 对象规范中的一次操作 | 调用结果不符合要求的操作顺序 |
| 多对象读取 | 原子快照 | 一次扫描 | 结果无法对应扫描期间某个逻辑时点的整体状态 |
| 事务读取 | 原子可见性、Read Atomic | 写事务在读取集合中的更新 | 同一次读取只观察到部分事务更新 |
| 失败后的结果 | ACID 的 A、强异常保证 | 事务或函数受保护的修改 | 中止或异常后留下部分效果 |
| 崩溃后的结果 | crash atomicity、原子块写 | 受保护的持久更新范围 | 恢复后留下部分新数据、部分旧数据 |
| 分布式提交决定 | atomic commitment | 同一事务各参与者的结果 | 一部分提交，一部分中止 |
| 消息交付 | atomic broadcast | 各参与者交付的消息及其顺序 | 应当交付的消息或相对顺序出现分歧 |
| 内存写入的传播 | multi-copy atomicity | 一次写入对多个观察者的可见性 | 写入以规范禁止的方式分阶段可见 |

还有几处容易被这些名字掩盖的区别。

**原子快照**把扫描多个位置做成一个线性一致的读取，但不会把写者的多个独立更新合成一个事务。它可能恰好拍到两次独立写入之间的状态；从快照对象的规范看，这并不错误。[Afek 等：Atomic Snapshots of Shared Memory](https://groups.csail.mit.edu/tds/papers/Shavit/JACM93.pdf)

**事务内存的 strong/weak atomicity**主要区别在比较哪些访问。weak 通常只要求事务之间有原子行为，strong 还要求相对于非事务访问也有这种行为。它们并非“强异常保证”的强弱等级；事务内存还可能同时提供中止回滚。[Khyzha 等：Safe Privatization in Transactional Memory](https://arxiv.org/abs/1801.04249)

**文件与管道的原子操作**也需要单独读接口规范。POSIX 中，不超过 `PIPE_BUF` 的管道写入不能与其他写者的数据交错，但读者可能分几次才读完。`rename` 的原子替换保护目标路径的切换，不自动保证断电持久性。[POSIX `write`](https://pubs.opengroup.org/onlinepubs/9699919799/functions/write.html)、[POSIX `rename`](https://pubs.opengroup.org/onlinepubs/9799919799/functions/rename.html)

**多副本原子性**来自硬件内存模型。Arm AMBA AXI/ACE Issue H 要求同一位置的写入被各 agent 按相同顺序观察，而且一次写入只要对某个 agent 可观察，就应对所有 agent 可观察。这里约束写入的可见性传播，不是事务回滚，也不是数据库复制。[Arm 规范，A7.1.1](https://developer.arm.com/-/media/Arm%20Developer%20Community/PDF/IHI0022H_amba_axi_protocol_spec.pdf)

other-multi-copy atomicity 允许写入者先从自身缓冲观察到写入，但约束其对其他观察者的可见性。不同架构与协议的定义不能混用；这项性质也没有替不同地址上的全部操作排好顺序。[Arm 对 other-MCA 的说明](https://developer.arm.com/community/arm-research/b/articles/posts/simplifying-persistent-programming-with-microarchitectural-support)

## 回到 DDIA 的三个 atomic

现在可以更准确地回答开头的问题。

CAS 与 fetch-and-add 都把一次读改写当作整体，要求并发调用按相应对象规范发生作用。原子提交则把同一事务各参与者的成败结果联系起来，不允许出现相互矛盾的决定。

它们确有共同的“不可分”含义，但不是一条可以直接互换的正式定义。**“操作”这个词不足以区分它们；需要说明操作包含哪些效果，再说明这些效果在并发、失败或跨参与者观察中必须保持什么关系。**

同样，原子也不意味着共识能力相同。在经典异步共享内存、允许使用原子读写寄存器并要求确定性无等待共识的模型中，fetch-and-add 的共识数为 2，CAS 为 ∞。DDIA 开头的等价性概述，需要结合后文限定阅读。[Herlihy，1991，§3](https://cs.brown.edu/~mph/Herlihy91/p124-herlihy.pdf)

一份有用的接口说明，应当能写成具体的话：这个读取保证拿到不撕裂的值；这个 CAS 保证比较与更新不可分；这个事务中止后撤销全部修改；这个写入断电后不会留下新旧混合的数据。只写“本操作是原子的”，还没有把这些区别告诉使用者。
