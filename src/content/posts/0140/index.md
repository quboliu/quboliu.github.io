读 DDIA 第二版 10.6.1 时，很容易遇到一个疑问：开头列出的四种共识问题中，三次出现 atomic——原子 CAS、原子的取值并加一、事务的原子提交。这里的“原子”是同一个意思吗？

前两个是，第三个有所不同。

原子加法要解决的是：两个线程各加一次，最后不能只加了一次。原子事务要解决的是：转账做到一半出了故障，不能钱扣了，却没有入账。一个担心别的操作插进来，另一个担心出了错只做成一半。

“不可分割”可以概括它们，但还不够解释它们。要理解每个 atomic，得看它到底在防什么。下面从这两个最常见的意思开始，再看原子可见性、原子广播和硬件中的多副本原子性。定义按论文和规范转述，分类是为了方便比较。[DDIA 第二版第 10 章](https://learning.oreilly.com/library/view/designing-data-intensive-applications/9781098119058/ch10.html)

## 1. 原子操作：别让两个线程把一次更新拆开

计数器 `x` 初始为 0。两个线程都要把它加一，代码看起来只是 `x = x + 1`，执行时却可能变成这样：

| 步骤 | 线程 A | 线程 B |
| --- | --- | --- |
| 1 | 读到 x 为 0 | |
| 2 | | 读到 x 为 0 |
| 3 | 算出 1，写回 x | |
| 4 | | 算出 1，写回 x |

两次加法，最后却只有 1。即使读取和写入各自都是原子的，也没用：问题出在“读完到写回”之间。

`fetch_add(1)` 把取旧值、加一和写回合成一次原子操作。两个线程都执行它，且没有其他修改或溢出时，一个拿到旧值 0，另一个拿到旧值 1，最后计数为 2。

**操作原子性指的是：相对于同一对象的其他相关访问，一次操作不可分割。** C++ 规范明确要求，即便采用 relaxed 内存序，原子访问也必须满足这一点。[C++ 工作草案，`atomics.order`](https://eel.is/c++draft/atomics.order)

CAS 也是这个意思。`CAS(x, 0, 1)` 检查 x 是否等于 0，如果是，就改成 1。“检查”和“修改”必须连在一起，不能刚确认条件成立，另一个线程就改了 x，自己还照着原先的判断写下去。

所以，DDIA 中的 atomic CAS 与 atomic fetch-and-add，属于同一种原子性。

### 怎么判断一个复杂操作是不是原子的？

不能数它用了几条指令。一个操作即使内部做了很多事，只要外部看起来像一次完成，也可以提供原子语义。

在经典并发对象文献中，这通常用**线性一致性**来精确定义：并发调用的结果能够解释成某个合法的顺序执行，而且已经结束的调用必须排在之后才开始的调用前面。等价的直观说法是，每次完成的操作仿佛在调用与返回之间的某个时刻生效。[Herlihy 与 Wing，1990，§2](https://www.cs.cmu.edu/~wing/publications/HerlihyWing90.pdf)

共享内存论文里的 atomic register，以及分布式系统里的原子读写对象，常指这种保证。具体用锁、CPU 指令还是网络协议实现，是另一回事。

不过，看到代码中的 `atomic`，还得看内存序。C++ 的 relaxed 原子操作不会顺便把其他变量的访问也排好顺序。例如，用一个原子标志表示“数据准备好了”，不能仅凭标志本身原子，就断定另一个线程一定能正确读到旁边的普通数据。

### GPU、管道和文件重命名，也会用到这个意思

GPU 的 `atomicAdd` 同样防止并发更新互相覆盖，但要看作用范围：只对一个线程块有效，还是覆盖整个设备，或者也覆盖 CPU。CUDA 13.0 的传统原子函数还通常采用 relaxed 内存序，不能把它们当作所有线程都已完成工作的同步屏障。[CUDA 编程指南](https://docs.nvidia.com/cuda/archive/13.0.0/cuda-c-programming-guide/index.html#atomic-functions)

浮点数还有个细节：原子加法不固定谁先加、谁后加。浮点加法的舍入结果依赖顺序，因此没有丢失更新，仍可能每次运行得到略有差别的结果。

POSIX 管道也有“原子写”：不超过 `PIPE_BUF` 的写入不能与其他写者的数据交错。但读取端仍可能分几次才读完这些字节。`rename` 的原子替换则意味着已有目标路径不会经历“旧文件先被删掉、新文件还没放上来”的空档。[POSIX `write`](https://pubs.opengroup.org/onlinepubs/9699919799/functions/write.html)、[POSIX `rename`](https://pubs.opengroup.org/onlinepubs/9799919799/functions/rename.html)

这些保证各有范围。管道写原子，不等于消息一次读完；重命名原子，也不等于断电后一定保住新文件。

## 2. 失败原子性：出了错，不能只留下半个结果

现在看转账。A 给 B 转 100 元，需要扣 A 的钱，再给 B 入账。假如扣款之后数据库崩溃了，该怎么办？

ACID 的 A 回答的是这个问题：**一个事务要么提交全部修改，要么中止，丢弃或撤销它已经做出的修改。** 不能只保留扣款，把入账丢掉。这就是 Härder 与 Reuter 的 ACID 论文所说的 all-or-nothing。[原论文，§1.2](https://www.cs.princeton.edu/courses/archive/fall08/cos597B/papers/acid.pdf)

DDIA 第 8 章专门提醒，这里的 A 讨论失败后的处理；多个事务同时访问数据会怎样，则要看 I，也就是隔离性。[DDIA 第二版第 8 章](https://learning.oreilly.com/library/view/designing-data-intensive-applications/9781098119058/ch08.html)

这也解释了为什么一把锁不够。锁可以让两个线程排队转账，却不会在扣款后出现异常时，自动把钱加回去。防止别人插进来，与出错后撤销修改，是两件事。

### 分布式原子提交：别让一边提交，另一边撤销

如果 A、B 的账户分别在两台数据库上，要求依然是整笔转账全有或全无。困难在于：两边必须对是否提交作出一致决定。

**原子提交要求：同一事务不能有参与者提交、另一个参与者中止；已经作出的决定不能反悔，只有所有参与者都准备好，才允许提交。** 完整的协议要求还包括正常情况下什么时候应当提交，以及故障恢复到什么程度后应当结束等待。[Gray 与 Lamport，§2](https://arxiv.org/pdf/cs/0408036)

因此，atomic commitment 与 ACID 的 A 属于同一类意思。A 是事务的要求，原子提交协议负责协调多台机器；各台机器还要靠本地事务、日志和恢复机制落实这个决定。

这里最容易误会的是“全部提交”。它不要求两台机器同时收到消息。A 已知道要提交，B 还在等消息，并不矛盾；A 提交而 B 中止，才违反原子提交。

同理，客户端超时只表示没拿到结果，不能据此断定事务已经撤销。数据库可能提交成功，只是回复丢了。原子性不保证客户端随时知道结果，也不保证等待一定及时结束。

### 异常回滚和磁盘防撕裂，为什么也叫原子？

它们都在回答“做到一半失败了怎么办”，只是失败的原因和需要保护的东西不同。

C++ 的**强异常保证**要求：操作要么成功，要么抛出异常，并让受保证的状态保持为调用前的样子。Boost 称之为 commit-or-rollback。它属于失败原子性，但通常不负责断电恢复，也不意味着能被多个线程随意并发调用。[Boost：异常安全](https://beta.boost.org/community/exception_safety.html)

存储中的**崩溃原子写**则要求：在规定的崩溃或掉电后，写入区域要么是完整旧数据，要么是完整新数据，不能一半新、一半旧。这种混合结果叫 torn write，通常译作撕裂写。[Linux 内核：Atomic Block Writes](https://kernel.org/doc/html/next/filesystems/ext4/atomic_writes.html)

它的保证可能只覆盖一个指定大小、满足对齐要求的写入区域，并不覆盖整个文件。防撕裂也不等于持久性：只说恢复后允许“完整旧数据或完整新数据”，还不能证明成功返回的那次写入已经落盘。

无论保护的是数据库事务、内存中的容器还是磁盘块，这一类“原子”都在强调：失败不能留下半个成功结果。它只保护约定的资源，不能自动撤回事务里已经发出去的邮件。

## 3. 原子可见性：不能读到半笔转账

转账最终全部提交了，读者就一定能读对吗？

未必。假设只有这一笔转账：A 从 100 元变成 0 元，B 从 0 元变成 100 元。一个查询先读 A，再读 B。如果它读到转账前的 A 和转账后的 B，总额就成了 200 元。

两边的提交结果可以完全正确，但这次查询拼出了一个错误的组合。这就是 fractured read，碎裂读取。

**事务的原子可见性要求：在一次读取涉及的数据中，不能只看到另一个事务的一部分更新。** RAMP 论文通过 Read Atomic（RA）隔离定义这种保证；RA 也排除读取中止事务和事务内部的中间写入。[Bailis 等，2014，§3.1](https://www.bailis.org/papers/ramp-sigmod2014.pdf)

在上面的例子中，查询可以看到转账前的 `(100, 0)`，也可以看到转账后的 `(0, 100)`，但不能读到 `(100, 100)` 或 `(0, 0)`。

这不是要求查询必须读出事务修改的所有键。查询只读 A，当然没必要额外读取 B；但它既然要读 A、B，就不能把同一次更新拆开观察。有后续事务覆盖数据时，判断还要按论文中的版本关系处理。

原子提交与原子可见性因此需要分开讨论：前者决定这笔转账是否整体提交，后者保证读者不会拼出半新半旧的结果。要同时做到，提交协议还得配合锁、版本管理和读取协议。

原子可见性也不要求读到最新数据。一个完整但较旧的结果可以满足它；仅有这项保证，也不足以推出所有事务都像串行执行一样。

## 4. 原子广播：各个副本按同一个顺序接收命令

假设两个副本都维护一个初值为 0 的变量。现在有两条命令：“设为 1”和“乘以 2”。一个副本先设置再乘，得到 2；另一个先乘再设置，得到 1。

两条命令都收到了，副本还是不一致。原因是顺序不同。

**原子广播就是带有全序交付保证的可靠广播：相关进程不仅要交付相同的消息，还要按相同的相对顺序交付。** 这里的“交付”指协议把消息交给上层程序，不是网卡刚收到数据包。[Défago 等，§2.3–2.4](https://dspace.jaist.ac.jp/dspace/bitstream/10119/4883/1/defago_et_al.pdf)

在常见的崩溃故障模型下，规范还要求消息不能凭空产生或重复交付，正确进程广播的消息最终应当被交付，一个正确进程已交付的消息也应最终被其他正确进程交付。“正确进程”指遵守协议且不发生所讨论故障的进程。

论文还区分普通版本与 uniform 版本。后者对后来会故障的进程也提出相关要求，例如任一进程已经交付某条消息，都要求所有正确进程最终交付它。讨论具体算法时，需要说明采用哪个版本。

不过，交付顺序相同，不要求交付时间相同。一个副本先处理，另一个稍后赶上，是允许的。原子广播也不会替上层应用回滚执行到一半的外部操作。

DDIA 开头第二项的“全序广播”，后文也称 atomic broadcast。虽然开头只明写了三个 atomic，继续读下去，还会遇到这一种用法。

## 5. 多副本原子性：一次内存写入，能否只让一部分核心看见

硬件文档中的 multi-copy atomicity 又在讨论另一件事。

多核处理器有缓存和写缓冲。一个核心写入 `x=1`，这个修改什么时候能被其他核心观察到？有没有可能它已经对某些核心可见，却还不能被另外一些核心观察到？

**Arm AMBA AXI/ACE Issue H 对多副本原子性的定义是：所有 agent 按相同顺序观察同一位置的写入；一次写入只要对某个 agent 可观察，就应对所有 agent 可观察。** agent 是规范中的访问参与者，可以把核心看作理解这个定义的一个例子。[Arm 规范，A7.1.1](https://developer.arm.com/-/media/Arm%20Developer%20Community/PDF/IHI0022H_amba_axi_protocol_spec.pdf)

这里关注的是写入如何变得可见。它与“一个数会不会读到一半旧、一半新”不同，也不是数据库副本之间的复制协议。

还有一种 other-multi-copy atomicity：允许写入者先从自己的缓冲中读到新值，但对其他观察者的可见性仍受约束。不同规范的细节不能混用，也不能从 AMBA 的一条定义推断所有 Arm 版本的完整内存模型。[Arm 对 other-MCA 的说明](https://developer.arm.com/community/arm-research/b/articles/posts/simplifying-persistent-programming-with-microarchitectural-support)

“对所有核心可观察”不意味着所有核心同时执行读取。它也没有替不同地址上的全部操作排好顺序。

## 6. 把名字放回各自的位置

现在可以把常见用法放到一起。分类依据是它们保护什么，而不是它们出现在哪种机器上。

| 类别 | 常见名称 | 要防的问题 |
| --- | --- | --- |
| 操作原子性 | 原子读写、CAS、fetch-and-add、GPU 原子操作、原子快照 | 并发操作把一次访问或更新拆开 |
| 失败原子性 | ACID 的 A、原子提交、强异常保证、崩溃原子写 | 做到一半出错，只留下部分结果 |
| 事务原子可见性 | atomic visibility、Read Atomic | 查询读到一个事务的部分更新 |
| 原子广播 | atomic broadcast、total order broadcast | 副本交付的消息或顺序不一致 |
| 多副本原子性 | multi-copy atomicity、other-MCA | 一次写入以规范不允许的方式只对部分观察者可见 |

同一类里的保证也有区别。并发算法中的**原子快照**要求，一次扫描多个位置的结果，对应扫描期间某个逻辑时点的整体状态。但原子地扫描，不会让写者的多个独立更新自动合成一个事务。[Afek 等：Atomic Snapshots of Shared Memory](https://groups.csail.mit.edu/tds/papers/Shavit/JACM93.pdf)

**事务内存和原子代码块**则可能把几种保证放在一起：中止时撤销修改，执行时与其他访问隔离。事务内存中的 weak atomicity 通常只约束事务之间；strong atomicity 还要求相对于非事务访问具有原子行为。这里的 strong 与“强异常保证”不是一回事。[Khyzha 等：Safe Privatization in Transactional Memory](https://arxiv.org/abs/1801.04249)

最后回到 DDIA：CAS 和 fetch-and-add 都是原子操作，也不意味着它们能做的事情一样多。在经典共享内存、允许使用原子读写寄存器、要求确定性无等待共识的模型中，fetch-and-add 的共识数是 2，CAS 是 ∞。书中开头“彼此等价”的概述，需要连同后文的这个限定一起读。[Herlihy，1991，§3](https://cs.brown.edu/~mph/Herlihy91/p124-herlihy.pdf)

无等待要求一个进程不必依靠其他进程继续运行，就能在有限个自身步骤内完成操作。CAS 重试循环可以实现加法的功能，但某个线程可能反复失败，因此不能仅凭“功能相同”就说它也无等待。

“原子”也不等于“无锁”：用锁实现的操作照样可以是原子的，只是可能需要等待。这个词说明操作怎样生效，不单独说明它多久能完成。

看到 atomic 时，先把它翻译成当前场景中的一句具体话：这次加法不能被拆开，这笔转账不能只提交一半，这次查询不能读到半笔转账，或者这些副本不能按不同顺序交付命令。能说清这一句，才算知道这里的“原子”是什么意思。
