DDIA 第二版第十章先说“共享日志可以使用全序广播实现”，随后说：每个节点把自己的提议加入共享日志，选择日志第一条，就能解决共识问题。

要读懂这两句话，不必先学习某个共识算法。我们可以像理解 CAS 一样，先弄清全序广播提供什么操作和保证，再看怎样使用它。[DDIA 第二版第 10 章](https://learning.oreilly.com/library/view/designing-data-intensive-applications/9781098119058/ch10.html)

先用一句话概括本文的简化模型：**搞一个中心化的服务，收集各节点的请求，排定顺序，再把排好序的请求发给所有参与节点。**

关键是“所有参与节点”：不是只告诉请求者“你排第几”，而是让大家都按同一顺序交付这些请求。中心可以不断接收、排号、发送，不必等所有节点都提交完。

这是一种直观的实现办法。全序广播规定的是交付结果必须满足什么保证，并不要求内部一定有一台中心服务器。下面先用中心不故障的模型把流程讲清楚；中心坏了以后如何继续排序，是这个简化模型尚未解决的问题。

全文使用同一个例子：A、B、C 三个节点分别提出 a、b、c，最终都要决定同一个提议值。假设这次全序广播排出的顺序是 **b、a、c**。这只是一次合法结果，不代表 b 有特殊优先级。

![三个节点分别提出 a、b、c，全序广播向各节点按 b、a、c 的相同顺序交付；各节点写入自己的本地日志，并读取位置 0，最终都决定 b。](./broadcast-log-decision.png)

*图中虚线框代表一个逻辑上的通信服务，不代表必须存在一台中央服务器。右侧画的是三份本地日志都已追齐的状态；实际只要读到第一条，就能作决定，不必等后两条。*

## 1. 先分清四个动作

“把消息写进共享日志”并不是一次直接写入公共文件的操作。它可以拆成下面几步：

| 动作 | 谁在做 | 读入什么 | 改变什么 |
| --- | --- | --- | --- |
| `broadcast(m)` | 提交方调用通信服务 | 要提交的消息 m | 发起传播请求；此时不等于日志已经追加 |
| `receive(packet)` | 节点的通信层 | 网络送来的包 | 接收缓冲或协议状态；不直接给应用一个日志条目 |
| `deliver(m)` | 通信服务通知上层 | 已满足交付条件的消息 m | 触发上层处理；具体写不写日志由上层决定 |
| `read(k)` | 应用调用日志接口 | 自己的日志中位置 k 的条目 | 返回条目；没有就等待，不产生新条目 |

在 `deliver(m)` 的处理函数里，我们会增加一个动作：把 m 追加到本地日志。这样才把消息交付转换成日志记录。

尤其要分清 **receive 与 deliver**。网络先送来哪一个包，可以因节点而异；全序广播不能据此让各节点向上层交付不同的消息顺序。

`broadcast(m)` 也不应被理解为“立即写入自己的日志”。否则 A 会先写 a，B 会先写 b，第一条从一开始就不一致了。发送者也必须等待自己的通信服务交付消息。

## 2. 全序广播提供什么保证

全序广播向使用者提供两个主要接口：提交消息的 `broadcast`，以及收到有序通知的 `deliver`。它不是让使用者每次去查询“大家选了什么”，而是在消息可以交付时通知使用者。

为对应本书的共享日志，本文使用这样的保证：消息来自真实的广播请求，每条消息不重复交付；未故障节点的广播最终能交付；已经交付的消息会可靠地传播给其他未故障节点；各节点已交付的序列沿着同一个顺序增长。

例如 `[b]` 与 `[b,a]` 是同一序列的不同长度，允许暂时同时存在；`[b]` 与 `[a]` 则不是。这里采用与书中要求相匹配的前缀顺序和故障语义。不同文献中的普通、uniform、prefix-order 版本有细节差异，不能只看“全序”两个字。[Défago 等，全序广播综述 §2.3–2.5](https://dspace.jaist.ac.jp/dspace/bitstream/10119/4883/1/defago_et_al.pdf)

下面先用一个无故障的小实现展示流程。之后构造共享日志和决定算法时，依赖的是上述完整接口保证，而不是假定这个小实现已经解决了所有故障。

## 3. 一个具体流程：先排号，再按号交付

为了看清读写动作，暂时增加一个排号节点 S。假设本节所有节点都不故障，消息不丢失、不重复，最终都会到达，但到达顺序可以不同。S 串行处理请求。这个例子不需要其他节点为顺序投票。

每条消息带一个唯一标识，例如 `mA=(A,1,a)`。a 是提议值，`(A,1)` 用来区分消息，避免把相同值的不同请求当成同一条消息。

### 第一步：把提议交给排号节点

A 调用 `broadcast(mA)`，B、C 分别提交 mB、mC。这个调用读取本节点的提议，构造请求并发送给 S。此时三份应用日志都是空的。

假设 S 的接收顺序是 mB、mA、mC。S 维护一个初值为 0 的计数器 `next`，每处理一个新请求，就读取 next，把它作为位置编号，再把 next 加一。

S 得到以下结果，并把带编号的消息发给 A、B、C，包括原发送者：

```text
(0, mB)    # 值 b
(1, mA)    # 值 a
(2, mC)    # 值 c
```

这里写入的是 S 的编号状态和消息映射。S 并没有远程修改 A、B、C 的本地日志。编号也不是消息产生时间，只是这次排定的顺序。

### 第二步：接收可以乱序，交付不能跳号

每个节点的通信层维护两项状态：`pending` 暂存已收到但尚未交付的消息，`nextToDeliver` 表示下一个应交付的位置，初始为 0。

假设 A 先收到 `(1,mA)`。它把消息写入 `pending[1]`，然后检查 `nextToDeliver=0`。位置 0 还没收到，所以**不能交付 a，也不能把 a 写入应用日志**。

随后 A 收到 `(0,mB)`。它写入 `pending[0]`，发现现在可以交付位置 0，于是发出 `deliver(mB)`，再把 nextToDeliver 推进到 1。因为位置 1 已经在缓冲里，它随后又发出 `deliver(mA)`。

| A 上的事件 | 协议接收缓冲 | 向上层交付 | 上层日志 |
| --- | --- | --- | --- |
| 初始 | 空 | 无 | `[]` |
| 收到 `(1,mA)` | `{1:mA}` | 无，等待位置 0 | `[]` |
| 收到 `(0,mB)`，处理位置 0 | `{1:mA}` | mB | `[b]` |
| 继续处理已缓冲的位置 1 | 空 | mA | `[b,a]` |
| 收到并处理 `(2,mC)` | 空 | mC | `[b,a,c]` |

B、C 的收包顺序可以与 A 不同，但都从位置 0 起连续交付。排号节点只给每个位置安排一个消息，接收者又不跳号，因此三者向上层交付的顺序相同。

这说明了有序交付可以怎样工作，却没有证明它能容错。S 如果停止工作，编号就可能不再推进；它若恢复后重复使用编号，还可能破坏已有顺序。处理这些情况需要额外机制，不能藏在“排号”两个字里。本节只承担演示读写流程的任务。

## 4. 在交付接口上接一份本地日志

接下来把全序广播视为已经满足约定的通信服务。每个节点各自维护 `localLog`，没有谁需要直接写另一台机器的日志。

下面是停止故障模型下的示意代码：节点可以停止，但不在本段代码中处理重启；交付回调在本节点按序执行，不并发插入日志。

```text
requestAppend(message):
    TOB.broadcast(message)

on TOB.deliver(message):
    localLog.append(message)       # 写本节点的日志
    notifyWaitingReaders()

read(k):
    wait until localLog contains position k
    return localLog[k]            # 读本节点的日志
```

这里的 `requestAppend` 只是提交请求。若还要提供“追加成功并返回位置”的接口，应当等到对应消息已经安装到可读取日志中，再按接口约定返回；不能把请求发出去当作追加完成。

如果 A 的通信服务交付 b，A 就写自己的日志；B 收到交付通知后，B 才写自己的日志。通信服务保证交付序列相同，本地处理又保持这个顺序，于是三份物理日志构成同一个逻辑日志。

某一时刻可以是：

```text
A.localLog = [b,a]
B.localLog = [b]
C.localLog = []
```

C 读取位置 0 时要等一等；它不能因为日志为空，就把自己的 c 填进去。稍后它写入的第一条也必须是 b。

### 为什么这满足共享日志的要求

| 共享日志要求 | 从哪里得到 |
| --- | --- |
| 最终追加 | 未故障请求者的广播最终被交付，回调把它追加到本地日志 |
| 可靠传递 | 通信服务让已交付消息最终到达其他未故障参与者，后者也会记录 |
| 只追加 | 上层只向末尾追加，不覆盖或插入已记录条目 |
| 一致同意 | 各节点保持相同交付顺序，因而同一条目前面的记录序列相同 |
| 有效性 | 通信服务不凭空交付未广播的消息 |

“最终”还要求未故障节点继续执行回调和读取，存储没有超出模型的失败。一个调用线程停了、磁盘写满了，不能要求上面几行代码照样完成。

如果采用本书包含重启恢复的要求，还需要把日志持久保存：条目成为上层可读取的记录前，先完成所需的持久化；恢复时重建日志位置，并正确处理消息重放和去重。上面的内存列表示例没有实现这一层，单靠广播也不会自动生成持久文件。

## 5. 读第一条，就得到一个共同决定

现在有一份满足约定的共享日志。为这一次共识使用独立的、初始为空的日志；A、B、C 分别提出 a、b、c。不要复用已经含有其他业务记录的日志第一条。

每个节点执行同样的程序：

```text
propose(value):
    requestAppend(messageWithUniqueId(value))
    first = read(0)
    decidedValue = first.value
    return decidedValue
```

这段程序读写的对象很明确：提交时读取自己的提议；交付回调写本地日志；决定时读取本地日志位置 0，再写自己的 `decidedValue`。它不直接读取其他节点的候选变量，也不需要等其他节点宣布自己选了什么。

沿用前面的顺序，第一条是 b。可能 A 先读到 b 并决定，B 稍后决定，C 最后决定。它们的决定时间不同，决定值相同。

**“第一条”是共同日志的位置 0。** 它不是自己的第一条请求，不是网卡最先收到的包，不是字母最小的值，也不要求在物理时间上最早提出。本例 A 虽然先收到自己的 mA，仍然必须等位置 0 的 mB，然后决定 b。

节点也不用等自己的提议交付。A 读到 `[b]` 时就能决定，哪怕 a 还没出现在日志里。日志还可以继续增长，但这一次决定不再改变。

## 6. 为什么这个决定算法成立

这里的证明是条件性的：**假设共享日志已经提供上述保证，且至少一个未故障参与者提出值并继续运行。** 本文证明怎样使用这个工具，不证明工具本身如何在故障下实现。

**决定来自提议。** 日志第一条来自某个追加请求，而这份日志只接收本次共识的候选值，所以决定值一定是参与者提出过的值。

**大家不会决定不同的值。** 谁读到位置 0，读到的都是同一条记录。落后的节点只能等待，不能选择另一个“临时第一条”。

**决定不会反悔。** 日志已读条目不变，程序也只决定一次。后续 a、c 被追加，不会挤掉已经位于位置 0 的 b。

**未故障参与者最终能够决定。** 至少一个未故障节点的提议最终会进入日志，因此日志最终非空；可靠传递使其他未故障节点也能读到第一条。它们继续执行，就会结束等待并作出决定。这个论证继承了共享日志本身的进展条件，没有凭空增加可用性。[Chandra 与 Toueg，§7：共识与原子广播的转换](https://courses.csail.mit.edu/6.852/08/papers/CT96-JACM.pdf)

即使 b 的提出者后来崩溃，其他节点也不需要等它亲自通知结果。一旦 b 已作为确定条目交付，传播它是共享日志服务的责任。若使用重启模型，决定状态也需要保存，或者在恢复后从同一日志第一条重新得到，不能开启一份空日志另选一次。

这就是 DDIA 那两句话之间的连接：**全序广播决定交付顺序；各节点把交付结果依次记录，得到同一个逻辑日志；各自读取它的第一条，便得到同一个提议值。**

请求可以先后不同，收包可以乱序，节点可以读取不同长度的前缀。真正不能各行其是的，是交付给上层的确定顺序。理解了这一点，“哪一个值最先被交付”就不再是网络竞速，而是“共同日志的第一条是什么”。
