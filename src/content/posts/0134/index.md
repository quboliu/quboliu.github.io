DDIA 第二版在“使用逻辑时钟执行约束”中提出：即使有线性一致的递增 ID 生成器，也还不足以实现容错的锁和唯一性约束。

一个自然的反问是：三个请求分别拿到 `11、12、13`，服务端比较大小，把锁授予 `11`，不就解决了吗？

**这个方案可以成立，但正确性来自服务端的原子裁决，不是 ID 的大小关系。**

## 1. 最小 ID 获胜，是规则，不是锁的定义

锁的互斥要求是：同一时刻最多只有一个有效持有者。用户名唯一性要求是：同一个用户名不能同时分配给两个账户。

两者都没有要求编号最小的人必须获胜。DDIA 只是尝试了一种方案：给竞争请求分配时间戳，选择最小者。选定这条规则之后，才需要回答“我如何知道自己的时间戳最小”。[DDIA 第二版，第 10 章](https://learning.oreilly.com/library/view/designing-data-intensive-applications/9781098119058/ch10.html#sec_consistency_linearizable_id)

## 2. 能比较三个请求，不代表请求已经收齐

假设服务端收到：

```text
11：申请锁
12：申请锁
13：申请锁
```

如果竞争者确实只有这三个，选择 `11` 没有问题。但服务端怎么知道没有下面这个请求？

```text
10：已经取号并发出申请，但请求仍在网络中。
```

**取号顺序不等于申请到达顺序。** 即使取号服务是线性一致的，也只能约束编号的分配，不能保证携带编号的后续请求按序到达。

因此，“已收到的请求中，11 最小”，不等于“全部竞争请求中，11 最小”。线性一致的取号服务能排除后来新开始的取号请求拿到更小编号，却不能排除更小编号早已发出、申请仍未到达。

也不能简单地说“等一秒就收齐了”。没有可靠的延迟上界或额外协议，就无法仅凭超时区分“没有请求”和“请求尚未到达”。

## 3. 让迟到的 10 失败，可以吗？

当然可以。服务端可以采用下面的规则：

```text
收到 11：锁空闲，设置持有者为 11，返回成功。
收到 12：锁被占用，返回失败。
收到 13：锁被占用，返回失败。
收到 10：锁仍被占用，返回失败，不因编号更小而抢占。
```

只要 `11` 尚未释放锁，这个处理就满足互斥。它放弃的是“全体竞争者中最小 ID 获胜”，不是锁的正确性。

真正关键的是，服务端必须把下面两步作为一个原子操作：

```text
检查锁是否空闲 → 如果空闲，就设置持有者
```

否则，两个处理线程可能同时看到“空闲”，随后各自写入持有者并返回成功。无论请求编号排得多整齐，互斥都会被破坏。

在不考虑故障的单服务端场景中，可以用单线程串行处理、互斥锁或 CAS 完成这次原子转换。此时，把 `11、12、13` 换成互不重复的随机请求标识，也一样能授锁。

## 4. CAS 多提供了什么？

对初始空闲、尚未发生释放的一把锁，竞争者执行：

```text
CAS(owner, 空, A)
CAS(owner, 空, B)
```

线性一致的 CAS 保证只有一次能成功把 `owner` 从空改为自己的标识。成功响应已经表示“你取得了锁”。取号成功却只表示“你的编号是 11”，并不表示具体资源已经归你。

所以差别不是“CAS 只看局部信息，ID 必须看全局信息”。**CAS 操作的是竞争者共同认可的权威状态，并原子地修改它；ID 生成器只分配编号，没有修改锁的归属。**

分布式 CAS 的实现仍然需要协调，不能在任意一个可能过期的本地副本上比较后，就宣布全局成功。

## 5. 为什么 DDIA 接下来讨论共识？

加入一个服务端裁决，解决了谁能获得锁的问题，却还要处理这个服务端自身的故障。

假设主节点把锁授予 A，返回成功后宕机；备用节点不知道这次授锁，接管后又把锁授予 B。两个客户端便可能同时认为自己持有锁。

要在故障后继续服务，新的裁决者就必须保留已经确认的归属，不能重新作出冲突决定。共识协议可以支撑这种复制状态机，让副本对已提交的授锁决定保持一致；网络分区时，不能允许互不通信的两边都任意授锁。

这正是 DDIA 从 ID 生成器转向共识的原因：**编号可以比较，决定还必须被一致地执行和保留。** 若锁还涉及租约过期与旧持有者继续操作，则另需考虑 fencing；那不是编号排序自动解决的问题。

书中“需要听取每个节点的消息”，针对的是直接以时间戳最小者获胜、却没有其他确认机制的方案，并不是说所有锁实现都必须等待全部节点。

回到 `11、12、13` 的问题：选 `11` 完全可以。需要认清的是，方案里真正完成互斥的，是你补上的“服务端原子地授予锁”，而不是“11 比 12 小”。
