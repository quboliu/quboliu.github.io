DDIA 第二版第十章把单领导者复制作为 shared log 的例子。只有一个领导者写日志，为什么还叫“共享”？如果多个客户端都把请求交给同一台服务器，那服务器上的日志是不是都算共享日志？

这两个问题，需要分清谁请求追加、谁执行追加，以及大家是否在使用同一个日志序列。

## 多个请求者，一个日志序列

书中对 shared log 的起点很直接：**多个节点可以请求向同一个日志追加条目。** 实际执行追加的，可以只有一个领导者。[DDIA 第二版第 10 章](https://learning.oreilly.com/library/view/designing-data-intensive-applications/9781098119058/ch10.html)

例如，客户端 A 请求追加 a，客户端 B 请求追加 b。领导者决定顺序为 `[a, b]`，各追随者随后按这个顺序应用。多个请求者共用一个序列，与一个领导者负责排序并不矛盾。

这里的“同一个”是逻辑上的同一个。日志可以只有一份物理存储，也可以在多台机器上各存一份。**shared 说明参与者共用日志，replicated 说明日志有多个副本；这是两个不同的问题。** CORFU 就把分布在多台设备上的存储，对外提供为多个客户端共同追加和读取的一份日志。[CORFU 论文介绍](https://www.microsoft.com/en-us/research/publication/corfu-a-shared-log-design-for-flash-clusters/)

## 多客户端，不自动等于共享日志

如果每个客户端各有一本独立日志，只是存在同一台服务器上，它们没有共享同一个序列。

如果服务器处理许多请求，顺便写入内部调试日志，单凭“客户端很多”，也不能断定系统提供了共享日志抽象。

但如果多个参与者可以请求向同一日志追加内容，并按共同的顺序读取，那么它确实可以是共享日志。日志里记录的是调试信息、业务事件还是数据库写入，不是决定性区别。

这个接口也不必直接暴露给最终用户。数据库客户端调用写入接口，复制模块使用日志接口；共享日志可以是系统内部的组成部分。

因此，不能仅凭服务器服务了多人，就认定它有共享日志；也不能因为日志由一台服务器维护，就否认它是共享日志。

## 第十章还要求这本日志不能反悔

“允许多个节点请求追加”说明了共享方式。为了用它解决共识问题，书中接着给出了更严格的要求：

| 性质 | 要求 |
| --- | --- |
| 最终追加 | 未崩溃的请求者最终能在日志里读到它请求追加的值 |
| 可靠传递 | 一个节点读到的条目，其他未崩溃节点最终也能读到 |
| 只追加 | 已读到的条目不再改变；重读时顺序不变，包括崩溃重启后 |
| 一致同意 | 两个节点读到同一条目时，此前读到的条目序列必须相同 |
| 有效性 | 日志中的值必须来自某个追加请求 |

这些要求不意味着所有节点必须同时追到日志末尾。一个读到 `[a, b]`，另一个暂时只读到 `[a]`，可以是正常的滞后；它们不能分别认定共同历史是 `[a, b]` 和 `[b, a]`。

还要区分逻辑日志与实现中的暂存记录。例如 Raft 的未提交尾部可以在换主时被覆盖；已经提交的条目则必须保留。不能把磁盘上暂存过的每条记录，都当作已经通过共享日志接口交付的确定历史。[Raft 原论文，§5.3–5.4](https://www.usenix.org/system/files/conference/atc14/atc14-paper-ongaro.pdf)

## 共识难在维护日志的人出了故障

一个不会故障的服务器就能把追加请求逐个排序。问题从它失联或崩溃时开始：

- 一直等它恢复，剩余节点就无法继续追加。
- 随便找一个副本接替，可能丢掉已经确定的条目。
- 旧领导者只是网络失联而非死亡，还可能继续接受写入，与新领导者产生冲突。

共识协议需要在允许的故障范围内保住已确定的顺序，并在满足通信、存活节点数量等进展条件后继续追加。多放几个副本，或加一个自动重启脚本，都不直接解决这些问题。

所以，书中一方面说单领导者复制是共享日志的例子，另一方面又指出：没有故障转移的单领导者复制，不满足领导者崩溃后的活性要求。前一句介绍基本抽象，后一句指出容错实现还缺什么。关于进展条件，可接着读[FLP 与现实共识算法的承诺](/posts/0139/)。

**让大家共用一本按顺序追加的日志并不神秘；共识这一章真正要解决的是，负责维护它的节点出了故障，大家还能否继续使用同一本、不会反悔或分叉的日志。**
