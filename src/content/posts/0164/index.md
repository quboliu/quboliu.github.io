DDIA 第二版第 13 章 P782 有一段话，初读很容易产生一个直觉上的反驳：

> 要把写入路径一直延伸到终端用户，就必须从根本上重新思考许多系统的构建方式：摆脱请求/响应交互，转向发布/订阅数据流。这需要投入工作，但好处是可以让 UI 响应更灵敏，并提供**更好的离线支持**。

反驳是这样的：客户端离线之后——

1. 请求/响应模式下，离线拿不到服务端数据；
2. 发布/订阅模式下，离线**同样**拿不到服务端数据。

既然都拿不到，「更好的离线支持」从何谈起？难道作者偷偷假设请求/响应模式的客户端完全无状态、而发布/订阅模式的客户端有部分状态？如果是这样，离线的客户端在本地产生的变更，重连后与服务端冲突，这不是反而带来问题吗？

这个反驳有一半是对的，另一半漏掉了一个关键变量。本文把这段话拆开注解。

## 1. 先承认对的部分

「离线就是离线，两种模式下都收不到服务端更新」——这在物理上完全正确。作者自己也承认，就在这段话前面几页：

> 设备有时会离线，在此期间无法接收服务器发来的任何状态变更通知。

所以「更好的离线支持」**绝不是**指「离线时还能收到新数据」。

至于第二个猜测——作者确实假设了状态差异，而且他在文中**明说**了：

> 过去，Web 浏览器是**无状态客户端**，只有在连接互联网时才能完成有用的工作（离线时几乎只能上下滚动之前在线加载过的页面）。然而，如今的单页 JavaScript Web 应用已经具备许多有状态能力，包括客户端 UI 交互以及浏览器中的持久本地存储。

整个论证的前提是：客户端从「无状态的窗口」变成「有状态的副本」。而发布/订阅，正是让这份本地状态保持新鲜的机制。这个论断的真正结构是：

```text
无状态客户端 + 请求/响应   ←—— 对照组（旧 Web）
有状态客户端 + 发布/订阅   ←—— 主张（写入路径延伸到终端）
        ▲
        └── 「更好的离线支持」来自这个组合，不是来自 pub/sub 本身
```

## 2. 比较的真正对象：不是「能否拿到新数据」，而是三件事

「更好的离线支持」比较的不是离线期间的信息获取能力（两边都是零），而是：

### 2.1 断线那一刻，手里有什么

- **请求/响应**：本地状态是**按需、惰性**填充的——你只缓存了你恰好点过的页面、调过的接口。缓存什么时候过期、哪些是旧的，客户端自己不知道（HTTP 缓存头只是粗粒度近似）。断线时手里是一堆零碎的、新旧不明的碎片。
- **发布/订阅**：只要在线，服务端变更**持续流入**设备，本地维护的是一个**完整的、截至断线时刻新鲜的副本**。书里的话：设备上的状态是「服务器状态的缓存」，是「远程数据中心状态的本地副本」。

```text
请求/响应，断线时手里：              发布/订阅，断线时手里：
┌─────────────────────┐            ┌─────────────────────┐
│ 缓存碎片: 点过的页面 │            │ 完整本地副本         │
│ 新旧不明、缺页漏项   │            │ 新鲜度=断线那一刻    │
│ → 退化为白屏/网络错误│            │ → 退化为「暂停更新的 │
└─────────────────────┘            │    完整应用」        │
                                   └─────────────────────┘
```

区别不是「离线时能不能同步」，而是「离线时你退化成什么」：一个退化成白屏和转圈，另一个退化成**一个暂时停止更新的完整应用**。

### 2.2 重新上线时，怎么恢复

- **请求/响应**：断线几小时后，客户端**不知道这期间服务端改了什么**。要么全量重新拉取（贵、慢），要么自己发明一套版本比对/差异协商协议——这正是同步引擎要解决的核心难题，在请求/响应模式里得从零造。
- **发布/订阅**：如果订阅挂在**基于日志的消息代理**上，断线期间的事件在日志里**排着队等你**。重连后从上次消费的偏移量（offset）继续读，精确补上漏掉的事件——不重拉全量、不比对差异、一条不漏。

```text
服务端事件日志:  e1 e2 e3 e4 e5 e6 e7 e8 e9 ...
                       ▲断线          ▲重连
                       │              │
设备消费进度:  e1 e2 e3┘              └─ 从 offset=4 继续，
                                         精确补上 e4~e9
```

这就是书中那句「这个问题我们已经解决了」：每台设备就是一个消费者组里的小型订阅者，断线重连追日志，是 Kafka 消费者每天都在做的事。

### 2.3 离线是不是一个「特例」

这是最深的一层，也是第 6 章里那句点题的话：

> 使用同步引擎后，应用不需要单独的离线模式：**离线就等同于网络延迟非常大**。

```text
请求/响应:   在线 ──────────────┐
                                ├─ 两条代码路径、两套 UI
             离线 ──────────────┘  （离线是异常分支，要单独写）

日志+订阅:   lag=10ms ─── lag=5min ─── lag=10h ───▶
             （在线）     （弱网）      （离线）
             同一条代码路径，只是滞后量不同
```

在日志+消费者的模型里，「在线」和「离线」不是两条代码路径，只是订阅滞后量（lag）是 10 毫秒还是 10 小时的区别。而在请求/响应模式里，离线是必须单独处理、单独写 UI 的异常分支。

## 3. 现实系统里的对照

这个架构不是设想，已经在几类系统里跑了很多年：

- **WhatsApp / 微信**：消息模型就是每设备一个订阅队列。手机关机三天，开机后按序补齐所有消息——「消费者偏移量」直接用在终端设备上。想象微信改成纯请求/响应：每次打开都要问「我错过的消息有哪些？」，服务端得为每个客户端维护复杂的已读/未读协商——这正是早期轮询式 IM 的痛点。
- **Firestore / Firebase**：客户端持久缓存由订阅维护，离线时读写全部落在本地，重连后自动同步。官方卖点的 "offline support" 就是这么来的。
- **Linear / Figma / Google Docs**：Linear 整个前端跑在一个同步引擎上，本地副本是事实来源，渲染零网络等待，断网照常建 issue、改状态，联网后后台同步。这正是书里引用的 "sync engine / local-first" 一脉（第 6 章「同步引擎与本地优先软件」）。
- **Git**：Kleppmann 点名它是本地优先系统。`git clone` 拿全量日志，`git pull` 从偏移量追增量——结构上和 Kafka 消费者一模一样。

## 4. 正面回答冲突质疑

开头的反驳里最尖锐的一句是：离线期间本地有变更、服务端也有变更，重连后冲突——这能叫「更好的离线支持」吗？这不是带来问题吗？

**对，但这不是发布/订阅带来的问题，而是「允许离线写」这个功能本身的代价。**

关键在于比较基准：请求/响应模式并没有「避免」冲突，它只是**禁止**离线写——断网时提交按钮要么报错要么转圈。如果产品需求是「地铁里也要能记笔记」，那么无论用什么传输模式，都必须：本地暂存写入 + 重连后合并 + 处理冲突。请求/响应不会让这个需求消失，只会让你在没有基础设施支持的情况下硬造它。

而事件日志架构恰恰给了处理冲突所需的原材料：事件有**全局排序、时间戳、持久日志**，冲突检测（版本向量）、自动合并（CRDT）、最后写入获胜（LWW）这些第 6 章多领导者复制的机制可以直接嫁接上去。事实上这条注解线的心智模型就是：**客户端 = 多领导者复制中的一个副本，同步引擎 = 复制协议**。冲突解决是这个架构里被正面承认和解决的问题（「自动冲突解决足以构建许多有用的应用」），而不是被掩盖的问题。

另外值得注意：大量应用的写冲突实际很罕见——数据天然按用户分片（你的笔记只有你在写）。冲突主要出现在真正的多人协作场景，而那正是 CRDT/OT 的领地。

## 5. 顺带解释「UI 响应更灵敏」

同一个根因：**本地有完整副本**。

- **读**：本地查，零网络往返，没有 loading 态；
- **写**：乐观更新（optimistic update），UI 立即反映变更，事件异步推给服务端；
- **协作**：别人的变更通过推送在一秒内到达你的屏幕，而不是等你刷新。

请求/响应模式下，每一次交互都要等一个网络往返；在蜂窝网络（慢、抖、经常假死）上，这个等待是用户体验的主要杀手。所以书里把两个好处放在一起说——它们都是「状态在本地」这一个事实的两个推论。

## 6. 一句话总结

「更好的离线支持」的真正含义是：**发布/订阅 + 持久日志，把客户端从「无状态的窗口」变成「服务端状态的持久副本」**。于是：

- 离线时，应用退化为「一个完整但暂时不更新的应用」，而不是废铁；
- 重连时，靠消费者偏移量精确追赶，不重拉、不比对；
- 离线不再是需要单独处理的特例——只是复制延迟变大了。

代价正如开头的质疑所敏锐指出的：一旦允许离线写，冲突就不可回避。但那是「离线写」这个功能本身的价格，而事件日志架构恰好提供了结算这笔账的工具。
