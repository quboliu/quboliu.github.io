DDIA V2 的 10.6.2 先说，把增量写入共享日志，对条目中的数值求和，就能实现原子的 fetch-and-add；随后又说，对日志条目计数可以生成 fencing token。

读到这里容易疑惑：取值加一、条目求和、条目计数，不都是同一个数吗？怎么又成了“隔离令牌”？

**如果初始值为 0、每条记录都加 1，更新后的计数器值确实等于条目数。但 fetch-and-add 不限于加 1；它返回的是旧值。Fencing token 则是在讲递增数字的另一种用途。** [DDIA V2 第 10 章，10.6.2](https://learning.oreilly.com/library/view/designing-data-intensive-applications/9781098119058/ch10.html)

## 1. 先纠正“取值并加一”这个限制

本地双语版将此处的 fetch-and-add 译为“取值并加一”，范围缩小了。这里应理解为“取值并加”：取出旧值，并加上指定的增量。加一只是特例。

它的语义是：

```text
fetch_and_add(增量)：
    旧值 = 计数器
    计数器 = 旧值 + 增量
    返回旧值
```

这段伪代码描述的是一个原子操作，不是让调用者分别执行一次普通读和一次普通写。并发操作必须表现得像按某个先后顺序逐次完成，不能有两个加法因交叉读写而丢掉其中一次更新。

## 2. 共享日志怎样实现这件事？

假设计数器初始值为 0，这条日志专门记录它的增量。三个并发请求由日志服务确定顺序：

| 日志位置 | 条目中的增量 | 返回的旧值 | 更新后的值 | 已有条目数 |
| --- | ---: | ---: | ---: | ---: |
| 1 | +5 | 0 | 5 | 1 |
| 2 | +3 | 5 | 8 | 2 |
| 3 | +10 | 8 | 18 | 3 |

第 3 次操作返回 8，因为排在它前面的增量之和是 `5 + 3`；它自己的增量加入后，计数器变成 18。条目数量则是 3。

设第 k 条增量为 dₖ，初始值为 C₀：

```text
第 k 次操作返回：C₀ + 第 1 至 k−1 条增量之和
第 k 次操作完成后的值：C₀ + 第 1 至 k 条增量之和
```

**自己的日志位置确定后，自己的旧值也随之确定。** 即使回复较晚、后面又追加了记录，也不能改成返回回复时的最新总和。

这里不是“先读计数器，再追加增量”。做法是先让增量进入已确认的日志顺序，再根据它之前的完整前缀计算返回值。应用不能把未确认的位置或尚有缺口的前缀当作最终结果；所用日志服务还须满足操作的实时先后要求，才能提供线性一致的 fetch-and-add。

因此，原子性来自日志服务确定共同顺序，以及计数器实现按该顺序计算结果的配合。日志数据不会自己做加法。

实现时不必每次从头求和，可以维护累计值和已处理位置。检查点或日志压缩也必须保留这些信息，不能把“当前磁盘上剩余的条目数”当作历史累计值。

## 3. 如果每条都加 1，确实退化成计数

初始值为 0，每次增量为 1：

| 第几次操作 | 返回旧值 | 更新后计数器值 | 条目数 |
| --- | ---: | ---: | ---: |
| 1 | 0 | 1 | 1 |
| 2 | 1 | 2 | 2 |
| 3 | 2 | 3 | 3 |

所以，“增量之和等于条目数”在这个特例中完全正确，只是不能把本次返回的旧值也混进去。旧值比更新后的值少 1。

要生成递增编号，可以使用返回的旧值，也可以使用更新后的值或日志位置，只要规则统一，编号不倒退、不复用。选择从 0 还是从 1 开始，不影响后面的 fencing 原理。

普通的 fetch-and-add 还可以接受负增量，因此任意增量的累计和未必递增。**适合生成 token 的是始终递增的编号，不是随便一个计数器的当前值。**

## 4. Fencing token：把递增编号用作授权批次号

假设一个共享文件由持锁者更新。每次成功授予新的锁，都给持有者一个比上次更大的 token：

```text
甲获得锁，token = 41
甲长时间暂停，锁过期

乙获得锁，token = 42
乙携带 42 写文件，存储服务接受并记住 42

甲恢复，仍以为自己有锁，携带 41 写文件
存储服务发现 41 < 42，拒绝写入
```

41 和 42 可以来自加一计数器，也可以来自日志中对应授权事件的位置。**没有发明一种新的数，只是把递增编号解释为“这是哪一批授权”。** [DDIA 作者对 fencing 的说明](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)

编号必须与授权绑定：同一资源的后一次授权使用更大的编号。旧持有者不能在恢复后随意申请一个新编号，就把旧授权冒充成新授权。若使用日志位置，应使用与该次成功授权关联的位置，不能给每次普通写请求随手发个新号。

token 不要求连续。两次授权之间夹着其他日志条目，编号从 41 跳到 58 也可以；需要的是新旧关系，而不是相差恰好为 1。

## 5. 谁真正挡住旧持有者？

计数器只产生编号。真正拒绝旧请求的是受保护资源的接收方。

| 部分 | 责任 |
| --- | --- |
| 授权服务 | 将递增 token 与每次成功授权绑定 |
| 请求发送者 | 使用该次授权的 token 发请求 |
| 资源接收方 | 记住已接受的最高 token，拒绝更小的 token |

接收方必须把校验、更新最高 token 和实际修改协调起来。不能先检查 41 合法，暂停后让 42 写入，再继续执行 41 的旧写入。故障恢复后，也不能忘掉已建立的授权边界。

同一授权可以包含多次写入，因此相等的 token 通常可以继续使用。**Fencing 不负责同一授权内的请求去重，也不决定这些请求的业务顺序。**

它也不会让旧持有者在锁过期的瞬间自动失效。上例中，存储服务是在接受 42 后拒绝 41；如果尚未得知新 token，单凭最高已见编号，不能判断旧锁是否过期。若业务要求更强的交接边界，需要把接收方安装新 token 纳入交接流程。

同样，生成编号的请求若超时，重试可能再占一个位置。编号有间隔通常无妨；若要把重试视为同一次加法或同一次授权，就还需要请求标识和去重。

这段原文实际连着讲了两件事：

```text
日志记录增量 → 按前缀求和 → 得到原子计数器及每次操作的旧值

递增编号 → 与授权绑定 → 接收方比较编号 → 拒绝旧授权的请求
```

**前半段讲如何得到数字，后半段讲如何使用数字。日志提供顺序，计数器计算数值，接收方执行 fencing；三者各有职责。**
