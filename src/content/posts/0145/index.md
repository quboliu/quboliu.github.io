DDIA V2 的 10.6.2 说：共享日志可以用于实现可串行化事务。条件是，每个条目代表一个待执行的确定性事务，各节点按相同顺序执行这些事务。

这句话容易让人疑惑：把事务排个序，怎么就保证隔离性了？日志会检查事务冲突吗？谁负责执行？

**原文回引的“实际串行执行”是关键：共享日志确定顺序，执行器按这个顺序逐个执行完整事务。事务的读取、判断和写入都在其中，不能只排列最后的写入。** [DDIA V2 第 10 章，10.6.2](https://learning.oreilly.com/library/view/designing-data-intensive-applications/9781098119058/ch10.html)

## 1. 可串行化允许事务相互影响

这里的可串行化属于 ACID 的隔离性：事务的执行效果，等价于按某个顺序逐个执行。

它不要求事务彼此没有影响。甲先订走座位，乙随后发现座位已被占用，就是正常影响。它排除的是：事务交叉执行后，出现无论谁先谁后、逐个执行都不可能出现的结果。

可串行化也不要求实际并行执行。**直接一个接一个地执行事务，本身就满足可串行化。** 并行执行是性能选择，执行效果等价于串行才是正确性要求。

## 2. 从两个订座请求到一个串行结果

假设各副本保存相同的数据，座位 S12 起初空闲。甲乙同时提交：

```text
T甲 = 预订(S12, 甲)
T乙 = 预订(S12, 乙)
```

`预订` 是一个完整的事务过程：

```text
读取座位状态
如果空闲：分配给该用户，返回订座成功
否则：不修改座位，返回座位已被占用
```

此时提交的是过程及参数，还没有读取座位、判断能否订座。共享日志服务接收两个提议，确定并保存顺序：

```text
第 1 条：T甲
第 2 条：T乙
```

各副本的执行器依次处理：

| 步骤 | 执行内容 | 结果 |
| --- | --- | --- |
| 1 | T甲读取 S12 | 空闲 |
| 2 | T甲将 S12 分配给甲，完成事务 | 甲订座成功 |
| 3 | T乙读取 S12 | 已分配给甲 |
| 4 | T乙完成事务，不修改座位 | 乙订座失败 |

**隔离性就保证在第 2、3 步之间：T乙不能提前读取座位，必须等 T甲完成。** 若前一个事务中止，则先撤销其修改，再处理后一个事务。

客户端可以并发提交，各副本也可以同时处理自己的那份日志；但在这个直接实现中，每个副本内部的事务逐个执行。副本可以有进度差异，在相同日志位置完成后，得到相同状态。

## 3. 日志像计划书，谁制定，谁执行？

在这个方案中，日志可以理解为一份已经确定顺序的执行计划。日志数据本身不运行代码，具体职责由程序承担：

| 部分 | 负责什么 |
| --- | --- |
| 共享日志服务 | 接收提议，确定顺序，并可靠地保存；已确认的历史不能随意改写 |
| 日志本身 | 记录待执行的事务及其顺序 |
| 事务执行器 | 按序执行完整事务，依据当时的数据状态作出判断和修改 |

这是职责划分，不要求三个独立进程。日志服务内部可以用单节点排序，也可以用带故障容错的复制协议；这里使用的是它提供的共同顺序。

日志服务不必先检查甲乙是否争抢同一座位。`T甲 → T乙` 和 `T乙 → T甲` 都能满足可串行化，只是谁订到座位不同。

**排序决定谁先执行；执行时的座位状态决定谁订座成功。** 日志中记录了订座请求，不等于系统已经答应把座位订给请求者。

## 4. 为什么只把写入排好序不够？

考虑另一种执行方式：甲乙都先读取空座位，各自判断“可以预订”，随后才把修改送进日志：

```text
甲读到空闲 → 决定成功
乙读到空闲 → 决定成功
日志依次记录：分配给甲、分配给乙
```

如果执行器盲目应用修改，并向两人都报告成功，日志虽然有序，结果却不符合任何串行执行：完整执行任一预订事务后，另一个都应看到座位已被占用。

问题出在读取和判断已经发生，后来的写入排序没有纠正它们。若系统通过条件写入、冲突校验或中止重试排除了异常，保证来自这些额外机制。

书中方案把读取和判断也放到日志确定的顺序之后。**日志排的是完整事务的执行次序，而不是两份提前算好的写入结果。**

## 5. 存储过程和确定性，各补上什么？

存储过程把读取、判断、写入装进一次完整调用。日志记录过程标识和参数即可，各副本已有对应代码，轮到它时能自行执行，不必每做一步都等待客户端发送下一条 SQL。

确定性要求：相同输入、相同初始状态，执行同一过程得到相同结果。如果过程需要时间、随机数或外部查询结果，就要固定这些输入，不能让各副本临时各取一份。

两项保证要分清：**串行执行保证隔离性；确定性让各副本执行出相同结果。** 存储过程本身不自动保证隔离性，可串行化也不会纠正事务代码中的业务错误。

逐个执行是最直接的解释，不是唯一实现。实际系统可以并行处理事务，但必须通过调度、锁或依赖控制，使效果等价于规定的串行顺序。原文引用的 [Calvin](https://cs.yale.edu/homes/thomson/publications/calvin-sigmod12.pdf) 就包含确定性调度机制。仅按日志顺序启动事务，再任其交叉读写，并不够。

## 6. PostgreSQL 的 WAL 为什么不是同一个模型？

两者记录的内容与时机不同：

| | 本文解释的方案 | PostgreSQL WAL |
| --- | --- | --- |
| 记录什么 | 待执行的事务调用 | 执行过程中产生的修改等记录 |
| 与执行的关系 | 先确定事务顺序，再读取、判断、修改 | 执行过程中产生 WAL，供恢复和复制使用 |
| 隔离性从哪里来 | 执行器按规定顺序执行完整事务 | 并发控制；Serializable 级别还要监测依赖，必要时中止事务 |

WAL 的“预写”要求对应日志先于修改后的数据页落盘，不是说整个事务执行前，先把事务写入日志。内存中的页面可以已经修改，一个事务也会产生多条 WAL。[PostgreSQL 18：WAL](https://www.postgresql.org/docs/18/wal-intro.html)

因此，有序 WAL 不自动带来可串行化。PostgreSQL 的 Serializable 隔离还需要独立的并发控制保证，不能由 WAL 的落盘顺序代替。[PostgreSQL 18：事务隔离](https://www.postgresql.org/docs/18/transaction-iso.html)

回到书中那句话，完整推导是：

```text
并发提交完整事务
    ↓
共享日志服务确定共同顺序
    ↓
每个副本按序逐个执行，包括读取、判断和写入
    ↓
实际串行执行，因此满足可串行化
    ↓
相同初始状态与确定性逻辑，使副本在相同进度得到一致结果
```

这个推导针对同一份有序历史覆盖的数据。各分片各排各的日志，不会自动得到跨分片可串行化；绕过执行规则的读取也需要单独保证。原文紧接着的 Note，正是在提醒跨分片事务还需要额外协调。
