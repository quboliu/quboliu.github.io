Lamport 时钟不能准确识别并发，向量时钟补上了这个能力。为什么混合逻辑时钟（HLC）没有继续解决这个问题？

关键在于：**识别事件的因果关系，和保证事务的读写合法，是两个不同的任务。** HLC 的设计目标是保留因果方向，同时兼顾物理时间含义和存储成本，而不是完整记录因果关系。

## 1. 偏序描述因果，不要求所有事件都有先后

在 Lamport 的定义中，同一进程内的执行顺序、消息从发送到接收的顺序，以及这些关系的传递，共同构成 *happens-before* 关系，记作 `a → b`。

如果既不存在 `a → b`，也不存在 `b → a`，就称这两个事件并发，记作 `a ∥ b`。这里的并发是指不存在因果路径，不要求物理时间上同时发生。这种关系是偏序，因为不是任意两个事件都能比较先后。[Lamport 原始论文](https://lamport.azurewebsites.net/pubs/time-clocks.pdf)

例如，箭头表示因果关系：

```text
    A
   / \
  B   C
   \ /
    D
```

B、C 都在 A 之后、D 之前，但 B 和 C 之间没有因果先后。把它们排列成 `A, B, C, D` 或 `A, C, B, D`，都不违反已有关系。这叫偏序的**线性扩展**：保留原来的先后约束，再给不可比的元素选定顺序。

因此，**给并发事件排序，并不等于宣称它们之间存在因果关系。**

## 2. HLC 保留因果方向，向量时钟保留更多信息

Lamport 时钟保证：如果 `a → b`，那么 `L(a) < L(b)`。但反过来不成立：时间戳较小，既可能是因果上的前驱，也可能只是一个并发事件。

经典向量时钟提供双向判断：在完整维护和传播时钟的模型中，`a → b` 当且仅当 `V(a) < V(b)`。这里的“小于”要求所有分量都不大于对方，且至少一个严格小于；两个向量互不可比，就表示事件并发。[Fidge 论文](https://fileadmin.cs.lth.se/cs/Personal/Amr_Ergawy/dist-algos-papers/4.pdf)

HLC 则延续了 Lamport 时钟的单向保证。它通常表示为 `(时间分量, 逻辑计数)`：先比较时间分量，相等时再比较逻辑计数。在物理时钟同步等假设下，时间分量保持接近物理时间，同时通过逻辑计数维护因果单调性。[HLC 原始论文](https://cse.buffalo.edu/tech-reports/2014-04.pdf)

三者的取舍可以概括为：

| 时钟 | 尊重已传播的因果关系 | 从时间戳识别并发 | 物理时间含义 | 经典实现的空间成本 |
| --- | --- | --- | --- | --- |
| Lamport 时钟 | 是 | 否 | 无 | 固定大小 |
| 向量时钟 | 是 | 是 | 无直接对应 | 随被追踪参与者数量增长 |
| HLC | 是 | 否 | 有，受时钟假设约束 | 固定大小 |

这不是从低级到高级的演进。向量时钟增加因果信息，HLC 增加物理时间含义，解决的需求不同。两者也都无法凭空捕获没有通过协议传播的外部因果关系。

还需注意：不同事件可能得到相同 HLC 值。若要给所有事件建立严格全序，需要额外的平局规则，例如唯一事件标识。时间戳可比较，不代表每个事件都有唯一序号。

## 3. 数据库需要合法顺序，但排好序还不够

数据库中的并发事务，通常指执行区间重叠的事务，不宜直接等同于上面的事件并发。

可串行化允许事务交错执行，只要求实际读取、返回结果和最终状态能由某个串行执行解释。它不要求事务真的排队执行，也不要求串行解释唯一；互不影响的事务可以有多种合法排列。[CockroachDB 官方说明](https://www.cockroachlabs.com/docs/stable/developer-basics.html)

不过，给事务分配可比较的时间戳，并不能自动保证这一点。

假设初始 `x = 1, y = 1`：

```text
T1：读取 y，若 y = 1，就把 x 改为 0
T2：读取 x，若 x = 1，就把 y 改为 0
```

如果双方都读到 1，再分别写入 0，最终得到 `x = 0, y = 0`。这个结果不符合任何串行执行：

- T1 先执行，T2 就应读到 `x = 0`，不再修改 y。
- T2 先执行，T1 就应读到 `y = 0`，不再修改 x。

即使规定 `HLC(T1) < HLC(T2)`，也无法修复 T2 已经读到旧值的事实。数据库必须阻止这种执行，或者让事务中止并重试。

**所以，时间戳排序只是提供顺序；可串行化还要求读写行为与顺序相容。** 它不是简单地给事件因果图做一次排序。关于串行等价的进一步解释，见[《可串行化：不是让事务排队》](/posts/0131/)。

## 4. CockroachDB 为什么适合用 HLC

CockroachDB 使用 HLC 为 MVCC 版本和事务提供时间戳。在简化模型中，时间戳为 T 的读取，可以选择“不晚于 T 的最新已提交版本”。这种版本选择需要方便的大小比较，不要求从时间戳还原完整因果关系。

HLC 的固定大小降低了元数据成本；接近物理时间则方便表达“读取某个历史时刻的数据”。这些是它相对于纯逻辑计数器的实际价值，而不只是“能排序”。

并发控制仍由事务机制完成：处理冲突、推进时间戳、验证先前读取，并在必要时重试。**HLC 提供时间戳，事务协议保证这些时间戳对应的读写历史合法。** [CockroachDB 架构论文](https://www.cockroachlabs.com/pdf/cockroachdb-the-resilient-geo-distributed-sql-database-sigmod-2020.pdf)

这不意味着 MVCC 必须采用标量时间戳，也不意味着向量时钟不能用于数据库。它说明的是：这套设计不需要让时钟承担完整的因果追踪，而是由并发控制机制处理读写约束。

## 5. 三种顺序，不要混为一谈

回到最初的问题，需要分清三个层次：

- **因果偏序**：事件之间已经存在什么先后关系？
- **时间戳顺序**：给定两个时间戳，怎样比较大小？
- **事务串行顺序**：怎样排列事务，才能解释实际的读写行为？

另一个独立约束是实时先后：一个操作已经返回，另一个操作才开始。可串行化本身不要求遵守事务间的实时顺序；严格可串行化才增加这一要求。HLC 接近物理时间，也不能单独保证这种语义。

因此，HLC 没有“不急于补上的缺陷”，而是选择了不同目标：用紧凑的时间戳保留因果方向，并提供物理时间含义。

**不能仅凭 HLC 识别并发，不等于数据库不处理并发；能给事务排出顺序，也不等于已经保证了可串行化。** 时钟负责提供时间信息，事务协议负责让读写符合承诺的语义。
