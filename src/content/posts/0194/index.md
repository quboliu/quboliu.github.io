（三）里我们修正了一个直觉：让出线程不是“改一下 PC”，而是保存现场、选择下一个执行者、恢复现场、再跳转。但这引出了一个更深的问题，一个几乎是本能的追问：

> 改 PC 的“那个人”是谁？

在朴素的想象里，系统里应该有一个类似早期电话接线员的主体：他坐在 CPU 旁边，手里攥着各段程序的地址，时机一到，就把某个地址“接”进 PC 寄存器，完成切换。

这个操作员并不存在。而且更有意思的是，连“程序自己交权”这个退而求其次的说法，也站不住。这是本文要连续破除的两个错误主体。

## 第一问：没有接线员，PC 是被谁改写的

CPU 内部没有任何专职主体盯着 PC。控制权转移在硬件上只有两种发生方式，除此之外没有第三条通道：

- **同步的自陷（trap）**：当前正在执行的指令本身就是一条转移指令——`call`、`ret`、`syscall`。CPU 执行它，PC 随之改变。
- **异步的中断与异常（interrupt / exception）**：CPU 每执行完一条指令，就检查一次中断线。如果有时钟或外设信号，硬件自动保存最少量状态，然后**从中断向量表里取出一个事先写好的地址**，塞进 PC。缺页、除零等异常走的是同一套查表逻辑。

注意这两种机制的共同特征：**目标地址都不是临时算出来的，而是事先写在表里的**。接线员的“知识”没有消失，而是在系统启动时就被预制成了静态数据结构——中断向量表、IDT、syscall 入口寄存器、每个线程的 TCB。操作员的第一部分，被“查表”取代了。

硬件在中断时做的事少得可怜：压几个寄存器、查表、改 PC，仅此而已。完整的上下文切换——保存全部寄存器、运行调度算法、挑选下一个线程——全部是软件做的。硬件只提供钩子，不提供流程。

## 第二问：“程序自己交权”吗——也不对

一个自然的修正说法是：自陷的情况下，是“程序自己执行了转移指令，自己交出了控制权”。硬件层面这没错——改 PC 的确实是当时正在 CPU 上跑的某条指令，不存在 CPU 之外的第三个主体。

但“程序自己”这个主语是错的。应用程序员写的源码里，交权机制的含量是零。hello world 没有一行代码是设计来让出的；一个写得再精心的并发程序，程序员也从未亲手安放过任何一条切换指令。把运行时进程里的每个控制转移点拿出来问“这是谁写的”，答案全部是别人：

1. **硬件代劳，程序零参与**。时钟中断到来，CPU 在两条指令之间直接劫持 PC。应用程序一条指令都没出，纯粹是乘客。hello world 运行一秒被抢占几十上百次，全程零参与。这是唯一真正“非自愿”的机制，也是一切抢占式调度的地基。
2. **指令存在，但住在别人的代码里**。程序员写了 `printf`，但 `syscall` 指令物理上位于 glibc 的包装函数里。应用只是执行流*路过*了别人预埋的转接点。程序员写的是意图，不是机制。
3. **指令存在，但程序员不知道自己“写了”它**。Go 编译器在函数序言里插入栈扩张检查作为抢占点；JVM 在循环回边和方法调用处插入 safepoint 轮询。这些转移逻辑是工具链织进二进制的，源码里没有对应物。
4. **程序员显式写了 `sleep` 或 `yield`**。这是最接近“自愿”的情形，但拆开看仍然只是表达了意图：真正的 trap 指令是 libc 的，真正的切换是内核做的。

所以“自愿让出”的“自愿”，不是应用的自愿，而是平台设计出来的自觉——它被编译器和运行时织进了二进制。**程序二进制是一个缝合体：应用逻辑被缝合在大量不属于程序员意志的检查站之间。**

## 操作员去哪了：拆成了三样无意识的东西

把两问合起来看，接线员并没有消失，而是被还原成了三样没有意识的东西，它们合谋扮演了他的角色：

- **硬件钩子**：指令边界的中断检查，以及 trap 指令本身。这是全部控制权转移仅有的两个物理通道；
- **静态表**：中断向量表、TCB、syscall 入口——操作员的“知识”被预制成了数据结构；
- **一段平时根本不运行的代码**：这是最关键的一样。**操作系统内核不是一个持续运行的“人”，它是一堆只有被中断或自陷唤醒时，才短暂借到 CPU 的代码片段。** 调度器挑选下一个线程的那一刻，CPU 上跑的仍然是普通指令，只不过那段指令恰好属于内核。调度一结束，内核代码随即“退场”，把 CPU 还给被选中的线程。

控制权从不“流动”。每一纳秒都有一个明确的持有者，转移动作永远由硬件在指令边界代劳、或由持有者正在执行的（平台预埋的）指令完成。没有旁观者，没有操作台。

## 往上每一层，都没有发明新的通道

操作系统和语言运行时看起来提供了很多种“切换”——系统调用、信号、线程调度、goroutine 切换、虚拟线程——但它们没有发明任何新的控制权转移通道，只是在硬件的两个钩子上叠加调度策略和数据结构：

- **OS 层**把 trap 包装成系统调用，把中断包装成时钟调度与设备处理，还发明了信号——本质上是内核模仿硬件中断、对进程做的一次“软件版劫持”。
- **Go 运行时**的 goroutine 切换发生在函数调用点和 channel 操作上——也就是编译器插入的检查点（第二类转接点）；Go 1.14 之后的异步抢占通过 OS 信号实现，而信号又骑在硬件中断上。
- **JVM** 的传统线程直接复用 OS 线程调度，GC 的安全点是协作式轮询；虚拟线程（Loom）则在用户态做 continuation 切换，同样是“普通函数返回”式的让出。

于是形成一条完整的退化链：**运行时的抢占 → OS 信号 → 硬件中断**。往下的每一层都没有新的切换原语，硬件给的两个钩子自始至终就是全部。

## 最后留下的模型

可以把这两层直觉的修正合并成一句话：

> 系统里没有接线员，也没有“自觉交权的程序”。硬件只提供两个钩子——自陷与中断；操作员的知识被预制成了表，操作员的流程被拆成了被唤醒才运行的内核代码；而应用程序对于控制权转移而言基本是乘客，它的二进制被平台缝合进了无数不自知的检查站。

所以，“控制权”从来就没有完整地属于过你的程序。它只是在平台铺设好的轨道、表和收费站之间，被托管着前进。
