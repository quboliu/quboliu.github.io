DDIA 第二版 10.4.2 的隐私照片例子提出了一个看似矛盾的问题：用户先把账户设为私密，再上传照片，但照片可能取得比权限修改更小的逻辑时间戳。

逻辑时钟不是保证因果序吗？如果后发生的操作取得更小的时间戳，还能叫逻辑时钟吗？

**可以。这里违背了用户通过外部行动建立的因果先后，却未必违反时钟协议所覆盖的系统内部因果序。** 理解这个例子，关键是看因果关系有没有进入协议。

## 1. 用户串起了两次操作，时钟没有

书中特意安排了两个细节：用户在笔记本上修改权限，然后在手机上上传照片；账户与照片分属不同数据库，照片数据库没有读取账户数据库。[DDIA 第二版：线性一致的 ID 生成器](https://learning.oreilly.com/library/view/designing-data-intensive-applications/9781098119058/ch10.html#sec_consistency_linearizable_id)

从用户角度，操作顺序很明确：

```text
权限修改成功 → 用户看到成功 → 用户拿起手机上传照片
```

但假如手机没有携带权限修改的时间戳，数据库之间也没有传播相关信息，时钟协议看到的就是两条未关联起来的请求。用示意数字表示：

```text
笔记本 → 账户数据库：改为私密，时间戳 100
手机   → 照片数据库：上传照片，时间戳  80
```

连接这两次操作的是用户的行动。人知道上传发生在修改成功之后，照片数据库却没有收到这个信息，本地计数器仍可能落后。

因此，不能笼统地说“两次操作没有因果关系”。准确说法是：**这条因果路径经过了时钟协议没有覆盖的外部事件。**

## 2. “尊重因果序”有一个前提

Lamport 时钟的基本保证是：

```text
如果 a → b，那么 L(a) < L(b)
```

其中的 `→`，由模型内的进程执行顺序、消息发送与接收，以及这些关系的传递构成。相关通信必须按协议携带时间戳，接收方也必须更新本地时钟。

假如上传请求携带了权限修改的时间戳 `100`，照片数据库原有计数器为 `79`，它接收请求时就必须推进：

```text
L := max(79, 100) + 1 = 101
```

之后再为照片写入分配事件时间戳，也必须大于 `100`。如果仍分配 `80`，那才是违反了时钟规则。

不能把实现遗漏的通信随意排除，再声称算法正确。如果某条通信本来就在模型中，却没有传播或合并时间戳，那就是实现没有满足算法前提。这个照片例子的特殊之处，是依赖通过人的跨设备行动传递，并未自动成为协议内的消息。

## 3. Lamport 原论文已经讨论过这个问题

这不是对逻辑时钟的事后辩解。Lamport 在 1978 年论文的 **Anomalous Behavior** 一节中举过几乎相同的例子：一个人提交请求 A，然后打电话让另一座城市的朋友提交请求 B，B 却可能取得更小的时间戳。

电话建立了先后关系，但它是计算机系统外部的通信。论文因此区分了系统内部的事件关系，以及把相关外部事件也纳入之后的关系，并提出可以显式传入前一次请求的时间戳，让后一次请求排在它之后。[Lamport 原论文，第 562 页](https://lamport.azurewebsites.net/pubs/time-clocks.pdf)

DDIA 把“打电话给朋友”换成了“用户从笔记本转到手机”，问题没有变：外部已经建立的依赖，不一定被系统内部的时钟记录下来。

## 4. 为什么这会让私密照片暴露

回到书中的简化 MVCC 场景。假设账户原来公开，权限修改的时间戳为 `100`，照片写入的时间戳为 `80`。如果查看者读取时间戳为 `90` 的快照：

- 照片版本已经可见，因为 `80 ≤ 90`。
- 私密设置尚不可见，因为 `100 > 90`，读到的仍是旧的公开设置。

于是出现了“照片存在，但账户仍公开”的组合。它符合这组时间戳定义的可见性，却违背了用户先收紧权限、再发布照片的意图。

这里不能只问版本有没有按时间戳读取，还要问：**时间戳顺序是否覆盖了应用依赖的先后关系？**

## 5. 两条修复思路

第一条是把依赖显式传入系统。上传请求携带权限修改的时间戳，或者在写入前读取到那次权限修改，并把它的时间戳合并进后续操作。仅仅发起一次读取还不够：读到旧副本上的公开状态，不能建立对那次修改的依赖。

第二条是使用线性一致的递增 ID 生成器。如果前一次取号已经完成，后一次取号才开始，后者就必须得到更大的 ID，不要求客户端显式传入上一个 ID。这是书中给出的另一种解决办法。

它适用于这里“权限修改完成之后，才开始上传并取号”的顺序。但不能进一步推导出：只要 ID 生成器线性一致，整个数据库就自动线性一致。数据提交、读取和权限检查仍有各自的正确性要求。

换成 HLC 或向量时钟，也不能自动补上缺失的依赖。HLC 接近物理时间，但不能仅凭这一点保证所有跨节点的实时先后；向量时钟保留更多因果信息，但前提仍是信息得到传播。

**逻辑时钟保证的不是“现实中凡有因果，时间戳都能正确排序”，而是“纳入模型、按协议传播的因果关系，会得到正确排序”。** 在讨论因果一致性之前，先问一句：这条依赖通过什么传给了下一次操作？
