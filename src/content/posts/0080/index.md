## 摘要

v2ex 上有个经典月经贴：[《做个调查：你们的 Go 项目中会用到依赖注入吗？》](https://v2ex.com/t/1131027)，81 个回复吵成两派——一派说 Go 用 DI 框架是「把简单问题复杂化」，另一派说「项目大了手动注入必然崩溃」。帖子里最尖锐的追问是：不用依赖注入，单元测试怎么 mock 各种依赖？

我维护的 Code Scalpel 后端恰好是一个现成的投票样本：Go 单 module、约 30 个领域包、780+ 源文件，`go.mod` 里 wire / dig / fx / gomock / testify 一个都没有。这篇文章用这个项目的实际代码回答帖子里的几个问题：不用 DI 框架，但把 DI 的思想做对；单测靠窄接口 fake 加真实隔离栈，而不是 mock 框架。

---

## 第 1 章 先想清楚两派在争什么

把 81 个回复读下来，争论其实不在同一个层面上。

反对方的核心论点是心智负担：dig/fx 的容器注册是隐含的运行时逻辑，wire 虽然是编译期代码生成，但也多了一套声明语法要学。有人贴出对比——`container.Provide(ai.NewAiService, dig.As(...))` 对比直接 `ai.NewAiService(...)`，前者并没有更简单，反而多了一层要理解的框架逻辑。

支持方的核心论点有两个。一是初始化顺序：依赖关系是图，新增一个被多处依赖的 service 时，手动方案要人工判断初始化代码插在哪、哪些已有顺序要调整；DI 框架自动拓扑排序。二是修改成本：给一个被广泛使用的 service 加一个新依赖，手动方案要改所有调用点，DI 只改声明。

注意一个事实：这两个论点都是**规模问题**，不是对错问题。所以「要不要 DI 框架」的正确问法是——你的项目规模到了手动方案的痛点阈值没有？

## 第 2 章 不用框架，但 DI 思想要做对

Code Scalpel 后端的答案是手动构造函数注入，关键不在「手动」，而在接口定义的位置。帖子里有位叫 Hyponet 的网友说了一句我认为全场最值钱的话：

> 只需要使用「将 Interface 定义在用的地方，而不是实现的地方」这个小技巧，就基本可以获得 DI 的好处了。

这正是我们的做法。以图谱查询服务为例，`pkg/api/graph/service.go` 的 Service 有 22 个依赖，全部是窄接口——`query.RawReader`、`query.TraversalReader`、`query.CFGReader`……每个接口一个文件，定义在**消费侧**的 `pkg/graph/query/` 目录；Neo4j 包是实现方，包注释里钉死「跨包消费者必须走接口」。装配全部集中在 `cmd/server/main.go`，启动时顺序 new 出来往下传：

```go
// 构造函数即注入点，依赖关系编译期可检查
func NewService(repo Repository, cfg config.GraphConfig, ...) *Service
```

这个结构同时化解了帖子里的两个质疑：

**「全局 Container struct 是 lazy init 还是启动时 new？后者要考虑线程安全」**——我们没有这个问题，因为所有依赖在启动时一次性构造完毕，根本不存在运行时按需创建的单例。

**「手动方案要自己排初始化顺序」**——是真的，但在一个 server 二进制、30 个包的规模下，这就是 main 函数里几分钟的事。而且构造函数签名让依赖关系编译期可检查：少传一个参数直接编译失败，不存在容器运行时才发现 missing dependency 的问题。

对 AI 重度参与开发的项目还有一个额外收益：手动装配的依赖关系 grep 可见、跳转可追，agent 读代码不需要理解框架的隐含注册逻辑。帖子里也有人提到「反正都是 AI 写」——恰恰因为 AI 在写，显式比隐式更重要，隐式逻辑是 AI 最容易理解错的地方。

## 第 3 章 单元测试怎么办：三层答案

这是帖子里最尖锐的追问，也是最容易被「不用 DI」一票否决的地方。我们的答案是分层的：

**第一层：窄接口 + 手写 fake。** 因为接口定义在消费侧且足够窄（两三个方法），测试里手写一个 fake struct 实现它就行，完全不需要 mock 框架生成。`pkg/api/job/service_test.go`、`pkg/api/project/service_test.go` 里大量 `fakeXxx` 手写实现；中间件层用 `httptest.NewRecorder` 直接打 HTTP 行为。

**第二层：DB 绑定的代码不 mock，直接打真实栈。** 这是关键决策，也是诚实的部分——我们有 54 个文件直接持有 `*gorm.DB`，这些代码本质上不可 mock。与其引入 DI 把它们强行变成可 mock（然后用 mock 的行为仿真自欺欺人），不如承认它不能 mock：`tests/testutil` 提供一次性隔离栈（tmpfs + 端口偏移 + 环境变量护栏防误连主栈），集成测试 fail-closed 地打真实 Postgres 和 Neo4j——栈连不上就 `t.Fatal`，绝不 `t.Skip` 装绿。代价是真的：测试必须连栈，比纯单测慢。

**第三层：契约断言库代替对账。** 对图谱这类没有 ground truth 的语义产物，单测断什么？我们抽了 `tests/graphtest` 断言库，专门校验 IR（中间表示）的良构性——词表合法、边无悬空、node-id 唯一。正确性的定义是「自洽 + 跨引擎对账 + 重构行为保持」，而不是断言一个不可知的绝对真值。

所以「不用 DI 怎么 mock」的完整答案是：**能窄接口 mock 的手写 fake，不能 mock 的承认它不能 mock、直接上真实栈**。

## 第 4 章 帖子里其他争议点的对照

**「依赖注入什么时候和 Java 绑定成了一种邪恶的东西？它明明是一种思想」**——完全同意，而且这正是本文的立场：DI 思想（依赖倒置、面向接口）是必须的，DI 框架（容器、注册表、反射或代码生成）是可选的。把两者混为一谈，才会吵出 81 楼。

**「给一个常用 service 加依赖，手动方案要改所有调用点」**——这是手动方案确定无疑的成本，我不打算粉饰。目前的缓解因素是规模可控，以及 AI 辅助改写把机械成本摊得很薄。但如果某天跨包 service 数量翻倍，这会是我们重新评估 wire 的第一个理由。

**没有 DI 框架不等于没有依赖纪律问题。** 给一个诚实的反面证据：我们依然出了一处依赖方向事故——`pkg/agent/tools/drawtools` 反向 import 了 `pkg/api/diagramset`，因为领域服务住进了传输层包，下层工具层被迫向上伸手。这说明依赖纪律靠的是边界设计，不是注入工具：边界没划对，上什么框架都没用；边界划对了，手动注入并不痛苦。

## 第 5 章 什么时候该改判上框架

不用框架是有前提的，把我们的判据摆出来：

1. **单一部署单元**（一个 server 二进制，装配集中在一个 main）；
2. **包数量在几十量级**，初始化顺序可以人肉拓扑；
3. **接口定义在消费侧**已经是团队纪律，fake 成本足够低。

如果哪条破了——比如拆出多个二进制各自有复杂装配、跨包 service 爆炸式增长、加依赖改调用点的机械成本失控——那就该上框架，而且选 wire：编译期生成、无反射、可跳转可审查，是三者中唯一不引入运行时隐含逻辑的方案，和这个项目「显式优于隐式」的气质一致。

## 结尾

回到帖子的原始问题。Go 项目用依赖注入吗？我们的答案是：用 DI 的思想，不用 DI 的框架。单测怎么办？窄接口 fake 加真实隔离栈，不维护 mock 的行为仿真。

这个答案不普世，它有明确的规模前提。但「要不要 DI 框架」本来就不是一个信仰问题——它是一个「你的依赖图复杂度有没有超过手动管理阈值」的工程问题。先把接口的位置放对，框架就只是随时可以补票的交通工具，而不是上车前必须买的信仰。
