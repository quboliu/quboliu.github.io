写时复制、缓存、懒加载、批处理、预写日志、多版本并发控制、异步复制、垃圾回收和零拷贝，看起来属于不同领域。

它们却反复回答同一个问题：

> 一笔昂贵的成本，是否必须现在、在当前路径上、由当前请求完整支付？

很多高性能系统的第一步，不是把计算做得更快，而是让当前路径少做一些工作：

- 能晚一点做，就不要提前做；
- 能共享，就不要重复复制；
- 能只处理变化部分，就不要全量重算；
- 能批量处理，就不要把固定开销分摊给每一条操作；
- 能异步更新，就不要把所有派生状态绑在主事务上。

这不是“少做工作”的技巧，也不是把复杂性消灭掉。

更准确地说，它们是在重新安排成本的时间、位置和承担者：

> 把成本移出主路径，换来更短的当前延迟、更高的吞吐或更好的并发；再用缓存、日志、版本、回收、背压和修复机制，承担被推迟的复杂性。

这篇文章试图把这些机制放进一个统一框架里。DDIA 提供的是正确性、复制、日志、派生数据和流处理的系统视角；《Systems Performance》提供的是从工作负载、延迟、利用率、饱和度和错误出发的性能视角。

两种视角合在一起，才能回答一个完整的问题：

> 这项设计究竟把哪一笔成本移到了哪里？它是否仍然符合系统的语义承诺？被移走的成本是否可观测、可限制、可恢复？

## 一、先把“主路径”和“成本”说清楚

### 1.1 主路径不是“所有同步代码”

主路径是一个操作在得到承诺结果之前必须经过的关键链路。

对于一个 HTTP 请求，它可能包括网络接收、鉴权、读取权威状态、执行约束检查、提交事务和生成响应。

对于一个数据库事务，它可能包括锁等待、WAL 刷盘、页更新和提交确认。

对于一个流处理任务，它可能包括读取消息、更新状态、保存检查点和向下游发送结果。

因此，把工作移出主路径，并不等于简单地创建一个后台线程。真正要问的是：

- 当前操作必须等到什么结果才能对外承诺成功？
- 哪些工作只是在维护缓存、索引、统计或历史版本？
- 哪些工作可以晚一点完成，却不会改变已经对外作出的语义承诺？

如果把库存扣减从订单事务中移到后台，得到的不是性能优化，而是改变了“订单成功”的含义。

如果把搜索索引更新移到异步消费者，通常只是接受搜索结果稍后可见。

两者都叫“异步”，但一个可能破坏业务不变量，另一个主要改变及时性。

### 1.2 成本不只有 CPU 时间

系统中的成本至少包括七种：

|成本|典型表现|
|---|---|
|延迟|请求等待更久，尤其是尾延迟变长|
|CPU|解析、复制、压缩、重算、垃圾回收占用处理器|
|内存|缓存、版本、队列、预取和中间结果持续占用空间|
|I/O|随机读写、刷盘、压实、扫描和页面换入换出|
|网络|跨节点复制、广播、重试和全量查询|
|协调|锁、共识、事务、版本冲突和跨分片往返|
|运维复杂度|监控、修复、回放、迁移和故障演练|

一个设计可能减少当前请求的 CPU 时间，却增加后台 I/O。

也可能降低平均延迟，却让首次访问和尾延迟变得更差。

还可能减少写路径协调，却把冲突处理和修复责任交给应用。

所以，“变快”必须先说明是哪个指标变快：

- 平均延迟还是 p99 延迟？
- 单请求响应时间还是整体吞吐？
- 前台请求还是端到端新鲜度？
- 正常负载还是系统接近饱和时的表现？

### 1.3 成本转移的四个动作

本文把相关设计归纳成三条主线，并把批量和异步看作常见的实现方式：

|主线|核心动作|典型机制|
|---|---|---|
|延迟|把工作从现在推迟到真正需要或更适合的时候|懒加载、惰性求值、写回、批处理、后台回收|
|共享|让多个读者或版本复用同一份资源|COW、快照、MVCC、结构共享、缓存、零拷贝|
|增量|只处理变化部分，而不是重复处理全部内容|增量计算、WAL、CDC、物化视图、异步索引|

三条主线经常组合出现。

LSM-tree 先延迟合并，再通过追加写和批量压实完成增量整理。

MVCC 共享旧版本供读者使用，再通过后台回收清理不再需要的版本。

事件日志保存增量变化，再由多个消费者异步构建各自的派生状态。

这正是系统设计容易变复杂的地方：一次成本转移，常常会触发下一次成本转移。

## 二、从《Systems Performance》看：移走的成本去了哪里

### 2.1 先描述工作负载，再评价设计

《Systems Performance》反复强调，性能问题不能脱离工作负载讨论。

同一种机制在读多写少、写多读少、顺序访问、随机访问、稳定负载和突发负载下，可能得到完全不同的结论。

至少要先描述：

- 请求速率和突发程度；
- 单次请求的数据量；
- 读写比例；
- 数据访问的局部性；
- 并发度和队列深度；
- 数据是否共享；
- 结果是否允许陈旧；
- 操作是否必须立即持久化。

COW 适合大对象、读多写少且修改局部的场景。

如果每次写入都会改动大部分页面，COW 只会把复制成本推迟到写路径，并可能制造更大的写放大。

缓存适合有重复访问和稳定局部性的负载。

如果访问近似随机，或者数据每次都被修改，缓存命中率很低，维护缓存反而会增加内存和失效成本。

批处理适合吞吐量优先的工作负载。

如果用户等待时间是硬约束，增大批次只能让平均单位成本下降，却可能让单个请求等待更久。

### 2.2 延迟、吞吐、利用率和饱和度必须一起看

把工作移到后台，常见的第一层效果是前台延迟下降。

但后台任务仍然要消耗资源。压实会使用磁盘带宽，垃圾回收会使用 CPU，预取会使用网络，副本追赶会占用 I/O 和缓存。

当资源接近饱和时，后台工作会开始和前台争抢资源，前台的尾延迟就会反弹。

因此，不能只看接口 p50。至少要同时观察：

|观察对象|要回答的问题|
|---|---|
|延迟分布|成本是否被藏进 p99、首次访问或重试路径|
|吞吐量|系统每秒实际完成了多少工作|
|利用率|CPU、内存、磁盘、网络用了多少|
|饱和度|是否出现队列、等待和排队增长|
|错误|是否通过超时、丢弃、重试和降级转移了失败|
|新鲜度|派生状态落后权威状态多久|

USE 方法可以作为资源层的快速入口：看利用率、饱和度和错误。

例如，异步索引更新后接口变快了，但磁盘队列持续增长，说明系统只是把写路径的等待变成了后台积压。

如果积压最终追不上生产速度，所谓“异步”只是在延迟爆炸前暂存工作。

### 2.3 主路径缩短，不代表端到端变快

把一次昂贵的操作拆成前台确认和后台完成，必须重新定义“完成”。

用户看到订单创建成功，可能只代表订单和库存已经提交。

它不一定代表搜索结果、推荐列表、统计报表和所有副本都已经更新。

这种语义可以是合理的，但必须公开：

- 哪个状态是权威状态；
- 哪些状态是派生状态；
- 派生状态允许落后多久；
- 用户如何读到自己的写入；
- 失败时谁负责重试和修复。

DDIA 对一致性、派生数据和流处理的讨论，核心并不是“全部同步”或“全部异步”。

核心是区分完整性与及时性：哪些不变量不能暂时破坏，哪些视图可以稍后收敛。

## 三、延迟：先不做，等真正需要时再做

延迟的收益很直观：启动更快，当前请求更短，工作可以合并。

延迟的代价也很统一：首次使用变慢、错误出现得更晚、后台债务不断积累。

### 3.1 懒加载：把初始化成本推到访问点

操作系统的 demand paging 不会在进程启动时把所有虚拟页面都装入物理内存。

程序第一次访问某个页面时，缺页异常触发映射、读取或分配。

现代前端的动态导入、代码分割和路由级加载，也是在把不一定使用的资源移出启动路径。

数据库的 buffer pool、Git 的 partial clone、容器镜像的 lazy pull，都体现相似的安排：

> 先建立足以继续工作的最小状态，真正访问某部分资源时再把它补齐。

这样做通常能得到：

- 更短的启动时间；
- 更低的初始内存占用；
- 更少的初始网络和磁盘 I/O；
- 只为真实访问路径支付资源成本。

但成本被移到了第一次访问：

- 冷启动抖动；
- 缺页和随机 I/O；
- 运行期才暴露依赖、权限或网络错误；
- 许多小访问导致大量碎片化加载。

治理机制包括预取、预热、read-ahead、热路径加载、fallback 和运行期缺失监控。

《Systems Performance》的视角提醒我们，不能只看进程启动时间。

还要观察缺页率、磁盘等待、缓存命中、首次请求 p99 和工作集是否超过内存。

如果应用启动快了，但用户在接下来的每一次交互中都遭遇一次冷加载，优化只是把一次等待拆成了很多次等待。

### 3.2 惰性求值：把计算推到结果真正被消费时

迭代器、生成器、数据库游标和函数式语言的 call-by-need，都可以避免提前产生不会被使用的结果。

查询引擎的 late materialization 也类似：先在列式数据上过滤和聚合，最后才把必要的完整对象拼出来。

JIT 编译则把编译成本推迟到运行时，并把资源集中到真正的热点路径。

延迟计算的收益是减少无效工作和中间结果。

它的代价是时序更隐蔽：

- 代码构造完成，不代表计算完成；
- 迭代开始，不代表所有结果已经准备好；
- 第一次调用可能承担编译、读取或缓存初始化；
- 访问路径可能产生意外的重复查询。

ORM 的 lazy loading 就是典型例子。

它避免了初始查询加载全部关联对象，却可能在循环中触发 N+1 次数据库访问。

治理方式不是简单地“全部改成 eager loading”，而是根据工作负载选择预取、批量查询、缓存和明确的访问边界。

### 3.3 写回、组提交与批处理：把许多小成本合并

每次写入都立即执行随机 I/O 或 fsync，通常无法获得理想吞吐。

写回缓存先标记脏数据，稍后统一刷出。

数据库使用 WAL 先顺序记录恢复依据，再把数据页延后写入；多个事务还可以通过 group commit 共用一次刷盘。

批处理和微批处理则把固定调度、网络和系统调用成本分摊到一组记录上。

这类设计的收益包括：

- 随机写转化为更顺序的写；
- 固定开销被批次摊薄；
- 系统调用和网络往返减少；
- 前台请求不必等待每个派生动作完成。

但“写成功”需要重新定义。

如果响应返回时数据还只存在内存或缓存中，系统承诺的可能是“已接收”，而不是“已持久化”。

WAL 可以缩小崩溃丢失窗口，却不能替代明确的 durability 语义。

批次也不是越大越好：

- 批次越大，吞吐可能越高；
- 等待凑批的时间可能越长；
- 单次失败重做的工作更多；
- 内存占用和尾延迟可能更高。

需要同时设置批次大小、等待上限、刷新策略、背压和积压告警。

### 3.4 延迟回收：先保持可用，再在安全时清理

垃圾回收、RCU、epoch-based reclamation、tombstone、VACUUM 和 compaction，都把“删除”拆成两个动作：

1. 先让对象在逻辑上不再被使用；
2. 等确认安全后，再物理回收空间。

这能避免读路径承担立即清理的成本，也能给并发读者留下稳定的旧版本。

但空间不会因为逻辑删除而自动消失。

旧对象、墓碑、版本和碎片会持续占用内存或磁盘，并可能在后台形成新的资源高峰。

因此，后台回收需要自己的性能预算：

- 回收速率能否追上产生速率？
- 回收与前台 I/O 是否争抢同一设备？
- 长事务或慢消费者是否阻止安全回收？
- 资源达到水位后是否会触发限流或降级？

把回收当成“系统自动会处理的小事”，通常是后台债务失控的开始。

## 四、共享：不要为每个读者和每个版本复制一份

共享的核心不是延迟，而是避免重复占用。

它通常要求系统明确：谁可以读，谁可以写，何时需要分叉，以及共享资源何时能够回收。

### 4.1 COW：先共享，写入时再分叉

写时复制是这类设计最清晰的例子。

多个读者先共享同一份页面、块或对象。某个写者第一次修改时，系统只复制将要修改的部分，并把新版本接到新的引用上。

Unix fork、文件系统 reflink、快照、容器的 overlay layer 和持久化数据结构，都可以看到类似思想。

COW 适合：

- 复制对象很大；
- 实际修改比例很小；
- 读者远多于写者；
- 需要快照、回滚或稳定旧版本。

它把“立即完整复制”换成了“按写入粒度分裂”。

代价则包括：

- 首次写入出现隐性复制；
- 写入热点产生写放大；
- 共享引用和生命周期变复杂；
- 版本、块和元数据需要回收；
- 碎片可能降低后续读写局部性。

COW 并不是让写入免费。

它只是把复制成本从创建副本的时刻，移到真正发生修改的路径上。

因此，评估 COW 时要看写入分布、页面粒度、共享持续时间和回收压力，而不是只看快照创建耗时。

### 4.2 MVCC：共享稳定的过去，让读写不必争夺同一个瞬间

MVCC 把共享版本的思想用于事务隔离。

写者创建新版本，读者根据自己的快照和可见性规则读取某个旧版本。

这样，长查询不必阻塞所有写入，写入也不必覆盖正在被读取的内容。

但 MVCC 的代价从锁等待转移成了版本管理：

- 旧版本需要保存；
- 读者需要判断可见性；
- 长事务会阻止旧版本回收；
- VACUUM 或类似机制必须持续清理历史。

DDIA 中关于事务隔离的一个重要提醒是：

> 稳定快照不等于所有并发执行都自动可串行化。

快照隔离解决的是读视图和一部分读写竞争问题。

跨行不变量、写偏斜、唯一性和范围条件，仍然需要约束、锁、条件写或更强的隔离机制。

所以，MVCC 不是“无锁数据库”，而是把一部分协调成本改写为版本可见性和空间管理成本。

### 4.3 缓存和记忆化：共享已经付过的计算成本

缓存不是简单地“保存一份数据”，而是让后续请求复用先前已经支付过的读取或计算成本。

页面缓存复用磁盘读取，查询缓存复用执行结果，memoization 复用函数计算，物化视图复用聚合和连接。

它们的共同条件是存在某种重复性：

- 输入或访问模式有局部性；
- 结果可以在一段时间内复用；
- 失效和一致性成本低于重复计算成本。

缓存带来的问题也十分一致：

- 命中率不足时，维护成本无法摊薄；
- 失效策略错误时，结果陈旧；
- 大量请求同时失效时，出现 cache stampede；
- 缓存占满后，驱逐和重建造成抖动；
- 缓存被误当成权威状态后，修复变得困难。

一个重要边界是：

> 缓存越像权威数据，系统越难解释；派生数据越容易重建，系统越容易演进。

这也是 DDIA 讨论派生数据时反复强调的思路：保留可靠的事实来源，让索引、缓存和查询视图成为可以重建的表示。

### 4.4 零拷贝与共享缓冲区：不要反复搬运同一批字节

零拷贝、scatter-gather I/O、buffer pool、借用和所有权模型，都是在减少数据跨边界复制。

复制不仅消耗 CPU，也消耗内存带宽、缓存容量和总线资源。

但“零拷贝”通常不是字面意义上的完全不复制。

它更常表示：在一条具体的数据路径上，减少不必要的内核态和用户态复制、拼接或解码。

共享缓冲区后，系统必须回答：

- 这个缓冲区由谁拥有？
- 谁可以修改？
- 读者退出前，生产者能否复用？
- 发生异常时，引用计数和生命周期如何结束？

Rust 的借用规则、网络框架的 buffer pool 和高性能数据库的页面管理，都说明了同一件事：

> 避免复制不是免费优化，它会把内存生命周期和所有权问题暴露到接口设计中。

《Systems Performance》的视角会进一步追问：复制节省的 CPU 和带宽，是否真的成为瓶颈？如果系统主要受磁盘或网络延迟限制，零拷贝带来的复杂度可能超过收益。

## 五、增量：只为变化部分付费

延迟解决“什么时候做”，共享解决“是否重复占用”，增量解决“变化了多少”。

增量设计最容易被误解为“只改一行代码”。它真正要求系统保存足够的中间状态、依赖关系和进度，才能知道哪些结果需要更新。

### 5.1 增量计算：从 f(D) 走到 f(D + ΔD)

如果输入数据集从 D 变成 D + ΔD，朴素方案会重新计算 f(D + ΔD)。

增量方案试图利用旧结果和辅助状态，只计算 ΔD 对结果产生的影响。

典型应用包括：

- 构建系统只重新编译受影响的目标；
- IDE 只更新受修改文件影响的语义信息；
- 物化视图只更新变化的聚合；
- 流处理器只处理新到达的事件；
- 电子表格只重新计算受影响的单元格。

增量计算的收益取决于变化的局部性。

如果一次小输入变化会影响大部分连接结果，增量维护仍然可能接近全量重算。

删除操作也常常比追加操作难，因为系统不仅要知道新贡献，还要知道旧贡献曾经是什么。

因此，增量系统需要保存：

- 输入或事件的稳定身份；
- 中间聚合和依赖关系；
- 处理进度；
- 必要时用于撤销的旧值；
- 能够重建状态的日志、快照或检查点。

增量计算省下了重算成本，却增加了状态、恢复和版本管理成本。

### 5.2 日志：先记录变化，再派生当前状态

日志把“修改一个复杂状态”拆成两个动作：

1. 先以追加方式记录足以恢复或传播的变化；
2. 再由存储引擎或消费者把变化应用到具体表示。

但不同的日志不能混为一谈：

|日志类型|主要目的|
|---|---|
|WAL|保障存储恢复，记录重做或撤销所需信息|
|CDC|传播数据库中的变更，供下游构建派生状态|
|业务事件日志|记录业务语义，供多个消费者解释和重放|
|应用日志|记录诊断信息，不一定能重建状态|

追加写通常比随机覆盖更适合磁盘和网络，但它会产生新的整理工作：

- 日志越来越长；
- 恢复重放越来越慢；
- 多个版本和派生状态需要压缩；
- 压实会造成读放大、写放大和资源争抢。

日志压缩可以把同一个键的历史压缩成较新的状态，但这可能丢失完整历史。

因此，压缩前必须明确：系统承诺的是恢复当前状态，还是保留可审计的全部业务事实。

### 5.3 异步派生数据：把更新协调移出写路径

搜索索引、推荐列表、统计表、缓存和分析视图，通常不是业务事实本身，而是从事实来源派生出的读取表示。

如果每次业务写入都同步更新所有派生系统，写路径就会被网络、分片、索引和外部服务绑定。

异步派生把它改成：

1. 先提交权威事实；
2. 记录需要传播的变化；
3. 由消费者稍后更新各自的表示；
4. 通过重试、去重、排序和修复最终收敛。

这正是 CQRS、异步二级索引、CDC 管道和许多事件驱动系统的共同结构。

它换来了：

- 更短的核心写入路径；
- 派生系统之间的故障隔离；
- 各种读取表示可以分别扩展；
- 派生状态损坏后可以重建。

它同时引入：

- 读到旧视图；
- 消息重复、乱序或丢失；
- 失败重试和幂等要求；
- 用户读己之写的体验问题；
- 派生状态与事实来源不一致的修复工作。

所以，异步不是“最终会自己好”的魔法。

一个可运维的异步系统至少要定义：

- 事件的稳定 ID；
- 同一对象的顺序或版本规则；
- 消费者的检查点；
- 重试和死信策略；
- 允许的最大滞后；
- 从事实来源重建派生状态的方法。

### 5.4 分片和局部性：只在需要的地方计算与协调

分片也可以看作增量化和局部化的一种结构安排。

如果一个请求能根据分区键定位到一个分片，它就不必扫描和协调整个系统。

如果相关事件被路由到同一个分区，消费者可以在局部范围内维护顺序和不变量。

但分片并没有消除约束，只是把约束分布到数据布局中。

跨分片查询、全局唯一性、全局排序和跨分片事务，仍然需要广播、协调或重新设计业务边界。

热点键还会让一个局部队列成为新的瓶颈。

《Systems Performance》会要求继续检查访问分布、队列长度和尾延迟，而不是只看分片数量。

“加机器”只有在能够缓解实际饱和资源时才是扩展；它不能自动消除串行裁决和热点。

## 六、同一笔成本如何在系统中转移

把前面的机制放在一张表里，可以看到它们并不是互相孤立的模式：

|原来的主路径成本|转移方式|新的成本|需要的治理|
|---|---|---|---|
|启动时加载全部资源|懒加载、按需拉取|首次访问抖动、运行期缺失|预取、预热、fallback、缺页监控|
|完整复制大对象|COW、快照、结构共享|首次写放大、版本膨胀|引用管理、回收、碎片整理|
|每次查询都重算|缓存、物化视图、增量计算|失效、陈旧、依赖维护|版本、失效、重建、命中率监控|
|每次写入都立即落盘|写回、WAL、组提交|持久化窗口、后台积压|durability 级别、刷盘调度、背压|
|删除时立即物理清理|GC、RCU、tombstone|空间滞留、回收抖动|水位、epoch、VACUUM、compaction|
|写入时同步更新全部读模型|异步派生、CDC、CQRS|旧读、重复、乱序|幂等、版本、重试、修复|
|跨边界反复复制和解码|零拷贝、共享缓冲区|所有权和生命周期复杂|借用、引用、buffer 池、边界检查|

这张表揭示了一个关键规律：

> 每次把成本移出主路径，都会在另一个位置产生一笔更难直接观察的成本。

因此，设计评审不能只问“主路径缩短了多少”。

还要问：

- 成本现在由哪个线程、哪个节点或哪个用户承担？
- 它是变成了后台队列、版本空间，还是一致性滞后？
- 这笔债务是否有上限？
- 资源接近饱和时，系统如何退化？
- 中途崩溃时，哪些工作可以重做，哪些工作已经不可逆？

## 七、DDIA 与《Systems Performance》如何合成一套方法

### 7.1 DDIA 先问：什么必须正确

DDIA 的价值不在于给出一张“应该使用哪些组件”的清单。

它更像是一套分析不同系统设计的语言：

- 权威状态是什么？
- 派生状态是什么？
- 哪些写入必须排序？
- 哪些副本可以暂时落后？
- 哪些操作需要原子提交？
- 哪些失败只能通过重试、补偿或重建处理？

如果没有这些语义边界，“异步”“缓存”“复制”和“最终一致”都只是模糊的性能口号。

例如，搜索索引可以晚一点更新，但库存不能因为索引滞后而重复扣减。

统计报表可以接受旧数据，但支付成功的持久化边界不能依赖一个稍后才运行的消费者。

### 7.2 《Systems Performance》再问：瓶颈到底在哪里

性能分析不能从“我想把这一步异步化”开始，而应该从测量开始：

1. 描述工作负载；
2. 观察延迟和吞吐；
3. 找出利用率和饱和度最高的资源；
4. 区分服务时间与排队时间；
5. 建立假设；
6. 用追踪、剖析和计数器验证；
7. 改变一个变量后重新测量。

当一个系统变慢时，不能仅凭 CPU 利用率低就判断“CPU 不是问题”。

线程可能正在等待磁盘、锁、网络、内存访问或后台队列。

同样，接口变快也不能证明系统成本下降。

工作可能只是离开了请求线程，进入压实、GC、重试、消息堆积或副本追赶。

### 7.3 联合方法：先定语义，再移成本，最后验证

可以把两本书的抽象合成七步：

1. **声明不变量。** 哪些条件绝不能被破坏？
2. **声明完成语义。** 返回成功时，究竟保证了什么？
3. **描述工作负载。** 访问比例、大小、局部性、并发和突发是什么？
4. **画出主路径。** 哪些工作是当前结果必须等待的？
5. **选择转移方式。** 延迟、共享、增量、批量或异步，哪一种最匹配？
6. **建立成本账本。** 新成本在哪里积累，如何限流、回收、重试和修复？
7. **用指标验证。** 延迟分位数、吞吐、资源饱和度、队列、错误和新鲜度是否真的改善？

这套流程能避免一种常见误判：

> 把“请求线程变空闲”误认为“系统完成了更少的工作”。

## 八、一个综合例子：订单进入搜索和统计系统

假设一个订单系统希望同时满足：

- 同一个下单请求不能重复扣库存；
- 订单写入成功后不能轻易丢失；
- 搜索和统计可以稍晚更新；
- 消费者失败后可以继续恢复；
- 查询高峰不能拖垮写入主路径。

### 8.1 必须留在主路径的部分

客户端为一次下单流程生成稳定的操作 ID，并在重试时复用。

服务端在事务内完成：

- 检查操作 ID 是否已经处理；
- 校验库存条件；
- 创建订单；
- 修改库存；
- 写入待发布的 Outbox 事件；
- 保存可以返回给客户端的结果。

这些动作之所以不能随意移到后台，是因为它们共同构成业务不变量。

如果库存更新和订单创建分开异步执行，系统就可能先展示成功订单，再发现库存不足。

事务提交达到约定的持久性条件后，服务端再返回成功。

这并不意味着所有读取视图已经更新，只意味着权威状态已经满足本次操作的承诺。

### 8.2 可以移出主路径的部分

Outbox 事件由发布器或 CDC 管道送入日志。

搜索消费者更新搜索索引，统计消费者更新聚合表，推荐消费者更新推荐特征。

每个消费者都保存自己的进度，并根据事件 ID 去重。

同一个订单的事件需要按照约定的版本或分区顺序处理。

消费者失败时可以重试；派生索引损坏时，可以从权威事件或数据库变更重新构建。

这里接受的是搜索和统计的暂时陈旧，而不是订单事实的不确定。

### 8.3 共享与增量如何参与

订单列表可以使用数据库提供的稳定快照，避免长查询读到混合状态。

热门商品和只读详情可以进入缓存，但库存可用量仍以权威事务状态为准。

统计消费者不必每次扫描全部订单，而是用事件增量更新计数、金额和分组聚合。

历史事件和派生状态需要检查点与保留策略，否则恢复时间和存储空间会无限增长。

### 8.4 应该观察什么

除了 API 的 p50 和 p99，还要观察：

- 数据库锁等待和 WAL flush 延迟；
- Outbox 发布延迟；
- 各消费者的队列年龄；
- 搜索索引和统计视图的新鲜度；
- 重试次数、重复事件和死信数量；
- 磁盘利用率、队列深度和 compaction 时间；
- 缓存命中率和回源峰值；
- 从日志重建派生状态所需的时间。

如果 API 很快，但队列年龄持续增长，系统并没有真正变快。

如果搜索延迟从 2 秒变成 20 分钟，也不能继续把它称为“异步优化”而不说明语义变化。

## 九、什么时候值得把成本移出主路径

### 9.1 值得考虑的信号

|信号|适合考虑的方向|
|---|---|
|启动时加载了大量很少访问的资源|懒加载、预取、分层初始化|
|读多写少且对象复制昂贵|COW、快照、结构共享、MVCC|
|结果会被重复查询或重复计算|缓存、memoization、物化视图|
|许多小操作共享固定开销|批处理、组提交、向量化|
|输入变化局部且依赖关系可追踪|增量计算、增量构建、流处理|
|派生视图不必与事实同时可见|CDC、异步索引、CQRS|
|数据复制和解码已经成为可测量瓶颈|共享缓冲区、零拷贝、延迟解码|

这些信号还不够。

还必须确认团队能够承担对应的后台治理、观测和修复工作。

### 9.2 不适合贸然使用的信号

- 操作涉及不能暂时破坏的业务不变量；
- 用户已经获得强持久化或强实时承诺；
- 负载没有明显重复、局部性或批量机会；
- 关键路径本来就很短，治理复杂度更高；
- 没有后台资源预算和积压上限；
- 没有稳定 ID、版本、检查点和重建来源；
- 团队无法解释陈旧数据、重复处理和修复过程。

尤其要警惕“默认全部异步”。

异步化最先改善的是等待，不一定改善的是正确性、资源使用和端到端完成时间。

## 十、评审一项“成本转移”设计时，问这十个问题

1. 当前主路径究竟在等待什么？
2. 这笔成本是被延迟、共享，还是被增量化？
3. 哪个状态是权威状态，哪个状态只是派生表示？
4. 对外的“成功”需要满足什么持久性和一致性条件？
5. 被移走的工作会在哪个资源上执行？
6. 它会形成多长的队列、多少版本或多大的缓存？
7. 资源饱和时，系统如何背压、降级或拒绝新工作？
8. 重试、乱序、崩溃和重复执行时，结果如何保持正确？
9. 派生状态如何检测差异、重建和回收？
10. 通过哪些指标证明系统真的改善，而不是把等待藏起来？

如果这些问题回答不出来，系统通常只是把一笔可见的同步成本，换成了几笔不可见的后台债务。

## 十一、结论：高性能不是少做工作，而是安排工作

延迟、共享和增量设计的共同目标，不是让系统永远不做昂贵的工作。

它们是在寻找更合适的支付方式：

- 在用户真正需要之前，不要过早初始化；
- 在多个读者之间，不要重复复制；
- 在输入只改变一部分时，不要全量重算；
- 在固定开销可以摊薄时，不要逐条支付；
- 在派生状态不必立即可见时，不要把它们绑进核心事务。

但每一次成本转移都必须留下清晰的账本：

> 成本从哪里移出，移到了哪里；谁承担它，何时必须完成；如何观测、限流、恢复和回收。

DDIA 帮助我们判断哪些状态和不变量必须正确，哪些状态可以作为派生数据稍后收敛。

《Systems Performance》帮助我们判断成本是否真的离开了瓶颈，还是只是转移到了队列、尾延迟、磁盘饱和和后台任务。

把两种视角放在一起，才是这类设计真正可迁移的抽象：

> 先定义系统必须保证什么，再把不必现在完成的工作移出主路径；最后用可观测的指标证明，这笔成本被放到了系统能够承担的位置。

这不是偷懒。

这是对时间、资源、状态和复杂性进行更精确的安排。
