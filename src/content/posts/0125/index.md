“原子”是计算机领域最容易产生误解的词之一。CPU 提供原子指令，C/C++、Rust、Java 和 Go 提供原子类型，数据库提供原子更新，而事务又把原子性列为 ACID 的第一个字母。

这些概念显然有亲缘关系，却不承诺同一件事。理解“原子”的最好办法，是每次都追问两个问题：**什么东西不可再分？它是在抵抗并发交错，还是在抵抗中途失败？**

前一个问题指向并发原子性：其他执行者不能观察到操作的中间状态。后一个问题指向失败原子性：操作如果未能完成，已经产生的局部效果不能残留。

并发编程中的原子操作主要属于前者；ACID 中的原子性主要属于后者。二者共享“不可分割”这个隐喻，却沿着两条不同的轴约束系统行为。

## 一、“原子”至少有两种含义

并发原子性关心的是观察和交错。假如一个线程执行原子操作，其他线程只能观察到操作之前或之后的状态，不能插进操作内部，也不能看到一半完成的结果。

失败原子性关心的是提交和撤销。假如一个事务包含五次写入，而执行到第三次时发生断电，那么恢复后的数据库不能留下前三次写入；只有整个事务最终成功提交，这些写入才允许存在。

《Designing Data-Intensive Applications》第二版第八章（第一版为第七章）对此作了很干净的区分：ACID 原子性不描述并发访问，那属于隔离性；ACID 原子性的定义性能力是中止事务并撤销其全部写入。作者甚至指出，“可中止性”可能是更贴切的名字。

因此，可以先记住两个问题：

> ACID 原子性问：事务失败以后，哪些效果留下？
>
> 隔离性问：事务并发执行时，允许彼此观察到什么？

下面这张表把各层次放到同一坐标系中。

| 层次 | 不可分割的单位 | 主要对手 | 核心保证 | 不保证什么 |
| --- | --- | --- | --- | --- |
| CPU 原子读写 | 一次满足架构条件的内存访问 | 其他核心 | 不产生撕裂值，并服从单地址修改顺序 | 多步读—改—写、其他内存操作的顺序、持久化 |
| CPU CAS、Fetch-Add | 对一个位置的一次 RMW | 其他核心的竞争修改 | 比较、计算或写回有单一生效点 | 多变量不变量、失败恢复 |
| 语言原子类型 | 一次语言层原子操作 | 线程、编译器和 CPU 重排 | 语言内存模型规定的原子性与顺序 | 周围多条语句组成的业务操作 |
| Mutex、监视器或所有权协议 | 一个临界区 | 其他线程 | 多步内存操作的互斥与可见性 | 进程崩溃后的撤销、持久性 |
| 数据库原子更新 | 一次受支持的对象更新或条件写 | 并发客户端 | 单对象更新不被交错或覆盖 | 任意多对象业务不变量 |
| ACID 原子性 | 一个事务的全部效果 | 崩溃、错误和中止 | 全部提交或全部撤销 | 并发事务的合法交错 |
| ACID 隔离性 | 一个事务的执行历史 | 其他事务 | 约束读写可见性及并发历史 | 崩溃恢复和持久性 |

## 二、CPU 的原子：从不撕裂到 RMW

CPU 层最小意义的原子性，是某些满足宽度、对齐、内存类型与缓存属性等架构条件的读写不会被撕裂。一个值从 A 变成 B 时，其他核心不会读到一半来自 A、一半来自 B 的拼接结果。

这并不意味着使用该值的表达式也是原子的。`x++` 通常包含三个逻辑步骤：

```text
读取 x
计算 x + 1
写回 x
```

两个核心可能都读到 `x = 10`，分别算出 11，然后都写回 11。每一次加载和存储都可能不撕裂，整个读—修改—写过程仍然丢失了一次增量。

原子 RMW（Read-Modify-Write，读—修改—写）指令把这些步骤合成一个不可分割操作。常见形式包括交换、Fetch-Add 和 CAS（Compare-and-Swap，比较并交换）。

```text
CAS(address, expected, desired):
    if *address == expected:
        *address = desired
        return true
    return false
```

一次成功的 CAS 看起来像在某个瞬间生效。这个瞬间通常称为**线性化点**。线性化要求并发对象的每个操作，都能被解释为在调用与返回之间的某一点瞬时完成。[Herlihy 与 Wing 的论文](https://www.cs.cmu.edu/~wing/publications/HerlihyWing90.pdf)给出了这一经典定义。

以 x86 为例，带 `LOCK` 语义的指令通常通过缓存一致性协议取得相应缓存行的独占权，使竞争访问形成先后顺序；某些特殊地址或访问形式可能使用总线锁。[Intel 架构手册](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html)对此有详细说明。

ARM 可以使用原子 CAS 指令，也可以使用 Load-Exclusive/Store-Exclusive 指令对组成重试循环。二者实现手段不同，但都要让冲突写入只能有一个成功者。

[Arm 对原子指令映射的说明](https://developer.arm.com/community/arm-community-blogs/b/tools-software-ides-blog/posts/making-the-most-of-the-arm-architecture-in-gcc-10)展示了这两类路径。

然而，**对一个地址的访问不可分割，不等于周围所有内存访问都按源码顺序对其他核心可见**。现代 CPU 和编译器都会重排操作，因此原子性之外还需要内存顺序、屏障以及 acquire/release 等同步语义。

## 三、语言原子：同一种硬件，不同的语言契约

应用程序不应该直接依赖“这台 CPU 恰好不会把这个值写裂”。程序员真正能够依赖的是语言内存模型：它规定什么是数据竞争、哪些执行结果合法，以及同步操作如何建立可见性顺序。

C、C++、Rust、Java 和 Go 最终可能生成相似的 CAS 或 Fetch-Add 指令，但它们暴露给程序员的契约并不相同。

| 语言 | 主要接口 | 内存顺序 | 非同步数据竞争 | 设计特点 |
| --- | --- | --- | --- | --- |
| C | `_Atomic(T)`、`<stdatomic.h>` | 可选 Relaxed、Acquire、Release、AcqRel、SeqCst 等 | 未定义行为 | 接口低层，原子性与顺序可分别选择 |
| C++ | `std::atomic<T>`、`atomic_ref` | 与 C 类似，默认 SeqCst | 未定义行为 | 泛型更强；原子对象不保证一定无锁 |
| Rust | `Atomic*`、`Ordering` | Relaxed、Acquire、Release、AcqRel、SeqCst | 数据竞争是未定义行为 | 模型以 C++20 为基准；安全类型系统排除大量非同步共享可变访问 |
| Java | `volatile`、`Atomic*`、`VarHandle`、`synchronized` | 从普通、opaque、acquire/release 到 volatile 语义 | JMM 约束可能结果，不按 C/C++ 方式整体判为 UB | `volatile` 解决可见性与顺序，但复合 RMW 仍需 Atomic 类或锁 |
| Go | `sync/atomic`、Mutex、Channel | 标准原子 API 统一提供顺序一致语义 | 数据竞争是程序错误，但语义不像 C/C++ 那样完全放任 | 接口刻意简单，官方优先建议使用锁或通信 |

### C 与 C++：把“是否原子”和“怎样排序”拆开

C11 的 `_Atomic` 与 C++11 的 `std::atomic` 把原子对象纳入语言内存模型。默认操作使用顺序一致的 `seq_cst`；开发者也可以显式选择更弱的顺序，换取实现和硬件上的优化空间。

`memory_order_relaxed` 仍保证当前原子访问不可分割，并保留该原子对象自己的修改顺序，只是不借此排列其他内存访问。Release 写与观察到它的 Acquire 读可以建立同步边，把发布前的数据安全地交给另一个线程。

WG14 的[内存模型说明](https://open-std.org/jtc1/sc22/wg14/www/docs/n1479.htm)明确区分了原子访问与 `volatile`：C 的 `volatile` 主要约束优化和特殊内存访问，并不自动提供线程间原子性和同步。

C++ 的 `std::atomic<T>` 也不保证所有类型、所有平台上都由无锁指令实现。实现可以使用锁，只要满足标准规定的可观察语义。程序可以通过 `is_lock_free` 查询某个原子对象是否无锁。[C++ 工作草案的原子章节](https://eel.is/c++draft/thread#atomics)规定了这些操作与内存顺序。

这套自由度很强，也很容易用错。Release/Acquire 配对、失败 CAS 的顺序参数、对象生命周期和内存回收，都可能让“代码中用了 atomic”与“并发算法正确”相距甚远。

### Rust：没有数据竞争，不等于没有竞态条件

Rust 的原子类型位于 `std::sync::atomic`，其内存模型以 C++20 为基准，但没有 `Consume`。`Relaxed` 保留当前地址上的原子性和修改顺序；Acquire、Release、AcqRel 和 SeqCst 逐步加入跨操作的顺序约束。[Rust 原子模块](https://doc.rust-lang.org/std/sync/atomic/index.html)对此有明确说明。

Rust 的特殊之处不在于 CPU 指令不同，而在于类型系统。`Send`、`Sync`、借用规则和内部可变性限制，使安全 Rust 很难形成“多个线程任意写同一个普通变量”的数据竞争。

但是类型系统无法自动证明业务层竞态不存在。两个线程可以安全地读取两个受锁保护的账户，再依据过时结果分别作出合法更新；程序没有数据竞争，业务不变量仍可能被破坏。

换句话说，Rust 擅长阻止未定义的内存访问，却不会自动把一组业务操作变成可串行化事务。原子顺序选择错误也仍可能造成逻辑缺陷。

### Java：`volatile` 不是 `AtomicInteger`

Java 内存模型通过 happens-before、同步顺序、监视器锁和 `volatile` 规则定义线程可见性。对一个 `volatile` 字段的写，与随后观察该写的读取之间建立同步关系。[Java 语言规范第 17 章](https://docs.oracle.com/javase/specs/jls/se25/html/jls-17.html)给出了正式规则。

但 `volatile int x` 只让对 `x` 的独立读取和写入具有相应可见性与顺序保证，`x++` 仍然是读取、计算、写回的复合操作。它可能丢失更新。

`AtomicInteger.incrementAndGet()`、`getAndAdd()` 与 `compareAndSet()` 才提供原子 RMW。`VarHandle` 又进一步暴露 plain、opaque、acquire、release、volatile 等不同访问模式，允许库作者精细控制顺序成本。

Java 的非同步数据竞争不会像 C/C++ 那样让整个程序落入完全的未定义行为，但读者可能看到陈旧值或出乎直觉的合法重排。因此，“不会内存损坏”与“并发逻辑正确”仍是两回事。[Java 原子类文档](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/atomic/package-summary.html)将这些类定位为单变量上的线程安全操作工具。

### Go：用较强的默认语义换取较小的选择空间

Go 的 `sync/atomic` 提供 Load、Store、Swap、Add、And、Or 和 CompareAndSwap，以及 `atomic.Int64`、`atomic.Pointer[T]` 等类型化包装。

Go 没有让调用者为标准原子操作逐次选择 Relaxed 或 Acquire/Release。所有原子操作表现得仿佛处在某个顺序一致的总顺序中；一个原子操作的效果被另一个观察到时，二者还建立 synchronized-before 关系。[Go 内存模型](https://go.dev/ref/mem)规定了这一点。

这种设计减少了顺序选择错误，却没有扩大原子边界。两个 `atomic.Int64.Add` 仍然只是两个原子操作，不会自动合并成一次转账。

Go 还明确建议：除非在实现低层同步算法，优先使用 Channel 或 `sync` 包中的设施。[`sync/atomic` 文档](https://pkg.go.dev/sync/atomic)把它称为需要谨慎使用的低层原语。

“不像 C/C++ 那样把数据竞争整体视为未定义行为”不意味着竞态是安全的。Go 内存模型明确警告：在多数实现中，接口、map、slice、string 等多字值的内部指针—长度或指针—类型对可能被撕裂，进而造成任意内存破坏。正确程序仍应消除所有数据竞争。

## 四、并发编程中的“隔离”去了哪里

并发编程并没有忽略隔离。更准确地说，它把隔离拆进了原子操作、互斥、线性化、happens-before、内存顺序和所有权等概念中。

对于单次 CAS，“读取—比较—写入”已经被定义成一个操作。其他线程不能插入其内部，所以它的原子性本身就包含了一小块隔离：竞争者只能排在这个操作之前或之后。

但这块隔离严格受原子边界限制。假设两个账户分别由两个原子整数表示：

```text
from.Add(-100)
to.Add(100)
```

两条语句各自都是原子的，合在一起却不是。读线程可能在二者之间统计总额，看到 100 元暂时消失。这与数据库中的读偏差具有相同结构。

若不变量跨越多个值，程序必须扩大受保护区域。可以让所有读写者共同遵守同一个 Mutex，也可以把完整状态做成不可变对象，再通过一个原子指针一次发布新版本。

```text
lock
from = from - 100
to   = to + 100
unlock
```

这里真正提供隔离的不是某条赋值，而是一套访问协议：所有参与者都必须通过同一把锁、同一条消息通道或同一个原子状态入口访问数据。只要有一个读者绕开协议，隔离就会破裂。

不同层次共同完成这项保证：CPU 让锁状态或 CAS 不可分割；语言内存模型限制编译器和 CPU 重排；Mutex 或 Channel 建立 happens-before；程序设计者决定临界区究竟覆盖哪些不变量。

CAS 循环采用另一种方式。多个线程可以同时读取旧状态并计算新状态，但只有仍以当前版本为基础的 CAS 能成功；失败者重新读取并重试。这是一种乐观并发控制。

需要注意，只有最后成功的 CAS 是原子的。CAS 前的计算没有被隔离，而且可能执行多次。因此重试循环里不能随意发送邮件、扣外部账户或执行其他不可重复副作用。

## 五、数据库原子写：放大版的 Add 与 CAS

数据库中的原子更新，与语言中的原子 RMW 操作具有相同的算法形状。危险的做法是把读—修改—写拆到应用程序：

```text
SELECT value
在应用中计算 value + 1
UPDATE value
```

两个客户端可能读取同一个旧值，然后互相覆盖。更安全的写法是把计算交给数据库：

```sql
UPDATE counters
SET value = value + 1
WHERE key = 'foo';
```

数据库会让针对同一行的竞争更新形成某种先后关系，所以两个增量不会坍缩成一个。它在概念上对应 `fetch_add`。

条件更新则对应 CAS：

```sql
UPDATE wiki_pages
SET content = $new_content,
    version = version + 1
WHERE id = $id
  AND version = $expected_version;
```

在数据库明确为这种写法提供 CAS 语义的前提下，若受影响行数为 1，比较并更新成功；若为 0，说明版本已经变化，调用者必须重新读取、合并或放弃。事务最终还必须成功提交。

### 条件写入一定要加锁吗？

不一定要由应用显式加锁，但一定要有一种机制，为竞争更新裁定唯一顺序。条件写入的契约是“比较与决定是否写入不可分割”；锁只是实现这个契约的一种办法。

这里的“条件写入”首先是对调用者承诺的操作语义，不一定对应数据库内部一个同名的特殊接口。键值库可能显式提供 `compareAndSet`；SQL 数据库通常用一条带预期值条件的 `UPDATE` 表达同一意图，再由普通 DML 路径的并发控制机制兑现它。

如果数据库在确认 `content = 'old content'` 后释放保护，过一会儿才写回，其他事务就能插入两步之间。这时条件已经失去意义，形成典型的“检查时与使用时”（TOCTOU）竞态：

```text
T1: 读到 content = old content
T2: 写入 content = B 并提交
T1: 根据旧判断写入 content = A  ← 覆盖 T2
```

因此，这个契约意味着：数据库必须把“读取当前值—比较—若匹配则写入”暴露为一个不可分割的操作。多个请求可以并发开始，但在某个线性化点，基于同一旧版本的写入最多只能有一个成功。

数据库可以先获取行级写锁，再检查条件；也可以允许并行执行，在提交时验证版本并中止冲突者。把整次条件操作交给单线程状态机顺序执行，或通过共识日志确定执行顺序，也能提供同样的裁决。

这套裁决以存在唯一最新值，或能为目标对象建立唯一顺序为前提。多主或无主系统若沿普通路径接受并异步传播并发写，就不存在可供全局比较的唯一当前值，本地条件写也不是全局 CAS。系统必须另走共识协调路径，例如 Cassandra/ScyllaDB 基于 Paxos 的轻量级事务（LWT）；否则只能把写入视为并发冲突进行合并或裁决，不能声称提供全局 CAS。

[Apache Cassandra 文档](https://cassandra.apache.org/doc/stable/cassandra/architecture/guarantees.html)与[ScyllaDB 文档](https://docs.scylladb.com/manual/stable/features/lwt.html)都说明 LWT 使用 Paxos 来提供线性一致的条件写。

因此，若 T2 先成功，T1 必须重新检查最新版本并影响 0 行，或因冲突而失败、中止或重试。它绝不能拿着旧快照中“条件为真”的结果盲目覆盖新版本。

但 SQL 的字面形式不会自动创造这种保证。DDIA 为示例标注“是否安全取决于数据库实现”，正是因为 MVCC 系统对 `UPDATE` 条件和新版本可见性的规则不尽相同。应用必须核对具体数据库的契约。

PostgreSQL 在 `READ COMMITTED` 下遇到目标行被并发更新时，会等待竞争事务结束，再对更新后的行重新检查 `WHERE`。在 `REPEATABLE READ` 下，若竞争者已经提交对该行的更新，当前事务则报告序列化冲突并需要重试。两种路径都不会让过时的匹配结果盲目覆盖新值。[PostgreSQL 隔离级别文档](https://www.postgresql.org/docs/18/transaction-iso.html)描述了这两种行为。

应用若调用有明确原子语义的单次条件写入，必须检查受影响行数或失败结果，并确认事务最终提交，但不必先执行 `SELECT FOR UPDATE`。若把读取、业务计算和无条件写回拆成多步，则必须使用显式锁、版本条件，或目标数据库明确保证能防止丢失更新的事务隔离来封住竞态窗口。

版本号比直接比较内容更稳妥。若值经历 A→B→A，单看内容会误以为从未变化，这正对应并发算法中的 ABA 问题；单调递增版本可以把两次 A 区分开。

这也说明了本文所说的“一小块隔离”：条件写入的排他性已被折叠进单次操作的原子边界。它能保护一个对象的一次竞争更新，却不自动使跨多个对象的业务操作获得 ACID 隔离性。

这里可以看到几组有用但不完全等价的对应：

```text
Mutex 临界区        ≈ 数据库悲观锁
CAS 重试循环        ≈ 乐观并发控制
expected 旧值       ≈ 数据库对象版本号
CAS 失败并重试      ≈ 事务冲突后中止并重试
```

数据库还面对普通内存原子操作没有的问题：网络超时后，客户端可能不知道写入是否成功；操作可能跨副本或分片；结果还要在断电和进程重启后存在。因此它还需要日志、幂等键、复制与原子提交协议。

## 六、ACID 的 A 与 I 为什么必须分开

考虑一次转账：

```text
账户 A 减少 100
账户 B 增加 100
```

如果执行第一步后数据库崩溃，恢复后不能只留下扣款。ACID 原子性要求两项修改全部留下，或者全部撤销。WAL、undo/redo、事务状态和跨节点原子提交协议服务于这类保证。

然而，即便转账一定全有或全无，并发读者能够看到什么仍是另一个问题。它会不会在转账期间看到一个账户已经扣款、另一个尚未入账？一次查询中的两次读取是否来自同一个时间点？这些都是隔离问题。

满足失败原子性、却没有可串行化隔离的情况完全可能发生。假设两名医生中至少一人必须值班：

```text
事务 T1：看到医生 B 值班，于是让医生 A 休假
事务 T2：看到医生 A 值班，于是让医生 B 休假
```

两个事务都可以完整提交，谁也没有只执行一半，因此各自都满足失败原子性。但它们共同让两名医生都休假，破坏了业务不变量。这就是写偏差：问题来自并发历史，而不是中途失败。

隔离而不具备失败原子性也同样可能。程序可以用 Mutex 阻止其他线程观察两次文件写入之间的状态；若进程在第一次写盘后崩溃，Mutex 不会在重启后替它撤销已经落盘的内容。

因此两个性质分别约束不同维度：

- 原子性限制一次事务最终可以留下哪些效果集合。
- 隔离性限制多个事务可以形成哪些读写历史。

“ACID 数据库”也不意味着每个事务默认获得最强隔离。数据库通常提供读已提交、可重复读、快照隔离或可串行化等等级，让应用在并发能力、冲突率和推理难度之间选择。

## 七、线性化、可串行化与严格可串行化

并发原子操作常用线性化描述：每个操作仿佛在调用和返回之间的某个瞬间生效，而且现实中已经完成的操作必须排在后来才开始的操作之前。

数据库事务更常用可串行化描述：并发事务的读写历史必须等价于某个逐个执行事务的串行顺序。它关注整组读写，而不仅是一个内存地址。

普通可串行化不一定要求这个等价顺序服从现实时间。严格可串行化再加入实时先后约束，因此更接近“把整个事务视为一次线性化的多对象操作”。

这种类比很有帮助，但不能把术语直接画等号。单对象线性化具有局部组合性；数据库事务还要处理范围查询、谓词、幻读、索引、多版本和故障恢复。

PostgreSQL 对 `SERIALIZABLE` 的表述是：如果并发读写模式无法对应任何逐个执行的顺序，其中一个事务就会以序列化失败结束。[PostgreSQL 的可串行化隔离文档](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-SERIALIZABLE)体现了这种“验证并中止”的实现方式。

## 八、为什么事务必须正面讨论隔离性

并发编程把隔离分解进临界区、同步顺序和所有权协议；数据库则必须把这些约束提升为公开的数据服务契约。原因首先在于二者保护的时间与状态范围完全不同。

CPU 可以把一次 CAS 压缩成极短的硬件事件。数据库事务却可能持续数秒甚至数小时，执行许多语句，跨越不同表、索引、约束、分片和外部请求。

事务还会先读取数据，再根据结果决定后续写入。于是需要保护的不是某个地址，而是“我作出决定时所依据的事实”。其他事务可能修改一行，也可能插入一条此前不存在、却符合查询谓词的新行。

这就是幻读和写偏差比普通变量竞争更难处理的原因。锁一个已知地址很直接，锁住“所有当前或未来满足这个条件的对象”则需要谓词锁、索引范围锁或序列化冲突检测。

数据库也不能假设所有客户端共享同一进程的 Mutex。客户端来自不同线程、进程和机器，可能使用不同语言，甚至在运行过程中断线。数据库是唯一能够观察并仲裁全部数据访问的组件。

最后，完全串行执行虽然容易推理，却会损失大量并发能力。数据库因此必须把隔离性变成显式契约：哪些异常被禁止，哪些仍可能发生，冲突时是等待、失败还是读取旧版本。

所以，并发编程不是不讨论隔离，而是通常让程序员用临界区和内存模型亲自划定边界；事务系统则必须把这个边界提升为跨客户端、跨对象、可恢复的数据服务契约。

## 结语：原子是一份边界声明

“这个操作是原子的”从来不是一个完整陈述。至少还要补上五个问题：

1. 原子单位是什么：一个机器字、一个变量、一行、一个语句，还是整个事务？
2. 针对谁不可分割：CPU 核心、线程、进程、数据库客户端，还是恢复程序？
3. 防的是并发交错，还是中途失败？
4. 原子边界是否覆盖了业务不变量涉及的全部状态？
5. 是否还需要顺序、可见性、持久性和实时先后保证？

CPU CAS、语言原子类型与数据库条件写共享同一个核心形状：把竞争更新压缩到一个可以验证并决定成功或失败的单点上。

ACID 原子性处理的是另一条轴线：如果整体不能完成，就不能留下局部结果。隔离性则规定多个这样的整体如何同时存在，以及它们能够怎样观察彼此。

原子负责划定不可切开的边界；隔离负责安排边界之间的关系。真正困难的从来不是拥有一条原子指令，而是为问题选择正确的原子边界，并让所有参与者共同遵守它。
