“封装、继承、多态”能解释一部分 Java 和 C++ 代码，却无法解释为什么 Go 故意不建立类型层次，为什么 Rust 用 `trait` 而不是类继承，也无法解释 JavaScript 的原型链。

问题在于，这三个词把“面向对象的常见机制”当成了“程序设计的全部问题”。跨语言比较时，更有解释力的问法是：一种语言如何组织数据与行为，又把哪些约束交给编译器？

## 一、先建立同一把标尺

设想一个通知系统。它有邮件、短信等发送器，每种发送器都能 `send`。需求很小，却包含了几乎所有程序组织问题：

1. 邮箱地址、限流状态和网络客户端放在哪里？
2. 怎样说明不同类型都具有 `send` 行为？
3. 新增发送渠道时，谁需要知道这种关系？
4. 调用 `send` 时，在编译期还是运行时选中具体实现？
5. 连接、内存和共享状态由谁拥有，又何时释放？

五种语言都能实现这个系统。真正的区别不是“能不能”，而是它们让哪种写法更自然，让哪种错误更早暴露，以及为这些保证付出什么代价。

## 二、Java：先声明身份，再通过对象协作

Java 的经典建模单元是类。字段表示状态，实例方法表示行为，访问控制维护封装边界。一个对象是某个类的实例，引用可以指向声明类型的实例或其子类实例。

Java 的类关系是**名义式**的。`EmailSender` 即使恰好写了 `send` 方法，也不会自动成为 `Sender`；它必须显式声明 `implements Sender`。Java 语言规范明确说，仅仅拥有相同方法还不够。

这使“类型之间有什么关系”成为提供方的公开声明。编译器、IDE 和框架都能围绕这张显式的类型网工作；代价是抽象与实现者彼此知道，后加的抽象不能自动套在旧类型上。

Java 类只能单继承，但可实现多个接口。继承可复用状态和实现，接口则更适合表达跨越无关类层次的共同行为。通过接口引用调用可覆盖方法时，具体实现在运行时选择。

因此，Java 最有代表性的思路不是“把所有东西塞进继承树”，而是**用类守住不变量，用接口稳定协作边界，用对象组合完成业务**。类继承只是其中一种工具。

现代 Java 也已不只有传统对象建模。`record` 用简洁语法表示值的聚合；`sealed` 类和接口可限制子类集合；再配合模式匹配，Java 也能直接表达“有限种可能的数据”。

所以，称 Java “强烈支持面向对象”是准确的；称它“只能按传统面向对象思考”，已经不准确。

- [接口声明](https://docs.oracle.com/javase/specs/jls/se26/html/jls-9.html)

## 三、C++：类层次、值语义与泛型同时存在

C++ 有类、封装、多继承、虚函数和动态绑定，当然能写典型面向对象代码。抽象基类可充当接口，派生类覆盖虚函数，调用端通过基类指针或引用实现运行时多态。

但把 C++ 只定义为“面向对象语言”，会丢掉两条同样重要的主线：**值语义**与**泛型编程**。前者深入其对象和资源模型，后者支撑了大量标准库设计。

值语义把用户定义类型像整数一样看待：可以在栈上创建，可以复制、移动和比较，对象的含义不必依赖某个唯一身份。`std::string` 和 `std::vector` 就是典型：它们是类，但不属于多态继承树。

值语义又与 RAII 结合。对象构造时获得资源，析构时释放资源，作用域因而同时是资源边界。内存、锁、文件句柄和 socket 都能被封装成拥有者，释放不依赖垃圾回收时机。

泛型编程则不要求参与类型共享基类。模板按类型能否支持所需操作生成代码，`concept` 把对模板实参的要求显式命名，并让这些约束参与重载解析。这类抽象不必进入虚函数系统。

因此，C++ 里的 `Sender` 可以是抽象基类，以获得运行时可替换性；也可以是一个 `concept`，让模板在编译期接受任何能 `send` 的类型。前者买来运行时开放性，后者保留具体类型与优化机会。

C++ Core Guidelines 甚至明确建议：优先使用具体类型，只在概念本身具有层次结构时使用类层次。这和“见到复用就继承”几乎是相反的工程方向。

- [约束与 `concept`](https://eel.is/c++draft/temp.constr)
- [Stroustrup 与 Sutter 维护的 C++ Core Guidelines](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines)

## 四、Go：你说的方向对，但要区分组合与继承

用“结构体、接口与组合”概括 Go 的常见设计思路，方向是准确的。但更精确的说法是：**结构体组织数据，方法集提供行为，接口按行为建立抽象，嵌入用于组合与方法提升**。

首先，Go 的方法不只能定义在结构体上。方法依附于同一包内的已定义类型；这个类型的底层表示可以是结构体，也可以是整数、字符串或切片。所以 Go 不是用 `struct` 简单替换 `class`。

其次，Go 接口是**隐式满足**的。只要 `EmailSender` 的方法集包含接口要求的 `send`，它就实现了 `Sender`，无需也没有 `implements` 声明。旧类型因而可以适配后出现的小接口。

这是一种结构化关系：“能做什么”比“宣布自己是谁”更重要。它鼓励调用方在真正需要抽象的地方定义小接口，而不是由实现方预先设计一个覆盖所有用途的大接口。

最后，嵌入不是子类化。外层结构体可获得内嵌字段的提升方法，但调用这些方法时，接收者仍是内层值，不是外层值。外层类型也不因嵌入而成为内层类型的子类。

Go 的取舍是：少维护一张显式类型层次，多用局部的行为契约组合程序。具体类型上的方法静态解析；需要运行时动态派发时，才通过接口值调用。

- [Go 语言规范的接口与方法集](https://go.dev/ref/spec#Interface_types)
- [Effective Go 的嵌入说明](https://go.dev/doc/effective_go#embedding)

## 五、Rust：把数据、行为、可能性与所有权分开表达

Rust 没有一个能与“Java 是类”或“Go 是组合”工整对应的单一标签。如果必须压缩，最接近实际的概括是：**用所有权约束资源与访问，用结构体和枚举表示数据，用 trait 表示共享行为，用组合建立系统**。

Rust 中，`struct` 和 `enum` 定义数据，`impl` 块为类型提供方法。数据声明与方法实现在语法上分开，但仍可封装成稳定的公开 API。按“数据与方法绑在一个抽象里”的定义，Rust 具有面向对象特征。

但 Rust 没有类继承。一个结构体不能继承另一个结构体的字段与方法。状态复用通过字段组合，行为契约通过 `trait`，有限的实现复用可通过 trait 默认方法完成。

`trait` 和 Go 接口的目标相似，都在描述共享行为；关系的建立方式却不同。Rust 要求 `impl Sender for EmailSender` 这样的显式实现，Go 则根据方法集隐式判定。Rust 的 trait 关系是名义式的，不是鸭子类型。

Rust 又把“多态在何时发生”变成明确选择。`T: Sender` 或 `impl Sender` 使用泛型和 trait bound，通常在编译期产生针对具体类型的代码；`&dyn Sender` 或 `Box<dyn Sender>` 则通过虚表在运行时派发。

还有一条与接口完全不同的轴：`enum` 把一组已知可能性封闭在一个类型内，`match` 要求穷尽处理。这很适合表达“结果只能是成功、可重试失败或永久失败”这类封闭领域。

trait 解决“哪些类型具有某种能力”，枚举解决“一个值只可能是哪几种情况”。前者偏向开放扩展，后者偏向封闭穷举。这两个工具不是竞争关系。

Rust 最独特的部分是，它还要求 API 表明值的拥有、借用与可变访问。引用是否能活得足够久，同一时间能否存在多个可变访问，不只是文档约定，而是类型检查的一部分。

因此，Rust 的核心贡献不是发明了另一种“对象”，而是把数据、共享行为、可能性集合、资源所有权和派发时机拆成正交机制，再由类型系统检查它们能否安全组合。

## 六、JavaScript：对象先于类，继承本质是原型委托

JavaScript 的核心对象模型不是 Java 或 C++ 那样的类模型。ECMAScript 规范把对象定义为属性的集合，并且每个对象有一个原型对象或 `null`。

读取属性时，如果对象自身没有该属性，运行时会沿原型链继续查找。方法本质上也是值为函数的属性。所谓继承，因而更接近“这个对象没有回答，就沿链把请求委托给另一个对象”。

`class` 语法为构造、方法、继承和私有字段提供了更集中的表达，但它仍建立在原型机制上。说它只是“语法糖”又过于粗糙，因为类语法自己还有严格模式、私有元素等专属语义。

JavaScript 不要求 `EmailSender` 声明实现 `Sender`。调用端可以接收任何值，在运行时读取它的 `send` 属性并调用。这是动态的结构化协作，也常被称为鸭子类型。

这种模型的优势是边界轻。对象字面量、函数、闭包和对象展开都能用来组合行为，不需要先构造完整类层次。代价是纯 JavaScript 通常要到运行时才发现属性缺失或类型不符。

TypeScript 能在 JavaScript 之上增加静态结构类型检查，但它是额外工具链，不改变 ECMAScript 对象在运行时仍通过属性和原型工作的事实。

- [ECMAScript 规范的对象与原型定义](https://tc39.es/ecma262/#sec-terms-and-definitions-object)
- [普通对象的 `[[Prototype]]` 语义](https://tc39.es/ecma262/#sec-ordinary-object-internal-methods-and-internal-slots)
- [MDN 的原型链说明](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Inheritance_and_the_prototype_chain)

## 七、同一个 `send`，五种不同的关系

回到通知系统。如果只看最终的 `sender.send(message)`，五种语言很像。但是，这行调用背后的关系完全不同。

| 语言       | `EmailSender` 如何成为 `Sender`    | 常见派发方式                          | 新抽象能否适配旧类型                        |
| ---------- | ---------------------------------- | ------------------------------------- | ------------------------------------------- |
| Java       | 显式 `implements`                  | 接口调用运行时派发                    | 通常不能，需修改或适配器                    |
| C++        | 继承抽象基类，或满足 `concept`     | 虚函数动态派发，或模板静态派发        | `concept` 可在不改旧类型时约束其操作        |
| Go         | 方法集隐式满足接口                 | 具体类型静态，接口值动态              | 能，只要现有方法集满足接口                  |
| Rust       | 显式 `impl Sender for EmailSender` | 泛型静态派发，或 `dyn Trait` 动态派发 | 可为旧类型补 trait 实现，但受一致性规则约束 |
| JavaScript | 运行时值恰好有可调用的 `send`      | 动态属性查找与调用                    | 能，但纯 JavaScript 不提供编译期契约        |

这张表说明了一个重要事实：**接口、多态和继承不是同一件事**。接口描述契约，多态让一段代码处理多种类型，继承只是建立某些类型关系与复用实现的一种手段。

`overload` 也不是这里所说的运行时多态。重载是同名声明之间的选择，通常由编译期参数类型决定；重写是对可派发行为提供新实现。Go 故意不支持函数和运算符重载，却完全支持接口多态。

## 八、“开放的行为”与“封闭的可能性”

另一个比“是否面向对象”更有用的问题是：需要扩展的维度是开放的，还是已知且有限的？

通知渠道往往是开放集合。今天有邮件和短信，明天可以在不修改调用方的情况下增加推送。Java 接口、C++ 抽象基类、Go 接口、Rust trait 和 JavaScript 行为约定都能处理这类问题。

发送结果却可能是封闭集合：成功、可重试、不可重试。这时候，穷尽可能性比允许任意子类更重要。

| 语言       | 表达封闭变体的典型工具                        | 能否检查穷尽处理            |
| ---------- | --------------------------------------------- | --------------------------- |
| Java       | `sealed interface` + `record` + 模式 `switch` | 能                          |
| C++        | `std::variant` + `std::visit`                 | 可由类型与访问器组合检查    |
| Go         | 接口 + type switch，或显式标签字段            | 语言不保证 type switch 穷尽 |
| Rust       | `enum` + `match`                              | 能，非穷尽匹配无法编译      |
| JavaScript | 标签属性 + `switch`                           | 纯 JavaScript 不检查        |

面向对象的开放多态擅长“新增一种实现”，代数数据类型擅长“对已知的每种情况新增一项操作”。把开放问题强行封闭，或把封闭问题做成无限继承树，都会制造额外复杂度。

## 九、资源管理也是设计思想，不是运行时细节

类型如何组合，只回答了系统的静态结构。程序还必须回答：对象由谁拥有，能被多少代码同时修改，资源何时释放？

Java、Go 和 JavaScript 使用垃圾回收管理大部分内存。这降低了内存生命周期的日常负担，但垃圾回收不会自动解决共享可变状态，也不能代替文件、锁和连接的确定性关闭。

C++ 用 RAII 把资源生命周期绑到对象生命周期，但语言仍允许裸指针、手工内存管理和复杂别名；安全性依赖严格的类型设计、库与工程纪律。

Rust 同样依靠作用域结束时的确定性销毁，但它进一步用所有权和借用规则限制别名与可变访问。这迫使接口不只描述“能做什么”，还描述“谁可以在什么时候做”。

这也是从 Java 或 Go 转向 Rust 时最需要换掉的直觉：借用检查器不只在审查内存技巧，它在审查整个 API 对数据所有权与共享方式的设计。

## 十、一张表看清五种语言的默认选择

| 维度         | Java                 | C++                        | Go                       | Rust                    | JavaScript                         |
| ------------ | -------------------- | -------------------------- | ------------------------ | ----------------------- | ---------------------------------- |
| 常见数据单元 | 类、`record`         | 值类型、`struct` / `class` | 已定义类型、`struct`     | `struct`、`enum`        | 动态对象                           |
| 数据与行为   | 在类中聚合           | 成员与非成员并用           | 类型声明与接收者方法分开 | 类型与 `impl` 分开      | 属性可保存数据或函数               |
| 抽象关系     | 名义式接口           | 名义式继承或表达式约束     | 隐式结构接口             | 显式 trait 实现         | 运行时结构约定                     |
| 类型继承     | 类单继承，接口多继承 | 支持多继承                 | 无                       | 无                      | 原型链委托，`class extends` 建立链 |
| 主要组合手段 | 对象字段与接口       | 成员、值类型、模板         | 字段、嵌入、小接口       | 字段、trait、泛型、枚举 | 对象、函数、闭包、原型             |
| 资源思路     | GC；外部资源显式关闭 | RAII 与显式所有权类型      | GC；`defer` 常用于清理   | 所有权、借用、`Drop`    | GC；外部资源按 API 管理            |

这些都是“默认重心”，不是能力边界。Java 可以大量使用函数风格，C++ 可以全程不写虚函数，Go 可以写面向对象风格，Rust 可以用 trait object 实现运行时多态，JavaScript 也可以用类组织大型系统。

## 十一、如何从问题选择抽象

语言已经选定时，不需要羡慕另一种语言的外形。先看变化发生在哪里，再使用本语言最直接的机制。

- 实现种类将由第三方持续增加，用开放的行为契约：Java 接口、C++ 抽象基类、Go 接口、Rust trait object，或 JavaScript 对象约定。
- 可能性已知且必须全部处理，用封闭数据模型：Rust `enum`、Java sealed hierarchy 或 C++ `variant` 比无限子类更直接。
- 具体类型在编译期已知，而抽象成本敏感，优先考虑 C++ 模板与 `concept`、Rust 泛型与 trait bound，不必为了“多态”强制引入运行时间接层。
- 只是复用一段实现，不要立刻声明“是一种”关系。优先使用字段组合、委托、普通函数或库，只在领域概念真有稳定层次时才用继承。
- 正确性依赖独占修改、借用期限或确定性释放时，资源模型就是 API 设计本身。这是 Rust 的类型系统和 C++ RAII 尤其值得关注的地方。

## 结论：不要用一个名词包办所有设计

“Java 和 C++ 是面向对象，Go 是组合，Rust 是什么？”是一个有用的起点，但分类粒度太粗。

更准确的回答是：Java 偏向显式名义类型与对象协作；C++ 同时重视对象层次、值语义、泛型与 RAII；Go 用已定义类型、隐式小接口和嵌入组合降低层次成本。

Rust 把数据、行为、封闭变体、派发方式与所有权拆开，用类型系统检查组合；JavaScript 则以动态对象和原型委托为底层模型，并可在其上选择类或函数组合。

语言思想最终不是一套必须信奉的口号，而是对四个问题的系统回答：**数据怎样组织，行为怎样约束，变化怎样隔离，错误最迟应在什么时候暴露。**
