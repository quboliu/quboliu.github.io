“线性一致性是不是也叫可串行化？”

这个疑问非常典型，因为二者都在做同一件表面相似的事：把并发执行解释成某种顺序执行。但它们约束的对象、要求保留的顺序以及组合方式并不相同。

一句话先给结论：**线性一致性约束单次操作，并要求尊重真实时间；可串行化约束事务，但不要求尊重真实时间；严格可串行化才是二者在事务语境中的结合。**

要真正分清这些术语，不能只背一条“强弱排行榜”，而要先回答两个问题：**约束谁？保留什么顺序？**

## 一、先拆开三个同名的“一致性”

“一致性”至少在三个语境中出现，它们不是一回事。

| 语境 | 核心问题 | 典型概念 |
|---|---|---|
| ACID 的 Consistency | 事务前后是否保持业务不变量 | 余额非负、外键有效、借贷平衡 |
| 并发与副本一致性模型 | 多个操作能否被解释为满足某种顺序的历史 | 线性一致性、顺序一致性、因果一致性 |
| 事务隔离 | 并发事务彼此能看到什么，结果能否等价于串行执行 | 读已提交、快照隔离、可串行化 |

ACID 中的 C 主要是应用不变量。数据库可以通过约束和事务机制帮助维护它，但“什么状态算合法”最终由业务定义。

分布式语境中的一致性通常讨论多个副本、进程或客户端观察到的操作历史。它关注的是读写结果与某种顺序模型是否相容。

隔离级别则讨论事务之间如何互相影响。一个事务往往包含多次读写，正确性不能只靠单个键的一次读写来判断。

因此，“数据库开启了 ACID”不能推出副本是线性一致的；“每个键都线性一致”也不能推出跨键事务可串行化。

## 二、单机与分布式不是概念分界线

把“隔离级别属于单机，一致性模型属于分布式”当作入门近似尚可，但不能当作严格定义。

单机上也有多个线程、CPU 缓存与并发对象，因此同样可以讨论顺序一致性和线性一致性。线性一致性最初就是作为**并发对象的正确性条件**提出的，并非专属于网络副本。

分布式数据库也必须处理并发事务，因此同样需要读已提交、快照隔离或可串行化。网络只是让实现这些语义更昂贵，并没有改变概念本身。

更准确的划分方式是：

- **一致性模型**观察操作历史，常以读、写或对象方法调用为单位；
- **隔离模型**观察事务历史，以一组读写组成的事务为单位；
- 单机和分布式只是这些模型运行的不同环境。

## 三、读懂一致性模型：系统承诺保留哪一种顺序

不同一致性模型并非只是在“多久能读到最新值”上做快慢取舍。它们真正的区别，是系统承诺所有观察者共同保留哪些顺序关系。

### 3.1 最终一致性：停止写入后，副本最终收敛

最终一致性承诺：如果不再产生新更新，所有副本最终会收敛到同一状态。

它没有单独保证收敛前读到什么，也不天然保证读己之写、单调读或因果顺序。一次读到新值后，下次连接到落后副本，仍可能读回旧值。

“最终”也不是固定延迟，例如“数据会在五秒内一致”。前者是收敛性质，后者是带时间上界的服务承诺。

### 3.2 客户端中心一致性：让一次会话不至于反直觉

在弱一致副本上，可以为单个客户端提供更实用的会话保证：

- **读己之写**：自己写入后，后续读取不会看不见该写入；
- **单调读**：一旦见过某个版本，后续不会退回更旧版本；
- **单调写**：同一客户端的写入按发出顺序生效；
- **写跟随读**：若客户端读到某个版本后发起写入，该写入必须在产生该版本的写入之后生效。

这些保证改善单个会话的体验，但不意味着所有客户端拥有统一的全局顺序。

### 3.3 因果一致性：原因必须出现在结果之前

如果操作 B 可能受操作 A 影响，例如用户看到帖子后回复，那么所有观察者都必须先看到 A，再看到 B。

没有因果关系的并发操作可以被不同观察者按不同顺序看到。因此因果一致性保留的是偏序，而不是强行制造唯一全序。

这也是它比线性一致性更容易扩展的原因：系统只协调真正有依赖的操作，不必为所有无关事件排出全球统一名次。

### 3.4 顺序一致性：所有人同意一个全序，但它可以违背墙上时间

顺序一致性要求存在一个包含所有操作的全局顺序，并且该顺序保留每个进程自身的程序顺序。

它不要求保留跨进程的真实时间顺序。即使 A 的写操作已经返回，随后 B 才开始读，系统仍可能把 B 的读排在 A 的写之前，只要不破坏各进程内部顺序。

“所有人看到相同顺序”与“该顺序符合现实先后”是两项不同承诺。

### 3.5 线性一致性：全局全序还必须尊重真实时间

线性一致性要求每个操作仿佛在其调用与返回之间的某一个瞬间原子生效，这个瞬间称为**线性化点**。

若操作 A 已经完成，操作 B 随后才开始，那么全局顺序中 A 必须位于 B 之前。若二者时间区间重叠，则它们确实并发，可以按任一合法顺序排列。

例如，写入 `x=1` 已返回，之后另一个客户端发起读取却得到 `x=0`，且期间没有其他写入。这不可能是线性一致的，因为真实时间已经固定了先写后读。

线性一致性也常被称为**原子一致性（atomic consistency）**。它通常就是 CAP 讨论中的 C；CAP 里的“一致性”不是泛指任意一致性模型。

### 3.6 一致性模型不是简单的一条直线

若只比较历史允许集合，并固定对象语义与模型前提，可以形成一个便于记忆的近似关系：

```text
线性一致性  ⇒  顺序一致性  ⇒  因果一致性
```

最终收敛属于另一维度：它描述停止更新后的长期结果，不能仅凭上述安全性箭头推出。不同论文还可能采用不同对象、故障模型和进度条件；会话保证与因果一致性之间也不是一个简单刻度。

真正可靠的做法始终是读定义：它量化的是所有客户端还是单个会话？约束的是全序、程序顺序、因果顺序还是真实时间？

## 四、读懂隔离级别：并发事务能互相看到什么

一致性模型常把一次读写当作操作，隔离级别则把多次读写组成的事务视为整体。

SQL 标准常用脏读、不可重复读和幻读描述隔离级别。但只靠这三个现象并不足以完整刻画现代实现，还应关注丢失更新、读偏斜与写偏斜。

### 4.1 读未提交：可能看到尚未提交的数据

事务可能读到其他事务尚未提交的写入。如果对方随后回滚，读到的就是从未正式存在过的状态，即**脏读**。

这是很弱的隔离。许多现代数据库即使标注此级别，实际也可能提供更强行为。

### 4.2 读已提交：每次读取只看已提交数据

读已提交消除了脏读，但同一事务中的两次查询可能各自获取不同的已提交快照。

因此，同一行可能前后读出不同结果，形成不可重复读；两次范围查询也可能出现或消失若干行。

它还不自动防止“读取—计算—覆盖写回”造成的丢失更新，具体行为取决于数据库实现和语句形式。

### 4.3 可重复读：名称相同，实现语义未必相同

按 SQL 现象定义，可重复读禁止脏读和不可重复读，但仍可能允许幻读。

现实数据库中的“可重复读”差异很大。有的接近锁式实现，有的实际使用多版本快照。因此不能只凭级别名称推导写偏斜、幻读或丢失更新是否可能发生。

讨论具体系统时，应查它的并发控制机制与异常保证，而不是把产品标签当作完整形式化定义。

### 4.4 快照隔离：事务读取同一个一致快照

快照隔离让事务中的所有读取来自同一快照，通常还采用“先提交者胜出”等规则阻止两个并发事务写同一数据项。

它同时消除了读偏斜：事务内的多次读取来自同一快照，不会像读已提交那样先后拼出一个从未同时存在过的状态。

它能避免许多读异常，并提供很好的并发性能，但**快照隔离不等于可串行化**。

经典反例是写偏斜：值班规则要求 A、B 至少一人在线。两个事务都从快照中看到二人在线，随后分别让 A 和 B 下线；它们写不同记录，不发生写写冲突，却共同破坏了业务约束。

### 4.5 可串行化：结果等价于某个串行事务顺序

可串行化要求并发事务的整体效果与某个逐个执行的串行顺序等价。

它没有要求这个串行顺序符合真实时间。即使事务 T1 已完成、T2 随后才开始，理论上也可能把 T2 排在 T1 前，只要整个历史仍与该串行顺序等价。

可串行化描述的是允许哪些历史，不限定必须使用严格两阶段锁、串行化快照隔离或乐观并发控制。隔离语义与实现算法也应分开。

## 五、最容易混淆的三兄弟

现在可以正面比较线性一致性、可串行化与严格可串行化。

| 性质 | 约束单位 | 是否要求等价于顺序执行 | 是否尊重真实时间 | 是否可按对象独立组合 |
|---|---|---:|---:|---:|
| 线性一致性 | 单次对象操作 | 是 | 是 | 是 |
| 可串行化 | 事务 | 是 | 否 | 否 |
| 严格可串行化 | 事务 | 是 | 是 | 否 |

### 5.1 为什么线性一致性不是可串行化

线性一致性中的“每个操作像瞬间发生”，确实很像把并发操作排成串行顺序；可串行化也确实要寻找一个串行事务顺序。混淆就来自这里。

但二者的语义边界不同：一个转账事务可能先读余额，再写两个账户。线性一致性通常分别判断对象操作；可串行化判断整组读写能否作为一个事务与其他事务排序。

此外，线性一致性明确保留非并发操作的真实时间顺序，而普通可串行化没有这项要求。

你可能记混的别名是：**线性一致性也叫原子一致性，而不是可串行化。**

### 5.2 严格可串行化才是交汇点

严格可串行化要求：

1. 并发事务等价于某个合法串行顺序；
2. 若 T1 在真实时间上先完成、T2 后开始，则串行顺序中 T1 必须先于 T2。

因此可以用下面的记忆式建立直觉：

```text
严格可串行化 = 可串行化 + 事务之间的真实时间顺序
```

也可以说，它把线性一致性的实时要求提升到了事务层面。但不要把它形式化地写成“线性一致性 + 可串行化”的集合运算，因为二者原本量化的历史单位不同。

### 5.3 为什么“每个对象线性一致”仍不够

线性一致性具有局部性：如果每个对象分别线性一致，那么由这些对象构成的历史也线性一致。这使对象可以独立实现和验证。

可串行化不具备这种局部性。账户 A 与账户 B 各自的读写都合法，不代表跨两个账户的转账事务不会暴露中间状态，也不代表多个事务能排成同一个串行顺序。

因此，一组线性一致的键值操作不会自动升级成可串行化事务。跨对象原子性与事务隔离仍需额外协议。

### 5.4 为什么可串行化也未必让外部世界满意

假设 T1 已提交 `x=1`，之后 T2 才启动，却读到旧值。若系统把 T2 串行化在 T1 之前，普通可串行化仍可能接受这段历史。

但用户会认为“已经完成的写入被后来的事务忽略了”。严格可串行化通过保留真实时间顺序排除这种解释。

这也是金融交易、锁服务、主节点选举等外部顺序重要的场景，往往需要比普通可串行化更强保证的原因。

## 六、几个高频错误推论

### 错误一：单机数据库天然线性一致

单机只消除了网络副本延迟，不会自动消除线程并发、缓存、异步 I/O 或事务可见性问题。是否线性一致仍取决于接口规约与实现。

### 错误二：强一致就是线性一致

“强一致”没有统一精确定义。有人用它指线性一致，有人用它泛指非最终一致。严肃讨论中应直接写出线性一致、顺序一致或严格可串行化。

### 错误三：可重复读一定没有幻读

标准现象表与具体数据库实现可能不同。“可重复读”只是产品暴露的名字，不能替代该产品的正式语义说明。

### 错误四：快照隔离就是可串行化

快照隔离能提供稳定读视图，也常阻止同一数据项的并发写，但仍可能发生写偏斜。

### 错误五：线性一致的数据库一定支持线性一致事务

单键操作线性一致，只说明各操作在真实时间兼容的全序中原子生效。多键事务还需要原子性与隔离机制；严格可串行化才是事务层面的对应目标。

### 错误六：CAP 中的 C 是 ACID 中的 C

CAP 的 C 通常指线性一致性；ACID 的 C 指事务把数据库从一个满足约束的状态带到另一个满足约束的状态。它们只是碰巧使用了同一个英文单词。

## 七、用四种顺序建立统一坐标系

遇到新术语时，可以问它是否保留下列顺序：

| 顺序 | 含义 | 典型模型 |
|---|---|---|
| 程序顺序 | 同一进程发出的操作不能随意颠倒 | 顺序一致性 |
| 因果顺序 | 可能影响后续操作的原因必须在结果之前 | 因果一致性 |
| 真实时间顺序 | 已完成的操作必须排在随后开始的操作之前 | 线性一致性、严格可串行化 |
| 事务串行顺序 | 整个事务历史等价于逐个执行 | 可串行化、严格可串行化 |

这个坐标系比背诵“强、中、弱”更可靠。

线性一致性保留真实时间，并为操作建立合法全序；顺序一致性只要求全局全序与各进程程序顺序相容；因果一致性只统一有因果关系的顺序；可串行化则换了观察单位，要求事务整体可排序。

## 八、工程上到底该选什么

不要先问“哪个级别最强”，先问错误结果能否被业务接受。

- 社交动态、点赞计数、缓存副本常可采用最终或因果一致性，再叠加会话保证；
- 配置发布、分布式锁、主节点与 fencing token 常需要线性一致的协调存储；
- 报表与只读分析常适合一致快照；
- 涉及跨行不变量的事务，应检查快照隔离下的写偏斜，并考虑显式锁、约束或可串行化；
- 若事务完成顺序本身对外部观察者具有业务含义，应进一步确认是否提供严格可串行化。

更强的语义通常意味着更多协调、更高延迟或更低可用性，但“弱一些”也会把复杂度推给应用：版本合并、幂等、补偿、冲突解决与异常测试都要付费。

正确选择不是无条件追求最强，也不是为了性能默认最弱，而是明确业务不变量，找到足以保护它们的最低正确性条件。

## 九、最后再记一次

```text
最终一致性：没有新写入后，副本最终收敛
因果一致性：原因必须先于结果
顺序一致性：所有人同意一个全序，但不保证符合墙上时间
线性一致性：操作像瞬间发生，并尊重真实时间

读未提交：可能读到未提交数据，即脏读
读已提交：只读已提交数据，但同一事务内两次读取可能不同
可重复读：同名级别的实际语义因数据库实现而异
快照隔离：事务读取稳定快照，但可能写偏斜
可串行化：事务结果等价于某个串行顺序
严格可串行化：可串行化，并尊重真实时间
```

所以，对最初问题最准确的一句话回答是：

> **线性一致性约束操作且尊重真实时间，可串行化约束事务但不要求真实时间，严格可串行化才是二者在事务层面的交汇。**
