DDIA 第二版 P773 说：数据库是「可变的共享变量」，但你没法订阅它的变更，只能轮询；想订阅得自己实现观察者模式。

这段话说得很抽象。落到实处的问题是：**现实系统里哪些东西是观察者模式？** 本文用两个真实机制做对照——etcd 的 Watch 和 PostgreSQL 的 LISTEN/NOTIFY——它们都是观察者模式，但钉在这个模式可靠性频谱的两端。

## 0. 先立判据

观察者模式的最低结构只有两条：

```text
注册：观察者向状态持有者登记「我关心什么」
推送：状态变更时，持有者主动通知，观察者不再轮询
```

满足这两条就算观察者模式。但工程上真正拉开差距的是第三条：

```text
通知丢了，能不能补回来？
```

## 1. etcd Watch：是，而且通知是日志派生的

etcd 的 watch 机制：客户端对单个 key 或前缀建立 watch（gRPC 流式连接），此后该 key 的每次变更都以事件形式推送给订阅者。

机制上值得注意的几点：

- **事件从 revision 历史派生。** etcd 的写入经 Raft 复制落盘，每次事务递增全局 revision；watch 事件不是凭空产生的回调，而是**从已提交的 MVCC 修订历史中流出**的。换句话说，watch 订阅的是一条持久、有序、全集群共识的日志。
- **可续传。** watch 可以指定起始 revision；连接断了，客户端记下最后看到的 revision，重连后从那里继续——错过的事件能补回来。
- **有序且原子。** 事件严格按 revision 顺序交付；同一事务内的多个变更作为一个批次交付。
- **可靠性的边界是 compaction。** revision 历史会被压缩；如果你的起始 revision 早于压缩点，watch 直接失败返回 `ErrCompacted`——日志保不住无限历史，落后的订阅者必须全量重读再重新订阅。

结论：etcd Watch 是观察者模式，而且正好是「把通知物化成日志条目」的形态——观察者模式的可靠性，直接继承了 Raft 日志的持久性和全序性。

## 2. PG LISTEN/NOTIFY：是，但通知是易失信号

PostgreSQL 的 LISTEN/NOTIFY：会话执行 `LISTEN channel` 注册；任意事务执行 `NOTIFY channel, payload`，**提交之后**，所有正在监听该 channel 的会话收到异步推送。

它满足注册 + 推送，也是观察者模式。但机制细节决定了它是「弱」的那一端：

- **与事务原子，但不持久。** 回滚的事务不会投递通知（这一点很好——通知和提交绑定）；但通知队列在内存中，**投递对象是「当前连接着的」会话**。订阅者断开时发生的事，它永远不知道——没有历史、没有重放、没有续传位置。
- **同事务内去重。** 同一事务对同一 channel 发出相同 payload 的重复通知，只会投递一次。
- **有明确的容量边界。** payload 默认上限约 8000 字节；通知队列积压到上限（标准构建 8GB）时，提交直接失败。
- **官方用法定位就是「唤醒信号」。** 收到通知后**重新查表**，而不是把 payload 当数据用——典型场景是缓存失效提示：通知只负责说「该刷新了」，新值自己去数据库读。

结论：LISTEN/NOTIFY 是观察者模式的易失形态——通知是一个动作，错过即失。它适合「提示 + 回读」，不适合当事件源。

## 3. 频谱上的其他成员

用「通知丢了能不能补回来」这把尺子量一遍常见系统：

| 机制 | 注册+推送 | 通知持久性 | 丢失语义 |
| --- | --- | --- | --- |
| DOM EventListener / 语言内回调 | ✓ | 无 | 进程内调用，错过即失 |
| Redis keyspace notification | ✓ | 无（走 pub/sub） | 订阅者不在线即丢 |
| PG LISTEN/NOTIFY | ✓ | 内存队列，无历史 | 断线即丢，同事务去重 |
| etcd Watch | ✓ | revision 历史（有 compaction 边界） | 可从 revision 续传；被压缩则报错 |
| K8s informer（list-watch） | ✓ | API server 的 resourceVersion 窗口 | watch 返回 `410 Gone` 后重新 list |
| Kafka 消费 | ✓ | 日志即数据源（有 retention 边界） | offset 即续传位置，落后被截断则重置 |

K8s informer 值得单独说一句：它是「观察者 + 轮询」的混血——先 list 拿全量，再 watch 拿增量，并且周期性 resync。这个设计公开承认了一件事：**纯推送一定会漏，所以用定期全量来兜底**。`410 Gone`（resourceVersion 太旧）和 etcd 的 `ErrCompacted` 是同一个信号：日志压缩越过了你的位置，回到全量同步重来。

## 4. 收束回 DDIA

P773 说数据库没有内置订阅，这句话在两个对照案例里变得更具体了：

- PG 作为传统数据库，给出的订阅是**内存信号**——够用但易失，所以官方劝你收到后回读；
- etcd 作为围绕共识日志构建的系统，给出的订阅是**日志消费**——watch 只是 revision 历史的一个跟随游标。

这正是观察者模式进入数据系统时必须补的那层东西：**把「通知」从动作变成事实**。动作错过即失，事实可以重放。

> **判断一个机制是不是「可靠的观察者模式」，别看它有没有 subscribe 接口，看一件事：订阅者掉队之后，能不能从某个位置把错过的通知补回来。能补的是日志消费（etcd watch、Kafka、CDC），不能补的是信号（PG NOTIFY、Redis pub/sub）。两者都叫观察者模式，但只有前者配得上当数据源。**
