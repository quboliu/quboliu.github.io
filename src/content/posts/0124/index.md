外部一致性、线性一致性、顺序一致性、因果一致性、最终一致性，经常被画成一条从强到弱的直线。

这张图很方便，也很危险。先看三个看似矛盾的问题：

1. 一次写入已经返回成功，稍后读取却得到旧值：为什么它违反线性一致性，却可能满足顺序一致性？
2. 每个账户的读写都线性一致：为什么转账仍可能被看见一半？
3. 一个系统从不返回错误结果，只是永远不响应：为什么它仍可能满足线性一致性？

如果一条“强—弱”轴能解释一切，这三个问题不该如此难答。真正的问题是，我们把不同的约束单位、不同的顺序和不同类型的承诺混在了一起。

先给结论：

> **线性、顺序和因果一致性的核心排序条件约束操作历史，属于安全性；外部一致性的核心条件约束事务历史，也是安全性。**
>
> **最终一致性的“eventual”主要承诺传播与收敛，属于活性。它们不是同一把尺子上的五个刻度。**

这篇文章不靠口号排座次，而是用执行历史逐一审问：模型究竟禁止什么，又根本没有承诺什么。

## 一、讨论一致性之前，先问“在审判什么”

### 1.1 一致性模型约束的是合法历史

一次操作不是纸面上的一个函数名，而是从调用到返回的一段时间区间：

~~~text
invocation ───────── response
   调用                  返回
~~~

一段历史记录了多个客户端的调用、返回和返回值。模型要判断的是：这段并发历史能否被解释成某种合法行为。

“合法”至少依赖两部分：

- 顺序或可见性约束：哪些事件必须排在另一些事件之前；
- 对象的顺序规约：寄存器的读应返回哪个写，队列的出队应返回哪个元素。

因此，“一致性只管排序、不管数据值”说得过头了。排序非常重要，但返回值也是历史的一部分；系统还必须符合对象语义。

例如一个队列只入队一次 x，却让两个出队都返回 x。无论怎样重排，这都不是合法的 FIFO 历史。

反过来，“一致性就是所有副本此刻逐字节相同”也不对。线性一致系统的内部副本可以暂时不同，只要差异没有以非法结果暴露给客户端。

最终一致性才把副本传播与收敛直接放到问题中心。

### 1.2 第一把尺子：操作、事务，还是副本状态

线性一致性、顺序一致性和经典因果一致性，通常以单次读写等**操作**为基本单位。

外部一致性以整个**事务**为基本单位。一次事务可以动态读取和修改多个对象，并作为一个整体参加排序。

最终一致性常以**更新传播和副本状态**为讨论对象：更新能否最终到达，副本能否最终收敛。

粒度不同，问题就不同。每个键的操作都正确，不代表由多个键组成的事务也正确；所有事务都正确排序，也不等于每个离线副本都必须在有限时间内追上。

### 1.3 第二把尺子：安全性还是活性

安全性说“坏事永远不能发生”。一旦某次读取返回了模型禁止的结果，一个有限历史前缀就足以定罪，未来再运行也无法撤回已经返回的值。

活性说“好事最终会发生”。某个副本十分钟没有追上，并不能证明它永远不会追上；只有无限拖延才真正违反“最终”。

这也解释了第三个开场问题：一个永远不响应的系统没有返回任何错误值，所以可能不违反线性一致性；但它显然没有终止性或可用性。

这里特意说“核心条件”。论文或产品可能把排序安全性与会话保证、最终可见、终止等条件打包在同一个名字下。判断安全性或活性时，应先拆开具体条件，不能只看模型名称。

### 1.4 第三把尺子：究竟保留哪一种顺序

几个模型口中的“先后”并不相同：

| 顺序 | 它表达什么 |
|---|---|
| 程序顺序 | 同一客户端或进程内，程序规定的操作先后 |
| 读自关系 | 某次读返回了某次写产生的值 |
| 因果顺序 | 程序顺序、读自关系及其传递闭包形成的 happens-before |
| 真实时间顺序 | A 已返回，B 才被调用，因此 A 的区间完全早于 B |
| 事务串行序 | 整体效果等价于事务一个接一个执行的顺序 |

这里的“真实时间顺序”是历史中两个区间的先后关系。定义它不要求 API 暴露时间戳，也不等于实现必须读取物理时钟。这个区别将在 Spanner 一节中展开。

为避免不同文献的同名异义，本文先讨论经典的非事务读写对象；谈外部一致性时，再明确切换到事务模型。

### 1.5 三把尺子是分析工具，不是永久户籍

“线性一致性属于操作、外部一致性属于事务”描述的是经典定义的量化单位，不是说某个词永远不能跨界。

系统可以提供事务因果一致性，也可以把整个事务抽象成数据库对象的一次操作，再讨论它是否线性化。最终一致性也能施加于某种事务结果，而不只适用于单键副本。

因此，真正应问的是“这份规约把什么当作一次原子事件”，而不是根据模型名字猜粒度。本文的坐标是为了防止偷换定义，不是再造一张僵硬分类表。

## 二、线性一致性：不能倒放已经完成的历史

线性一致性要求每次操作看起来都在调用与返回之间的某一瞬间原子生效。这个抽象瞬间称为线性化点。

所有操作必须能排成一个符合对象规约的顺序，而且这个顺序要保留非并发操作的真实时间先后。

考虑初值为 0 的寄存器：

~~~text
A：write(x, 1) ─────> 成功
                                B：read(x) ──> 0
~~~

假设中间没有把 x 改回 0 的写。A 的写已经返回，B 的读才开始，因此读不能再被排到写之前；返回 0 违反线性一致性。

如果两个时间区间重叠，结论就不同：

~~~text
A：write(x, 1) ─────────────>
B：       read(x) ─────> 0
~~~

读发生时写尚未完成，二者并发。模型允许把读排在写之前，所以返回 0 仍可能合法；也允许把写排在读之前，所以返回 1 也可能合法。

线性一致性承诺的是**已完成操作不可被后来操作越过**，不是所有请求都按到达机器的纳秒时刻排序。

### 一个常被忽略的优点：局部性

Herlihy 和 Wing 证明了线性一致性具有局部性：整个对象系统线性一致，当且仅当每个对象分别线性一致。

这意味着队列、寄存器和计数器可以独立实现和验证，再组合成一个线性一致的对象系统。这里组合的是**对象操作**，还没有获得跨对象事务的原子性。

### 线性一致性是安全性，不是响应保证

线性一致性只审查已经出现的调用与结果。实现可以因故障而阻塞；“每个正确客户端的请求最终返回”是额外的活性条件。

所以“线性一致”不自动等于低延迟、高可用，也不自动等于副本一定在有限时间内全部同步。

## 三、顺序一致性：大家同意一个顺序，但这个顺序可以不认墙上时间

顺序一致性要求存在一个合法的全序，并保留每个进程自身的程序顺序。与线性一致性相比，它少了跨进程的真实时间约束。

这里的全序是“存在一个能解释全部结果的共同顺序”，不表示每个客户端真的收到了完整日志，也不表示并发实现只能逐条执行。

还是那段历史：

~~~text
真实执行：

A：write(x, 1) ──> 成功
                               B：read(x) ──> 0

顺序一致性的解释：

B 的 read(x)  ──>  A 的 write(x, 1)
~~~

如果 A 和 B 的其他操作不与这个解释冲突，顺序一致性可以把 B 的读排在 A 的写之前。这个全序违背现实中的先后，却保留了两个进程各自的程序顺序。

因此可以用一句非正式等式建立直觉：

~~~text
线性一致性 ≈ 顺序一致性要求的合法全序 + 真实时间顺序
~~~

“≈”提醒我们：正式定义还要处理未完成操作、历史等价和对象规约，不能只看一条排序箭头。

### 为什么“写完后打电话告诉别人”是好例子

A 写完后打电话告诉 B，B 再读取。电话不在存储系统的会话和因果元数据里，但它让外部世界明确知道写先于读。

顺序一致性只保留各进程内部的程序顺序，因此仍可能把 B 的读排在 A 的写之前。线性一致性依据调用与返回区间，禁止这种“时间倒放”。

这个例子说明真实时间保证为什么有业务价值，但**没有证明实现必须使用物理时钟**。系统也可以靠单一 leader、锁或共识日志维护同样的先后关系。

## 四、因果一致性：原因必须先于结果，并发事件不必统一排队

因果一致性只要求所有观察者尊重因果顺序，不要求把所有并发操作塞进同一个全局全序。

经典的“帖子—回复”例子：

~~~text
W1：Alice 发布帖子 P
R1：Bob 读到帖子 P
W2：Bob 发布回复 Q

因果链：W1 → R1 → W2
~~~

回复 Q 是 Bob 读到 P 之后产生的结果。任何已经看到 Q 的观察者，都不能处在一个尚看不到 P 的因果快照中。

这个例子默认帖子没有被合法删除、观察者有权限读取，且“看到”指模型中的可见性。

若业务加入删除、过滤或权限，合法对象规约也要一起修改，不能只凭页面上没显示帖子判定违规。

若 Alice 和 Carol 互不知情地同时发布两篇文章，两次写没有因果关系。副本甲可以显示 Alice 在前，副本乙可以显示 Carol 在前；因果一致性不要求统一这两个并发事件的顺序。

### 它与顺序一致性的关键差别

顺序一致性要求整个历史存在一个大家共同接受的全序；因果一致性只统一有依赖的部分，并允许不同观察者以不同顺序看见并发写。

在标准读写内存模型及兼容定义下，可以写出：

~~~text
线性一致性  ⇒  顺序一致性  ⇒  因果一致性
~~~

箭头只比较**操作历史的安全性约束**：左侧允许的坏历史更少。它不表示左侧一定更可用、更快，也不表示系统自动拥有更新最终交付等活性。

“因果一致性”本身也是一族模型。实际系统还可能另行提供读己之写、单调读、单调写等会话保证；讨论产品时必须查看它究竟追踪了哪些因果边。

### “顺序一致性 ⇒ 因果一致性”有没有争议

在读写寄存器模型里，这条箭头成立。顺序一致性的全序保留程序顺序；读又必须返回该全序中最近的前序写，因此全序也保留读自边。

程序序与读自边的传递闭包正是这里采用的因果序。

争议通常不是这个证明本身，而是人们换了定义域：某些系统只跟踪应用显式声明的因果，某些模型还捆绑最终可见或会话保证，任意对象也未必以寄存器的读自规则定义依赖。

所以本文的箭头是**标准读写寄存器安全性之间的包含关系**。离开这个前提，应重新写出 happens-before、可见性和返回值规约，再判断是否包含，不能照搬箭头。

## 五、最终一致性：它回答的是“后来怎样”，不是“现在怎样”

最常见的非正式表述是：如果不再有新更新，更新经过足够长时间传播后，正确副本最终达到一致状态。

例如只有一次写入：

~~~text
t1：A 在副本 R1 写入 x=1，收到成功
t2：R1 返回 1，尚未收到更新的 R2 返回 0
t3：更新传播到 R2
t4：R1、R2 此后都返回 1
~~~

这段历史不满足线性一致性，因为成功写入后仍有已完成读取返回旧值；只要传播和冲突处理最终使副本收敛，它仍可能满足最终一致性。

### 为什么不能简单写成“因果 ⇒ 最终”

因果一致性限制的是**可见顺序**；最终一致性承诺的是**传播与收敛进展**。一个系统可以同时提供二者，也可以只提供其中一个。

一个线性一致服务可以在某次操作后永久停机，或让一个永不服务请求的内部副本永远落后。它没有产生非法返回值，却未必满足更新最终交付。

反过来，一个系统可以保证所有副本最终相同，却允许收敛前出现新值、旧值来回跳，甚至让某个并发写的业务效果被冲突规则覆盖。它未因此获得因果或线性顺序。

所以，这条链一般没有意义：

~~~text
线性  ⇒  顺序  ⇒  因果  ⇒  最终
~~~

前三项主要在安全性轴上比较，最后一项的“eventual”主要位于活性轴。只有补齐精确定义和运行假设后，才能讨论某个具体系统是否同时满足它们。

### “最终一致性是纯活性”为什么会有争议

“最终一致性”没有唯一、跨文献完全统一的定义。至少有三种常见说法：

1. 只抽取 eventual 条件：停止更新后，副本最终收敛；
2. 从客户端历史定义：某次写最终会对足够晚的操作可见，同时返回值仍须符合对象规约；
3. 从副本定义：把最终交付、收敛和终止组合成 EC，再用强收敛定义 SEC。

第一种说法里的“最终收敛”是活性：任何有限分歧都还能在未来修复。第二、第三种完整模型还可能包含返回值合法性、因果无环或强收敛等安全性。

因此，“最终一致性是纯活性”和“最终一致性也有安全性”并非必然互斥。前者往往只谈 eventual 这一条尾部承诺，后者谈某篇论文给出的完整模型。

若不先报出定义，两句话都容易误导。

Shapiro 等人的 SSS 2011 论文采用第三种拆法：

| 条件 | 含义 | 主要类型 |
|---|---|---|
| 最终交付 | 到达某正确副本的更新最终到达所有正确副本 | 活性 |
| 收敛 | 拥有相同更新集合的正确副本最终达到等价状态 | 带 eventual 的活性表述 |
| 强收敛 | 拥有相同更新集合的正确副本已经处于等价状态 | 安全性 |
| 终止 | 方法调用最终完成 | 活性 |

在这套定义中，SEC = EC + 强收敛。最终交付与强收敛结合后，普通收敛会随之成立；SEC 因而同时含有安全性和活性成分。

即使在 CRDT 文献内部，形式化方式也不完全相同。Shapiro 等人同年的 EATCS 文章把“相同更新集合得到等价状态”列为 correctness 下的 convergence。

SSS 2011 则区分最终 convergence 与立即成立的 strong convergence。

名称会漂移，逻辑结构不会：带“最终”的交付或收敛是活性；相同输入集合必须得到相同状态是安全性。

还要区分两类 CRDT。state-based CRDT 的合并通常依赖半格以及交换、结合、幂等；op-based CRDT 则要求并发操作可交换，并依赖满足前置条件的可靠传递，常见做法是因果传递。

所以，强最终一致性不能被粗暴地塞到“因果一致性更弱一级”的位置。两者一般不可比，也可以组合成 causal+ 等“因果顺序 + 强收敛”模型。

## 六、外部一致性：把真实时间约束提升到事务

本文采用 Spanner 和事务处理文献中的常见用法：

~~~text
外部一致性 ≈ 严格可串行化
           = 可串行化 + 事务真实时间顺序
~~~

可串行化要求已提交事务的整体效果等价于某个串行执行。严格可串行化进一步要求：若 T1 已完成后 T2 才开始，串行序中 T1 必须位于 T2 之前。

这里默认事务具备原子提交；崩溃后的全有或全无通常由恢复和提交协议保证。严格可串行化关注的是并发历史，不能替代全部事务原子性机制。

### “外部一致性 = 严格可串行化”要加什么前提

在 Spanner 和本文的事务语境里，二者可以视为同一保证：先有一个合法事务串行序，再要求它尊重不重叠事务的真实时间。

但“外部一致性”不是一个由 SQL 标准统一定义的隔离级别。Spanner 论文先规定时间戳反映串行序，再用真实时间约束定义 external consistency。

Google Cloud 文档则直接写成“表现得像串行执行，并符合可观察提交顺序”。

两种表述等价的关键，是前者已经把“时间戳反映串行序”作为前提。若只摘出“后来事务的时间戳更大”一句，就会漏掉可串行化这一半。

单有“时间戳按真实时间递增”不够。一个允许写偏斜的系统即使把提交时间戳排得很漂亮，仍然不存在合法事务串行序，因此不满足本文所说的外部一致性。

本文使用“≈”而非脱离语境的恒等号，就是为了保留这个术语边界。后文若简称“外部一致性”，均指 Spanner 语境下的严格可串行化。

### 普通可串行化为什么会允许“时间倒流”

设 x 初值为 0：

~~~text
T1：write(x, 1) ──> COMMIT
                                T2：read(x) ──> 0，COMMIT
~~~

普通可串行化可以把串行序解释成 T2→T1，于是 T2 读到 0。它只要求“存在某个串行序”，不要求这个顺序尊重 T1 已经完成、T2 才开始的事实。

外部一致性禁止这个解释。既然 T1 的完成已经能被外部客户端观察到，T2 就不能在事务串行序中穿越到 T1 之前。

这里说的是**可串行化这一规约允许什么**，不是说所有标称 Serializable 的数据库都会这样返回。许多实现额外保留会话或真实时间顺序，因而实际提供严格可串行化。

单机也不能从定义上自动把可串行化变成严格可串行化；分布式系统也并非注定做不到。决定差异的是历史规约与实现协议，不是机器数量。

因此，外部一致性不是最终一致性那一侧的活性，也不是“跨数据中心一致性”的同义词。它是**事务粒度、带真实时间约束的安全性**。

### 线性一致性与外部一致性究竟是什么关系

二者的精神相同：执行表现得原子，并尊重非重叠调用的真实时间。区别是被原子化的单位不同。

| 模型 | 经典单位 | 要寻找的合法解释 |
|---|---|---|
| 线性一致性 | 单个对象操作 | 尊重真实时间的合法操作序 |
| 外部一致性 | 多操作事务 | 尊重真实时间的合法事务串行序 |

若把整个数据库看作一个抽象对象，把每个事务看作该对象的一次原子操作，外部一致性可以理解为“事务的线性一致性”。

若每个事务都退化成对单个对象的一次读或写，严格可串行化也退化成线性一致性。Herlihy 和 Wing 正是用这个受限关系连接两者。

因此，在数据库 API 的语境里，可以说外部一致性覆盖了线性一致性的单操作特例；但脱离接口粒度，简单问“谁绝对更强”并不严谨。

这里甚至能看到一组表面矛盾的权威表述：Spanner 论文把事务序满足外部一致性称为“等价于线性一致性”。

Google 后来的产品文档又说，外部一致性比线性一致性更强，因为后者不描述事务。

二者并不冲突。前一句把整个事务当成数据库对象的一次操作，于是严格可串行化就是事务接口的线性化。

后一句比较的是 API 表达能力，单对象读写的线性一致性确实没有规定多对象事务。

## 七、为什么“每个键都线性一致”仍救不了转账

设账户 x=100、y=100。事务 T 要从 x 转 50 到 y，最终状态应为 x=50、y=150。

如果系统只保证两个键的操作分别线性一致，却没有把 T 作为跨键原子事务，观察者可能看到：

~~~text
以下各行按真实时间从上到下发生：

R：read(x)  -> 100
T：write(x, 50)
T：write(y, 150)
R：read(y)  -> 150
~~~

两次读各自都能在线性化历史中得到解释，但 R 组合出的快照是 (100, 150)，总额为 250，凭空多出 50。

操作粒度的法庭只能判断每次读写是否合法；它不知道两次写本应属于一个不可分割的转账，也不知道两次读想组成一个一致快照。

事务粒度的法庭会拒绝这个观察：结果既不是转账前的 (100,100)，也不是转账后的 (50,150)，无法解释成读事务与转账事务的某个串行顺序。

这正是“操作由什么组成”与“模型以什么为审判单位”的区别。事务当然由操作组成，但合法性不能只逐个操作判定。

### 局部正确为什么拼不成全局事务正确

线性一致性的局部性保证每个对象的线性化可以组合成对象系统的线性化。

但可串行化和严格可串行化不具有这种逐对象局部性。不同分片可以各自选出合法的局部事务顺序，却在全局形成 T1→T2→T1 的依赖环。

所以，跨分片事务需要全局兼容的并发控制与提交协议。每个分片上的锁表可以是局部的，但同一事务在所有分片持有的锁共同形成一套分布式 2PL 约束。

## 八、一致性与隔离性：不是互不相干，而是两套重叠词汇

工程文档常把复制层的语义称为“一致性”，把并发事务的语义称为“隔离级别”。这个分工有用，但不是形式理论上的绝对边界。

| 讨论传统 | 常见单位 | 典型问题 |
|---|---|---|
| 并发对象/复制一致性 | 单次操作、会话、更新 | 读写按何种顺序可见 |
| 数据库隔离 | 事务 | 并发执行是否等价于允许的事务历史 |
| 二者交界 | 严格可串行化/外部一致性 | 事务既可串行化，又尊重真实时间 |

“一致性管钟表，隔离性管边界”只能当助记句，不能当定义。因果一致性并不依赖墙上时间；可串行化本身也不保留真实时间。

更准确的说法是：两套术语来自不同研究传统，都在限制可观察历史；外部一致性把事务隔离的最高目标与外部真实时间连接起来。

还要避免把所有数据库隔离名称排成一条无条件成立的直线。Read Committed、Repeatable Read 的具体语义会随 SQL 标准和产品变化。

Snapshot Isolation 另有写偏斜，其与各家 RR 的关系也不能只看名字。

本文需要的稳定结论只有一个：

~~~text
严格可串行化（外部一致性） ⇒ 可串行化
~~~

反向不成立，因为普通可串行化可以选择违背真实时间的串行序。

顺便提醒：ACID 中的 C 通常指业务完整性约束。它与这里讨论的副本/并发一致性不是同一个 C；事务机制提供执行框架，业务仍需定义并维护不变量。

## 九、真实时间语义不等于物理时钟实现

这是整组概念中最容易从“定义”滑向“实现”的地方。

真实时间顺序只说：

> 若 A 的响应发生在 B 的调用之前，则合法顺序必须有 A→B。

它是客户端可观察历史上的约束，不要求系统把 UTC 时间写进日志。以下机制都可能在没有跨节点同步物理钟的情况下实现这一语义：

- 单一排序点用递增序号处理请求，并在状态生效后才响应；
- 单版本数据库在正确恢复与原子提交的前提下，用严格两阶段锁把冲突顺序和提交可见性锁住；
- 复制状态机用共识日志排序写入，再用 leader 或 quorum 保证读到足够新的状态。

这些方案依赖通信、锁、多数派协调或中心化瓶颈，但它们证明了：**物理时钟不是线性一致性或外部一致性的逻辑必要条件。**

### 带外通信说明“为什么需要实时序”，不说明“只能用钟”

A 提交转账后通过电话告诉 B，B 随后查询。数据库看不见电话携带的因果元数据，但调用—返回区间已经形成客观先后。

外部一致性保证 B 的事务不会被排到 A 之前，因此非常适合承接系统边界外建立的先后预期。

然而系统不必检测那通电话。只要 A 的提交在响应前已进入一个可靠的全局顺序，后来到达的 B 请求就无法越过它。锁、leader 和共识都能做到这一点。

逻辑时钟本身只能从系统内消息推导 happens-before，不能把“凌晨 2 点”映射成物理时刻。

但由此不能推出“任何实时一致系统都必须用物理钟”。共识协议可以用逻辑序号实现实时一致性。

Lamport 在 1978 年讨论电话例子时其实给了两条路：让后一个请求显式携带前一个请求的时间戳，把外部因果重新带回系统；或者使用满足强时钟条件的物理钟。

因此，那篇论文证明的是“只看原有系统内消息的逻辑时钟无法恢复未知的外部因果”，不是“所有实时顺序只能由物理钟实现”。

客户端因果令牌、统一排序协议和物理时钟，是在不同架构下弥合裂缝的办法。

### 争议的分界线：你需要“顺序”，还是需要“时间”

如果 API 只承诺“先完成的操作不能被后开始的操作越过”，系统只需维护可靠的相对顺序，不需要知道现在是 UTC 几点。

如果 API 还承诺“读取 02:00:00 的全球快照”，时间戳就必须和物理时间有可信映射。此时需要有界物理时钟、集中式时间权威，或语义等价的时间服务。

若系统既不要单一全球 sequencer，又希望各分片独立分配与真实时间兼容的时间戳，就更有理由引入 TrueTime 一类机制。

所以，“实时一致性需要物理时钟”在第一种需求下是错的，在后两种更强需求下可能是工程前提。争论往往来自把这三种 API 混成一句话。

### 那么 Spanner 为什么需要 TrueTime

Spanner 的目标不只是找到某种外部一致性的实现，而是在全球分片、MVCC 和高并发下获得**与真实时间兼容、全局可比较的事务时间戳**。

若所有事务都经过一个全局 sequencer，当然可以得到顺序，却会引入额外通信和扩展瓶颈。若所有强读都获取读锁，也能保住顺序，却会阻塞写。

TrueTime 返回一个保证包含真实时间的不确定区间：

~~~text
TT.now() = [earliest, latest]
~~~

在原始 Spanner 协议中，读写事务的提交时间戳 s 不小于协调者当时的 TT.now().latest，也不小于参与者给出的 prepare 时间戳。

向外暴露提交前，协调者还要等待 TT.after(s) 成立；等价地，新一次 TT.now().earliest 已经超过 s，系统能确定 s 已成为过去。这两步通常称为 timestamp selection 与 commit wait。

推导链缺一不可：commit wait 保证 s1 小于 T1 向客户端返回的绝对时刻。T2 在此后才开始，其时间戳选择又发生得更晚。

TT.now().latest 不小于选择时的真实时刻，而 s2 又不小于 TT.now().latest，因此 s2 > s1。

这样，MVCC 版本顺序同时兼容事务串行序和外部观察到的真实时间顺序。

TrueTime 的工程收益还包括：不经过单一全球排序点就产生恰当时间戳，并让跨分片强读和只读事务选择一致快照，尽量不阻塞写。

Google 的文档也明确指出，传统单版本数据库使用严格 2PL 就能提供外部一致性。TrueTime 是 Spanner 为“全球分布式 MVCC + 高效快照读”选择的答案，不是外部一致性的定义。

“精确读取某个物理时刻的全局快照”则是另一项更强的时间 API 需求。它确实需要把数据库时间戳与墙上时间建立可信映射。

但这不能反过来证明所有外部一致系统都必须依赖物理钟。

## 十、把五个概念放回正确的地图

| 模型 | 经典单位 | 核心约束或承诺 | 真实时间 | 性质分解 |
|---|---|---|---:|---|
| 线性一致性 | 对象操作 | 尊重真实时间的合法全序 | 是 | 安全性 |
| 顺序一致性 | 对象操作 | 程序顺序下的合法全序 | 否 | 安全性 |
| 因果一致性 | 操作/更新 | 因果偏序 | 否 | 安全性 |
| 外部一致性 | 事务 | 串行序 + 事务真实时间 | 是 | 安全性 |
| 最终一致性 | 更新/副本状态 | 最终交付与收敛，依定义而异 | 否 | eventual 核心是活性 |
| 强最终一致性 | 更新/副本状态 | EC + 强收敛 | 否 | 安全性 + 活性 |

这张表展示的是本文选定的经典口径，不是说模型名称天生只能占据一格。读表时要注意三点。

第一，在线性、顺序、因果采用兼容的标准读写定义时，可以比较操作历史：

~~~text
线性一致性  ⇒  顺序一致性  ⇒  因果一致性
~~~

第二，在事务历史中可以比较：

~~~text
外部一致性（严格可串行化）  ⇒  可串行化
~~~

第三，最终一致性位于传播与收敛轴。它可以和因果一致性组合成“因果 + 最终交付”，也可以与 CRDT 的强收敛组合成强最终一致性。

### 遇到一个新名词时，按五个问题判断

1. 模型审判的是单个操作、会话、事务，还是副本状态？
2. 它禁止某种有限坏历史，还是承诺某件事最终发生？
3. 它保留程序序、因果序、全局全序，还是事务串行序？
4. 它是否要求尊重不重叠调用的真实时间？
5. 它是否另行承诺终止、更新交付、可用性或收敛？

只要这五个问题答清楚，大多数“强一致、弱一致、最终一致”的术语争论都会消失。

## 十一、最后回答开场的三个问题

**为什么写成功后的旧读违反线性一致性，却可能满足顺序一致性？**

因为线性一致性保留跨客户端真实时间，顺序一致性只需找到保留各自程序顺序的全局全序。

**为什么每个账户都线性一致，转账仍可能被看见一半？**

因为线性一致性以操作为单位；跨对象事务还需要原子性与全局可串行化，后者不能靠每个键各自正确自动拼出来。

**为什么永远不响应的系统仍可能线性一致？**

因为线性一致性是安全性，只限制已经返回的结果；请求最终完成属于活性。

最终，可以把全文压缩成一句话：

> **线性、顺序、因果比较操作历史允许怎样排序；外部一致性要求事务按兼容真实时间的串行序出现。**
>
> **最终一致性的 eventual 核心承诺更新最终传播并收敛。前四者抽出的核心是“坏事不能发生”，eventual 回答“好事最终发生”；完整模型仍可能把两类条件组合起来。**
