## 摘要

ACID 和 CAP 经常被放在一起讲，缩写也很相似，还共享一个字母——但这种表面上的重合，几乎没有反映它们真正讨论的是同一类问题。ACID 是事务系统内部关于*恢复与并发控制*的契约；CAP 则是在不可靠网络中复制单个*寄存器*时得到的不可能性结果。两者中的 “C” 含义不同。本文精确定义这两个框架，考察 PostgreSQL、MySQL/InnoDB 和 SQLite 如何用三种截然不同的物理设计兑现 ACID 契约，分析法定人数、Gossip、Paxos 和 Raft 如何处在 CAP 设计空间的不同位置，进而论证：这两个框架由同一种稀缺资源统一起来——**协调**。可串行化和线性一致性，都要用往返通信、阻塞和争用来购买。近年的理论——高可用事务、不变量合流以及 CALM 定理——精确告诉我们，哪些保证可以不付出这笔代价，而这条边界正是本领域最有实践价值的结论。

**适合的读者。** 这是一篇面向已经熟悉事务和复制机制的工程师的综合性文章：它是高级工程师读物，不是入门介绍。文章假定你知道锁和副本是什么，会快速掠过标准材料（两阶段锁、ANSI 隔离级别），把篇幅用在标准材料错误、不完整或容易被误用的地方。想先建立基础的读者，可以从 Kleppmann 的《Designing Data-Intensive Applications》开始，之后再回来读本文。

## 1. 两组缩写，一种资源

理解这个主题的一个好入口，是观察这两个框架*实际上都在配给什么*。

可串行化要求并发事务产生的结果等价于某个串行顺序。要做到这一点，事务必须通过锁、提交时验证或时间戳排序等方式了解彼此。线性一致性要求一个分布式寄存器表现得仿佛所有操作都在真实时间中的某个瞬间发生。要做到这一点，副本必须通过法定人数交集、领导者或共识轮次等方式了解彼此。

在这两种情况下，被购买的东西其实相同：**并发参与者之间关于事件顺序的共识**。隔离级别是一张针对第一笔购买提供不同折扣的菜单；一致性模型则是针对第二笔购买提供不同折扣的菜单。

不过，标题中的这个说法需要加一个限定，而且这个限定很重要。说协调是一种货币，是因为被购买的东西始终是对事件顺序达成共识；但这张账单至少有三种不能相互替代的面额：

- **延迟**——一个操作得到确认前所需的往返通信次数。
- **可用性**——无法达成共识时必须拒绝的请求。
- **争用下的吞吐量**——同一数据项上的冲突操作必须串行化，而再多硬件也无法消除这一点。

第三种面额最容易被遗忘，却也最常成为真实系统的上限；§8.2 会直接讨论它。一个设计可以节省其中一种面额，却在另一种面额上付出沉重代价。因此，“它到底有多一致？”是一个没有定义好的问题；“每项保证要以哪一种面额、付出什么代价？”才是一个好问题。

严谨的工程师要做的，不是购买能买到的最强保证，也不是条件反射地购买最便宜的保证，而是判断应用的不变量究竟哪些需要协调，然后只购买刚好足够的协调成本。下面的全部内容，都是对这条主张的展开。

## 2. ACID 作为形式化契约

### 2.1 起源，以及四个字母为何并不正交

这个缩写源自 Härder 和 Reuter [1983]，它把 Jim Gray 在 IBM、后来在 Tandem 开展的一系列工作形式化了。ACID 是一个助记词，不是一条定理；其中四个性质位于系统的不同层次：

| 字母 | 它实际上是什么 | 由什么实现 |
|---|---|---|
| **A**tomicity（原子性） | 一种*日志与恢复*性质 | 撤销日志、回滚、ARIES 的撤销阶段 |
| **C**onsistency（一致性） | 一种*应用层*性质 | <code>CHECK</code>、<code>FOREIGN KEY</code>、<code>UNIQUE</code>、应用逻辑 |
| **I**solation（隔离性） | 一种*并发控制*性质 | 2PL、MVCC、OCC、SSI |
| **D**urability（持久性） | 一种*存储*性质 | 预写式日志、<code>fsync</code>、复制 |

一致性是其中格格不入的一项。数据库可以执行声明式约束，但“在这个业务规则下，两个表之间的账户余额不能变成负数”这一不变量，只有在应用正确编写事务并请求足够的隔离级别时才能得到维护。Härder 和 Reuter 很可能只是为了拼出 ACID 这个单词，才把 C 放了进来。这不是吹毛求疵：把 ACID 的 C 与 CAP 的 C 混为一谈，是这个领域产生混乱的最大源头，而 §5 将专门把它们拆开。

还要注意，原子性和持久性虽然总被连在一起提及，却是可以分开的。一个系统可以具有原子性但不具备持久性（例如支持回滚、却不做持久化的内存数据库）；也可以具有持久性但不具备原子性（例如不带事务边界、直接写入的追加式日志）。真实引擎用同一份日志实现二者，这正是它们经常被混为一谈的原因。

### 2.2 可串行化理论

隔离性的形式化目标是**可串行化**：如果一个交错执行的调度，其效果等价于对同一组事务进行*某种*串行执行，那么这个调度就是可串行化的。“某种”很重要——系统不必复现事务到达的顺序，只需等价于某个合法顺序即可。这正是可串行化与线性一致性的区别：后者*确实*要求遵守真实时间顺序。

判断视图可串行化是 NP 完全问题，因此实际系统通常追求更严格、但可处理的**冲突可串行化**。当两个操作属于不同事务、访问同一个数据项，且至少有一个是写操作时，它们就会冲突。构造一个优先图：每个事务对应一个节点；只要事务 <code>Ti</code> 的某个操作先于事务 <code>Tj</code> 的冲突操作，就添加一条 <code>Ti → Tj</code> 的边。当且仅当这个图无环时，该调度才是冲突可串行化的；图的任意一个拓扑序，都是等价的串行顺序。

每一种实际的并发控制机制，本质上都是保持这个图无环的一种策略：

- **两阶段锁（2PL）**——在增长阶段获取锁，在收缩阶段释放锁；一旦开始释放，就不能再获取新锁。定理保证：2PL 产生的任何调度都具有冲突可串行化性。代价是死锁，因此必须通过检测（等待图）或预防（wound-wait、wait-die）来处理。
- **时间戳排序**——为每个事务分配时间戳；任何可能产生反向边的操作都将触发中止。
- **乐观并发控制（OCC）**——在私有工作区中执行，在提交时针对并发提交者进行验证，发生冲突就中止。低争用时成本低，高争用时则会变得不稳定（§8.2）。
- **多版本并发控制（MVCC）**——保留旧版本，使读者不会阻塞写者，写者也不会阻塞读者。MVCC 单独只能提供快照隔离，*不能*提供可串行化；§2.3 将讨论这道鸿沟。

另有一条相互正交的层级，描述事务中止时会发生什么：

- **可恢复（Recoverable）**——事务只有在它所读取的写入均已提交之后才能提交。否则，一旦被读取的事务提交后又需要回滚，读取者的提交就必须被撤销，而这不可能做到。
- **避免级联中止（ACA）**——事务只能读取已提交数据，因此一个事务中止不会迫使其他事务中止。
- **严格（Strict）**——任何事务都不能读取或覆盖由尚未提交事务写入的数据项。严格性使得系统可以利用前镜像进行物理撤销。

**严格 2PL**——持有所有锁直到提交或中止——产生既冲突可串行化、又严格的调度，这就是它为何主导了第一代关系数据库引擎。MVCC 系统则通过另一种方式实现可恢复性：读者按设计只能看到已提交版本。

### 2.3 ANSI 层级存在缺陷

SQL-92 标准按照禁止哪些异常来定义隔离级别：

| 级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| Read uncommitted（读未提交） | 可能 | 可能 | 可能 |
| Read committed（读已提交） | 禁止 | 可能 | 可能 |
| Repeatable read（可重复读） | 禁止 | 禁止 | 可能 |
| Serializable（可串行化） | 禁止 | 禁止 | 禁止 |

Berenson、Bernstein、Gray、Melton 以及 O'Neil 两位作者 [1995] 指出，这些定义既有歧义又不完整。问题有两个：

**这些现象存在歧义。** 每种现象都可以按“宽松”方式理解（异常结果确实发生了），也可以按“严格”方式理解（发生了*可能*产生该异常的交错）。按严格解释，禁止这三种现象确实意味着可串行化；按宽松解释，则不意味着。标准没有说清楚应该采用哪一种解释。

**快照隔离在这个层级中无处安放。** 在 SI 下，事务从开始时取得的一致快照中读取数据，只有在没有并发事务写入它所写的任何数据项时才允许提交（先提交者获胜）。SI 禁止脏读、不可重复读和幻读——因此按照 ANSI 表格，它应该是“可串行化”的；但事实明确表明它并不可串行化。

SI 允许出现的异常是**写偏斜**。经典例子如下：

~~~text
不变量：至少有一名医生必须处于值班状态。

初始状态：Alice on_call = true，Bob on_call = true

T1（Alice）                         T2（Bob）
------------------------             ------------------------
SELECT count(*) WHERE on_call
  -> 2                              SELECT count(*) WHERE on_call
                                      -> 2
UPDATE Alice SET on_call=false
                                    UPDATE Bob SET on_call=false
COMMIT                              COMMIT

最终状态：没有医生值班。没有发生写-写冲突。
~~~

两个事务读取了相互重叠的数据，却写入了*互不重叠*的数据，因此没有触发写-写冲突，也没有任何一个事务中止。不变量已经被破坏，而数据库毫无察觉。所有“读取—检查—再写入”一个集合的模式——跨两个账户的余额约束、座位库存、应用代码执行的唯一性检查、资源配额——都可能出现这个问题；而且在许多生产系统中，它就发生在默认隔离级别下。

写偏斜之所以值得准确地内化，是因为低并发测试看不出它，而且它在任何时刻都不会抛出错误。

### 2.4 Adya 的形式化方法，以及异常的形状

Berenson 等人仍然用被禁止的交错来定义隔离级别，这使定义绑定于某一种实现方式。Adya 的博士论文 [1999] 则使用包含三种边的**直接序列化图**，给出了与实现无关的定义：

- **ww（写依赖）**——<code>Ti</code> 写入 <code>x</code> 的一个版本，<code>Tj</code> 写入下一个版本。
- **wr（读依赖）**——<code>Ti</code> 写入一个版本，<code>Tj</code> 读取这个版本。
- **rw（反依赖）**——<code>Ti</code> 读取 <code>x</code> 的一个版本，<code>Tj</code> 写入下一个版本。

隔离级别对应于这个图中哪些环被禁止。可串行化禁止所有环。上面的写偏斜例子，恰好是一个两节点环，并且两条边都是 rw：

~~~text
图 1——写偏斜作为依赖环

                        rw
              +-------------------->
        T1                              T2
              <--------------------+
                        rw

  T1 --rw--> T2：T1 读取了 Bob 的行；随后 T2 写入了该行
  T2 --rw--> T1：T2 读取了 Alice 的行；随后 T1 写入了该行

  不存在 ww 边，因为两个事务的写集合互不重叠；这正是
  快照隔离的“先提交者获胜”检查没有触发的原因。
~~~

Fekete 等人 [2005] 提出、Cahill、Röhm 和 Fekete [2008] 使用的一般定理，表述的是一个*必要性*方向：**快照隔离下每一个不可串行化的执行，都包含一个由两条连续 rw 边构成的环，且出边所指向的那个事务先提交。** 这种结构是必要条件，但不是充分条件——有些包含该结构的执行其实完全可以串行化。这种不对称性并非脚注；它正是 PostgreSQL 的 SSI 会产生误报式中止的原因，也是 §3.2 中重试循环之所以是必需的、而非一种防御性写法的原因。

~~~text
图 2——SSI 监视的危险结构

              rw                    rw
     Tin ------------> Tpivot ------------> Tout
                                              |
                                       先提交

  这是 SI 异常的必要条件，不是充分条件。
  SSI 一旦发现该结构就会中止其中一个参与者，
  因此它是保守的：某些被中止的事务其实是可串行化的。
~~~

现代验证工具——尤其是 Jepsen 的 Elle 检查器 [Kingsbury & Alvaro 2020]——正是使用这种形式化方法，从黑盒观测中推断异常。

### 2.5 持久性取决于故障模型

“已提交的数据能够存活”这句话，除非先说明它要在什么故障下存活，否则没有意义。可以粗略地排成如下阶梯：

| 保证 | 能经受什么故障 | 常见机制 |
|---|---|---|
| 进程级持久性 | 应用崩溃 | 向页缓存执行 <code>write()</code> |
| 机器级持久性 | 操作系统崩溃、断电 | 向稳定介质执行 <code>fsync()</code> / <code>fdatasync()</code> |
| 介质级持久性 | 磁盘故障 | RAID、校验和、复制 |
| 站点级持久性 | 机架或数据中心故障 | 跨可用区同步复制 |
| 地理级持久性 | 区域性中断 | 跨区域复制、提交等待 |

每上升一级，延迟大致要增加一个数量级。这就是 ACID 的 D 悄悄变成分布式系统问题的地方——也正是在这里，CAP 开始适用于那些自称“一个 ACID 数据库”的系统。§5.4 会回到这个问题。

持久性还依赖一些硬件和内核并不总能遵守的假设。**fsyncgate** 事件（2018）是一个典型例子：在 Linux 上，一次失败的 <code>fsync()</code> 可能清除错误状态，并把受影响的页面标记为干净；于是，之后对 <code>fsync()</code> 的*重试*会返回成功，但数据其实已经永久丢失。PostgreSQL 的修复方式是把 <code>fsync()</code> 失败视为 <code>PANIC</code>，强制进程崩溃，并从 WAL 完整恢复，而不是相信一个可能撒谎的内核。对把写入确认到易失缓存中的磁盘、虚拟化块设备和网络文件系统，也存在类似危险。

## 3. 单节点引擎如何兑现 ACID 契约

### 3.1 共同基础：ARIES

几乎所有具备持久性的事务引擎，都是 **ARIES** [Mohan 等，1992] 的某种变体。准确陈述它的规则很有价值，因为 PostgreSQL、InnoDB 和 SQLite 之间的差异，最好理解为在这个框架内做出的不同选择。

**预写式日志规则。** 修改后的数据页写入磁盘之前，描述这次修改的日志记录必须已经位于稳定存储中。事务被报告为已提交之前，它的提交记录必须已经位于稳定存储中。

**缓冲区管理策略决定需要哪种日志。** 有两条相互独立的轴：

| | **Force**（提交时刷入脏页） | **No-force**（不刷） |
|---|---|---|
| **No-steal**（永不刷入未提交页） | 不需要 undo，也不需要 redo——但性能很差 | 只需要 redo |
| **Steal**（可以刷入未提交页） | 只需要 undo | **undo + redo** |

ARIES 选择的是**偷取 + 不强制刷页（steal + no-force）**这一性能最高的角点，因此同时需要 undo 和 redo 信息。Steal 允许缓冲池在内存有压力时驱逐任意页面；No-force 则把提交变成一次很小的顺序日志写入，而不是分散的随机页面写入。

**恢复分为三遍：**

1. **分析（Analysis）。** 从最近一次检查点向前扫描，重建脏页表（哪些页面可能有尚未刷出的修改，以及这些修改从哪个 LSN 开始）和事务表（哪些事务当时正在执行）。
2. **重做（Redo）——“重演历史”。** 从最早的脏页 LSN 开始，重放*所有*已经记录的修改，包括那些随后会被回滚的事务所做的修改。这一步反直觉，却不可或缺：它恢复崩溃前页面的准确状态，使撤销可以在一个定义明确的起点上进行。每页的 LSN 提供幂等性——如果 <code>page.pageLSN >= record.LSN</code>，说明修改已经存在，就跳过它。
3. **撤销（Undo）。** 回滚失败者，为每一项被撤销的动作写入**补偿日志记录（CLR）**。CLR 携带一个指向下一个待撤销记录的 <code>UndoNxtLSN</code> 指针，因此即使恢复过程中再次崩溃，也不会重复撤销已经完成的工作。这样，撤销就变得幂等且可重启；没有 CLR，恢复期间的反复崩溃可能破坏数据库。

下面的一切，都是这个主题的变体。

### 3.2 PostgreSQL

**版本存储：在堆表中。** PostgreSQL 通过把每一个行版本都保留在表自己的堆表中来实现 MVCC。每个元组头部带有 <code>xmin</code>（创建它的事务）和 <code>xmax</code>（删除或替换它的事务）。一个 <code>UPDATE</code> 在物理上表现为插入一个新元组，并在旧元组上做标记。

**快照与可见性。** 一个快照基本上是三元组 <code>(xmin, xmax, xip_list)</code>：仍在运行的最老事务、下一个尚未分配的 XID，以及当前正在执行的 XID 集合。如果一个元组的 <code>xmin</code> 在快照之前已经提交，并且它的 <code>xmax</code> 不存在，或属于快照不可见的事务，那么该元组对这个快照可见。提交状态存放在提交日志（<code>pg_xact</code>，过去称为 CLOG）中，每个事务占两 bit；随后又会把它缓存回元组头部，作为*提示位（hint bits）*，避免反复查询 CLOG。

**这种设计的后果，构成了 PostgreSQL 的全部运维性格。** 回滚几乎不需要成本：在 CLOG 中把 XID 标记为中止即可，然后停止；之前的版本已经存在，并会立即重新成为当前版本。但清理工作被推迟了，由此产生：

- <code>VACUUM</code>：回收死亡元组并更新空闲空间映射表。没有它，表和索引会无限膨胀。
- **事务 ID 回绕。** XID 是 32 位的，并使用模 <code>2³²</code> 算术比较；比较窗口以 <code>2³¹</code> 为半径：落后当前值的 <code>2³¹</code> 个 XID 被视为过去，领先当前值的 <code>2³¹</code> 个被视为未来。因此，元组必须在创建它的 XID 脱离这个窗口、开始看起来像“未来”之前被冻结。防回绕 vacuum 没有商量余地，而且在超大表上可能造成明显的运维干扰。
- 长事务会拖住全局 vacuum 地平线，因此报表会话中一个被遗忘的 <code>BEGIN</code>，就可能让整个集群产生膨胀。

**隔离级别。** PostgreSQL 实际提供三个有效级别（请求 <code>READ UNCOMMITTED</code> 时，由于 MVCC 在结构上不可能出现脏读，实际会得到读已提交行为）：

- **<code>READ COMMITTED</code>（默认）**——*每条语句*都取得一个新快照。在同一个事务中，两次相同的 <code>SELECT</code> 可能返回不同的行。如果 <code>UPDATE</code> 发现某行被并发修改，它会针对新版本重新评估 <code>WHERE</code> 条件（“EvalPlanQual”），这是一个很隐蔽、却常常令人意外的来源。
- **<code>REPEATABLE READ</code>**——真正的快照隔离：整个事务只使用一个快照，先更新者获胜，失败者收到 <code>40001 serialization_failure</code>。注意，它比 ANSI 的可重复读更强：幻读不可能发生。但它仍然允许写偏斜。
- **<code>SERIALIZABLE</code>**——**可串行化快照隔离（SSI）**，基于 Cahill、Röhm 和 Fekete [2008]，于 PostgreSQL 9.1 发布 [Ports & Grittner，2012]。

SSI 值得仔细研究，因为它是 §2.4 依赖图理论最清晰的生产实现。它在快照隔离上运行，同时额外跟踪 rw 反依赖，寻找图 2 中的结构。读操作通过 **SIREAD 锁**记录；它们其实根本不是锁：不会阻塞任何操作，只会标记读取过的内容，包括页级或元组级粒度的谓词范围。一旦危险结构形成，就会中止一个事务，并返回序列化失败。

由此得到的性质包括：

- 读者永远不会阻塞，写者也不会阻塞读者——保留了 SI 的性能特征。
- 因为危险结构是必要而非充分条件（§2.4），检查是**保守的**：一些被中止的事务其实本来可以串行化。**应用必须实现重试循环。** 这不是可选项，而是 API 的一部分。

只读事务有时可以被证明是安全的（“安全快照”优化），随后便能零开销运行；这正是 PostgreSQL 提供 <code>SET TRANSACTION READ ONLY DEFERRABLE</code> 的原因。

§5.2 有一个容易漏掉、却很重要的限制：**热备库上无法使用 <code>SERIALIZABLE</code>。** SSI 的冲突检测需要一些不会传播给副本的信息，因此 PostgreSQL 会直接拒绝这个请求，并返回 <code>ERROR: cannot use serializable mode in a hot standby</code>，同时提示改用 <code>REPEATABLE READ</code>。因此，把只读负载卸载到副本之后，最多只能运行在快照隔离下——无论主库配置得多强，都是如此。

**持久性。** WAL 的同步级别可以配置：

| <code>synchronous_commit</code> | 提交在何时返回 | 会丢失什么 |
|---|---|---|
| <code>off</code> | WAL 仍在缓冲区中 | 崩溃时最近提交的事务，最多丢失 <code>3 × wal_writer_delay</code> 的时间窗口 |
| <code>local</code> | 本地 WAL 已执行 <code>fsync</code> | 本地磁盘故障 |
| <code>remote_write</code> | 备库已经执行 <code>write()</code> 写入 WAL | 备库操作系统崩溃 |
| <code>on</code>（默认） | 备库已经对 WAL 执行 <code>fsync</code> | 备库磁盘故障 |
| <code>remote_apply</code> | 备库已经*重放* WAL | —（同时使备库具备读己之写语义） |

<code>full_page_writes</code> 通过在检查点之后首次修改某个页面时记录该页面的完整镜像，来防止页面撕裂；这是 InnoDB 双写缓冲区的另一种实现方式。PostgreSQL 还通过 <code>PREPARE TRANSACTION</code> 为外部协调者提供两阶段提交。

注意，表格的最后三行其实是一个“ACID 数据库”内部的*分布式系统设置*。CAP 正是在这里接缝而入。

### 3.3 MySQL / InnoDB

**版本存储：撤销日志。** InnoDB 采取了相反的路径。聚簇索引中的每一行都带有 <code>DB_TRX_ID</code>（最后修改该行的事务）和 <code>DB_ROLL_PTR</code>（指向撤销日志的指针）。读视图沿着撤销链向后遍历，重建它有权看到的版本。索引中的当前行始终是最新版本。

这种取舍与 PostgreSQL 完全对应，只是痛点换了位置：

- 回滚是*真正的物理工作*——必须反向应用撤销记录。
- 没有 <code>VACUUM</code>，但有 purge 线程；长事务会钉住撤销记录，使**历史列表长度**无限增长。故障表现不再是堆膨胀，而是 undo 表空间增长和读性能下降；但根因相同，都是一个老旧的开放事务。

**物理布局会影响锁。** 数据行位于主键 B+ 树中（即索引组织表）；二级索引存储主键值，因此一次非覆盖式二级索引查找还需要进行第二次遍历。关键在于，**InnoDB 锁的是索引记录，不是行。** 这就是为什么一个索引计划糟糕的查询，锁住的数据可能远多于它表面上访问的数据。

锁的类型包括：

- **记录锁（Record lock）**——加在一条索引记录上。
- **间隙锁（Gap lock）**——加在索引记录*之间*的开区间上，用于阻止插入。
- **临键锁（Next-key lock）**——记录锁加上其前面的间隙锁。这是 <code>REPEATABLE READ</code> 下的默认行为，也是 InnoDB 通过锁定读阻止幻读的方式。

**InnoDB 默认的 <code>REPEATABLE READ</code> 具有两副面孔，必须明确警告。** 普通 <code>SELECT</code> 从事务快照中执行*一致性非锁定读*；但 <code>SELECT ... FOR UPDATE</code>、<code>SELECT ... LOCK IN SHARE MODE</code>、<code>UPDATE</code> 和 <code>DELETE</code> 执行的是*锁定读*，看到的是**最新已提交版本**，而不是事务快照。后果如下：

~~~sql
-- 会话 A，REPEATABLE READ
BEGIN;
SELECT COUNT(*) FROM t WHERE status = 'new';   -- 返回 5（快照）
                                                -- 会话 B 插入一行并提交
UPDATE t SET status = 'done' WHERE status = 'new';  -- 影响 6 行！
SELECT COUNT(*) FROM t WHERE status = 'done';  -- 现在看到 6
~~~

此外，与 PostgreSQL 不同，InnoDB **不会中止并发更新的失败者**。它会先阻塞；锁释放后，再重新读取并应用到新版本。因此，单条 <code>UPDATE t SET n = n + 1</code> 是安全的；但跨两个语句的读—改—写，如果读取时没有使用 <code>FOR UPDATE</code>，就可能悄悄丢失更新。

**InnoDB 中的 <code>SERIALIZABLE</code> 不是 SSI。** 它是在 <code>REPEATABLE READ</code> 的基础上，让每个普通 <code>SELECT</code> 隐式执行 <code>LOCK IN SHARE MODE</code>——实质上是对索引空间使用严格两阶段锁，并用临键锁覆盖幻读。这确实是可串行化的，但属于悲观方案：你应当预期阻塞和死锁，而不是乐观重试。于是，这两个引擎位于经典光谱的两端，应用层的后果完全不同：PostgreSQL 要求重试循环，InnoDB 则要求遵守锁顺序并处理死锁。

**持久性，以及两份日志的问题。** InnoDB 有 redo log；服务器层还有用于复制和时间点恢复的 binary log。这两份日志必须保持一致——一个事务只出现在其中一份日志中，就会成为正确性故障，并最终表现为副本分叉。MySQL 通过**内部 XA 两阶段提交**解决它：先在 InnoDB 中准备（刷出 redo），再写入 binlog，最后在 InnoDB 中提交。组提交会把并发事务的 <code>fsync</code> 批量合并，以使这笔成本可以承受。

相关开关包括：

- <code>innodb_flush_log_at_trx_commit</code>——<code>1</code> 表示每次提交都写入并执行 <code>fsync</code>（ACID）；<code>2</code> 表示每次提交写入操作系统页缓存，大约每秒执行 <code>fsync</code> 一次（可以经受进程崩溃，但经受不了断电）；<code>0</code> 表示两者都延后。
- <code>sync_binlog</code>——<code>1</code> 表示每次提交都对 binlog 执行 <code>fsync</code>。在宣称支持 ACID 的同时，把其中任何一个开关设为非持久化值，是一种常见而后果严重的错误配置。

**双写缓冲区。** InnoDB 把一个页面写入最终位置之前，会先把它写入一块连续的临时区域并执行 <code>fsync</code>。如果崩溃导致原位置的页面撕裂，恢复时就从双写副本中重建它。它解决的问题与 PostgreSQL 的 <code>full_page_writes</code> 相同，只是成本曲线不同：前者固定带来 2 倍的页面写放大；后者则在每个检查点之后可能出现 WAL 体积尖峰。

### 3.4 SQLite

SQLite 最值得借鉴，因为它几乎不需要并发控制机制，却取得了比前面两个系统*更强的*隔离保证。它的机制很简单：**整个数据库一次只允许一个写者。** 由于所有写操作在构造上已经被完全排序，而读者看到的是一致快照，SQLite 的隔离性是通过设计直接获得的可串行化，而不是依靠某种复杂算法。

**回滚日志模式**（经典默认模式）是一种*撤销式*设计：

1. 获取 <code>RESERVED</code> 锁，把即将修改的每个页面复制到 <code>&lt;db&gt;-journal</code>。
2. 对日志以及它的目录项执行 <code>fsync</code>。
3. 将锁升级为 <code>EXCLUSIVE</code>，原地修改数据库文件。
4. 对数据库文件执行 <code>fsync</code>。
5. 通过删除或清零日志头部来提交。

恢复很简单：打开数据库时如果发现日志存在，就把其中的页面复制回去。锁会按 <code>UNLOCKED → SHARED → RESERVED → PENDING → EXCLUSIVE</code> 的顺序升级；其中 <code>PENDING</code> 会阻止新读者进入，从而避免它们饿死正在等待的写者。

**WAL 模式**（自 3.7.0、2010 年起）是一种*重做式*设计，它反转了并发图景：

- 修改后的页面追加写入 <code>&lt;db&gt;-wal</code>，而不是原地写入。
- 共享内存索引 <code>&lt;db&gt;-shm</code> 把页号映射到 WAL 中该页面最新的帧。
- 每个读者在开始时记录一个结束标记，只读取不超过该标记的帧——这是真正的快照隔离。
- **一个写者和多个并发读者可以同时前进**，这正是选择 WAL 模式的主要理由。
- 检查点会把 WAL 帧转移回主数据库文件。

生产环境中有两个陷阱尤其容易踩中：

**延迟事务与快照升级失败。** 普通的 <code>BEGIN</code> 是延迟的：执行第一条语句之前不会取得锁。一个先读后写的事务随后必须“升级”；如果期间另一个写者已经提交，SQLite 就会返回 <code>SQLITE_BUSY_SNAPSHOT</code>——这是 <code>SQLITE_BUSY</code> 的扩展结果码——因为事务快照已经过时，无法再扩展。对于这种情况，不会调用 busy handler，因此 <code>busy_timeout</code> 无济于事；事务必须从头回滚并重试。读—改—写的正确模式是 <code>BEGIN IMMEDIATE</code>：一开始就取得写锁，把这次失败转化为普通的争用，让 <code>busy_timeout</code> 可以吸收它。

**WAL 模式下的 <code>PRAGMA synchronous</code>。** <code>synchronous = NORMAL</code> 是一个非常常见的推荐设置；在这个设置下，WAL 模式不会在提交时执行 <code>fsync</code>，只会在检查点执行。它可以经受进程崩溃，却经受不了断电或操作系统崩溃。<code>FULL</code> 才会恢复提交时的持久性。因此，许多应用随附的默认配置，其持久性其实并不像开发者以为的那么强。

在更底层，SQLite 的原子性依赖于一些有文档明确说明的平台假设：扇区写入是原子的，<code>fsync</code> 诚实可靠，以及在启用时，“幂等电源覆盖（powersafe overwrite）”成立——即写入扇区的一部分不会损坏其余部分。这些假设在消费级 SSD、某些网络文件系统以及若干移动平台上，历史上都曾被违反。

### 3.5 对比，以及一条守恒律

| | PostgreSQL | InnoDB | SQLite |
|---|---|---|---|
| MVCC 版本位置 | 堆表 | 撤销日志 | WAL / 日志 |
| 回滚成本 | O(1)，只需标记中止 | 与已完成的工作量成正比 | 与已完成的工作量成正比 |
| 延后支付的成本 | <code>VACUUM</code>、膨胀、XID 回绕 | purge 延迟、历史列表增长 | 检查点、WAL 增长 |
| 默认隔离级别 | 读已提交 | 可重复读 | 可串行化 |
| 最强隔离级别 | SSI（乐观，中止） | 2PL（悲观，阻塞） | 单写者串行化 |
| 应用必须处理 | 序列化重试 | 死锁、锁顺序 | <code>SQLITE_BUSY[_SNAPSHOT]</code> |
| 幻读防护 | 谓词 SIREAD 锁 | 临键锁 | 无关（只有一个写者） |
| 页面撕裂防护 | 完整页面写入 | 双写缓冲区 | 日志 / WAL |
| 写并发度 | 高 | 高 | 一个写者 |

值得提炼的规律是：**总工作量大致守恒，变化的只是成本被安排在什么时候支付。** PostgreSQL 把版本清理延后到后台进程，代价是膨胀和 vacuum 调优；InnoDB 在回滚和 purge 时支付代价；SQLite 则通过承认“一次只允许一个写者”，直接拒绝了这个问题。这里没有哪种设计是免费的——每种设计都选择了成本的落点，而你在运维中遇到的故事，往往都能直接追溯到那个选择。

## 4. 精确定义 CAP

### 4.1 CAP 定理

Brewer 在 PODC 2000 的主题演讲中提出了这个猜想；Gilbert 和 Lynch [2002] 对它进行了证明。他们的形式化表述中，每个术语都有严格含义：

> 在异步网络模型中，当任意消息都可能丢失时，不可能实现一个同时保证**原子（线性一致）行为**和**可用性**的读写寄存器。

- **一致性（Consistency）** = 单个对象的*线性一致性*：每个操作看起来都在调用与响应之间的某个瞬间原子生效，而且这个顺序与真实时间一致。如果一个写操作已经完成，随后才开始的读操作必须观察到这个写操作或之后的某个写操作。
- **可用性（Availability）** = *每一个*被不故障节点接收到的请求，最终都必须返回一个非错误响应。正如 §4.3 将强调的，这是一个非常强的要求。
- **分区容错性（Partition tolerance）** = 当节点之间的任意消息被丢弃时，系统仍然继续运行。

证明几乎简单得过分，而这份简单正是重点。把节点分成 <code>G₁</code> 和 <code>G₂</code> 两组，让两组之间的所有消息都丢失。向 <code>G₁</code> 中的一个节点写入 <code>v₁</code>；根据可用性，它必须返回。然后从 <code>G₂</code> 中的一个节点读取；根据可用性，它也必须返回，但它不可能已经获知 <code>v₁</code>，因此会返回旧值。线性一致性被违反。∎

### 4.2 分区不是设计选择

流行的“3 选 2”说法不仅简化，而且会主动误导。你无法选择分区是否发生——交换机故障、配置错误的防火墙、与分区无法区分的 GC 停顿、非对称路由以及光缆切断，都会替你做出选择。因此，任何部署在多台机器上的系统都必须容忍 P。真正的决策是：

> **发生分区时，你牺牲一致性，还是牺牲可用性？**

同样重要的是：**没有分区时，两者可以同时拥有。** 一个运行良好的单数据中心 Raft 集群，几乎一直既具备线性一致性，又具备可用性。CAP 描述的是一种罕见状态下的行为，不是永久征收的税。

Brewer 在自己的回顾文章《CAP Twelve Years Later》[2012] 中，把更有用的工程问题重新表述为明确的**分区管理**，分为三个阶段：检测分区已经开始；进入一种定义明确的*分区模式*，在其中限制、延迟或记录一部分操作以便稍后处理；分区恢复后执行*恢复*流程，合并状态，并为降级期间违反的不变量执行补偿。这比一张维恩图更能指导实践。

### 4.3 CAP 的“A”远比“高可用”更强

CAP 的可用性要求：*每个*未故障节点收到的*每个*请求都成功。在这个定义下：

- 一个要求多数派的 Raft 或 Paxos 集群是 **CP**，而不是 AP——即使是能够容忍两个故障的五节点集群，位于分区少数侧的节点也必须拒绝请求。
- 只有当一个幸存节点无需通信就能同时处理读和写时，系统才在 CAP 意义下真正“可用”。

与此同时，一个 Raft 集群的*实际*可用性可能高于运维混乱的 AP 系统。**CAP 可用性和运维可用性是不同的指标**；混淆它们，就会产生“CP 意味着经常停机”这一常见误解。

Fox 和 Brewer 更早提出的 **harvest / yield** 框架 [1999]，提供了比二元可用性更好的词汇：

- **Yield（产出率）**——成功得到回答的请求比例。
- **Harvest（收获率）**——回答中反映出的数据比例。

搜索引擎在部分故障下可以降低 harvest：它只用 90% 的索引回答，并明确不作掩饰。支付账本则会降低 yield：它宁可拒绝交易，也不从不完整的数据中给出答案。与其争论系统属于 CP 还是 AP，不如按端点决定究竟应该降低哪一个指标。

### 4.4 CAP 没有谈延迟——PACELC 才谈

CAP 对最常见的正常情况保持沉默，而你的全部成本恰恰都发生在那里。Abadi 的 **PACELC** [2012] 对 CAP 作了扩展：

> **如果发生（P）分区，就在（A）可用性与（C）一致性之间选择；否则（E）就在（L）延迟与（C）一致性之间选择。**

“否则”分支才是日常工程的主宰。想要强一致性的系统必须在每次操作上协调，而协调至少需要一次网络往返；跨区域时，这个成本受光速下界约束。

| 系统 | PACELC | 解读 |
|---|---|---|
| Dynamo、Cassandra、Riak | **PA/EL** | 分区时保持可用，其他时候追求低延迟 |
| HBase、BigTable、etcd、ZooKeeper | **PC/EC** | 始终保持一致，但支付协调延迟 |
| Spanner | **PC/EC** | 始终保持一致，同时通过工程手段把 L 做小 |
| MongoDB（典型配置） | **PA/EC** | 分区时偏向可用，其他时候偏向一致 |
| MySQL 异步复制 | **PA/EL** | 副本存在延迟；故障切换可能丢失已提交写入 |

### 4.5 一致性模型的层级

“一致，或者最终一致”是一个虚假的二分法。真实的版图从强到弱大致如下：

| 模型 | 保证 | 分区时可用？ |
|---|---|---|
| **严格可串行化** | 事务可串行化，并且跨事务遵守真实时间顺序 | 否 |
| **线性一致性** | 单对象、遵守真实时间顺序 | 否 |
| **顺序一致性** | 一个全局顺序，遵守每个进程的顺序，但不要求真实时间 | 否 |
| **因果+一致性** | 有因果关系的操作按顺序被观察；副本最终收敛 | **是**（需要粘性会话） |
| **会话保证** | 读己之写、单调读、单调写、写跟随读 | **是**（需要粘性会话） |
| **最终一致性** | 如果停止更新，副本最终收敛 | 是 |

会话保证源自 Terry 等人关于 Bayou 的工作 [1994]，往往是正确的目标：“读己之写”才是用户真正能感知到的东西；通过把一个会话固定到某个副本，或携带版本令牌，就能在不进行全局协调的情况下实现它。

一个重要的理论结果是：**因果一致性是在始终可用且最终收敛的系统中能够实现的最强模型** [Mahajan、Alvisi、Dahlin，2011]。如果要求分区期间也具备完全可用性，因果+就是上限；更高的模型都需要法定人数。

### 4.6 FLP：更深层的不可能性

CAP 并不是唯一的不可能性结果，甚至可以说也不是最根本的那个。**FLP 结果** [Fischer、Lynch、Paterson，1985] 指出，在一个完全异步的系统中，即使只有一个崩溃故障，也不存在确定性协议能够解决共识问题，因为系统无法区分“已经崩溃的进程”和“只是很慢的进程”。

实际的共识协议并没有违反 FLP，而是通过削弱模型来绕开它：

- **部分同步** [Dwork、Lynch、Stockmeyer，1988]——网络在某个未知的全局稳定时间之后最终变得同步。
- **故障检测器**——Chandra 和 Toueg [1996] 表明，只要有多数正确进程，一个最终强故障检测器 ◇S 就足以解决共识。能够解决共识问题的*最弱*故障检测器是最终弱故障检测器 ◇W [Chandra、Hadzilacos、Toueg，1996]；同一项工作还表明，◇W 可以被转换为 ◇S，因此二者在能力上等价。实际基于心跳和超时的检测器，都是这一族故障检测器的近似。
- **随机化（Ben-Or）**——随机退避或抛硬币，可以以概率 1 保证终止。

由此得到的工程结论准确而重要：**Paxos 和 Raft 无条件保证安全性，只在有条件的情况下保证活性。** 病态网络不能让它们返回错误答案，只能让它们停止推进。这种不对称是有意设计的；etcd 或 Raft 配置中的每个超时常数，都是一个不能损害安全性的活性旋钮。

## 5. 两者的关系：两条独立的轴

### 5.1 两个 C 是不同的词

把最核心的混淆再直白地说一遍：

| | ACID 的 C | CAP 的 C |
|---|---|---|
| 范围 | 跨多个对象的应用不变量 | 一个对象 |
| 由什么强制执行 | 约束 + 正确的事务 + 足够的隔离 | 复制协议 |
| 是否要求真实时间 | 否 | 是 |
| 什么会违反它 | 有缺陷的事务，或弱隔离下的写偏斜 | 从滞后副本读到旧值 |

它们不是同一种性质的强弱版本，而是两个互不相关、恰好共享一个字母的性质。

同样，**可串行化与线性一致性也是正交的**：

- 可串行化是一个*多对象*性质，*不要求真实时间*。一个可串行化的执行，可以等价于一个与墙上时钟顺序毫无关系的串行顺序。
- 线性一致性是一个*单对象*性质，*严格要求真实时间*。
- **严格可串行化**是二者的合取，也就是 Spanner 所说的“外部一致性”。

### 5.2 两轴模型

行表示**新近性**（副本视图有多新）；列表示**事务隔离**（事务如何交错）。二者都是越向上、越向右越强。

| ↑ 新近性 \ 隔离 → | 无 / 单键 | 读已提交 | 快照 | 可串行化 |
|---|---|---|---|---|
| **线性一致** | etcd；启用 <code>sync</code> 的 ZooKeeper；HBase 的单行 | — | TiDB（全局时间戳预言机上的 Percolator SI）；*平凡地*，任何处于 RR 的单节点数据库 | **Spanner、CockroachDB、FoundationDB**——严格可串行化；*平凡地*，处于 <code>SERIALIZABLE</code> 的单节点 PostgreSQL |
| **顺序一致** | ZooKeeper 默认的本地读 | — | — | — |
| **因果一致** | 带因果上下文的 Riak；使用向量时钟的 Dynamo | MongoDB 因果一致会话 | 带因果会话、使用快照 <code>readConcern</code> 的 MongoDB 事务 | — |
| **最终一致** | Cassandra、Dynamo 默认配置 | RC 下的异步读副本（MySQL、PostgreSQL） | RR/SI 下的异步读副本；PostgreSQL 热备库（见下文） | Spanner 的过时快照读；CockroachDB 的 <code>AS OF SYSTEM TIME</code>；通常意义上的 follower read |

表中的空白格并非偶然；理解它们和理解有内容的格子同样重要。顶行中间的格子为空，是因为**一旦为线性一致性付出了全局顺序的成本，把隔离级别降回读已提交并不会买到任何东西**——昂贵的部分你已经拥有了。顺序一致这一行几乎为空，是因为“顺序一致但不线性一致”是一个很窄的区间，很少有系统会专门瞄准它；ZooKeeper 落在那里，是本地提供读服务的副作用，而非设计目标。因果/可串行化这个格子为空，则是 §5.3 将精确说明的原因：可串行化无法在保持可用性的同时实现，因此一个已经放弃可用性的系统没有理由停在因果新近性上。

表中有两个条目标为*平凡地*，因为它们依赖退化情形下的论证：只有一个副本时，没有什么东西可以相对于它变旧，所以线性一致性是免费的。之所以列出这两个格子，是因为大多数开发者的直觉正是建立在这个退化情形上，而一旦加入副本，直觉就会失效。

四个角值得单独命名：

- **左下角**——最终一致、没有事务。Dynamo 风格存储的默认配置。
- **左上角**——线性一致但非事务化。etcd 对单个键的 compare-and-swap 具备线性一致性；但它几乎没有多对象隔离。
- **右下角**——可串行化，但可以任意滞后于真实时间。
- **右上角**——严格可串行化，即两条轴都取最大强度后的合取。

右下角最令人意外，因此值得给出一个精确例子，而不是一笔带过；不过，最直观的例子其实行不通。**PostgreSQL 热备库根本不能运行 <code>SERIALIZABLE</code>**——请求会被直接拒绝（§3.2），所以“可串行化读副本”并不是标准流复制可以构造的东西。诚实的例子，是那些同时提供可串行化、却有意暴露一个过时读取时间戳的系统：Spanner 在过去时间戳上的快照读、CockroachDB 的 <code>AS OF SYSTEM TIME</code> 和有界过时 follower read、YugabyteDB 的 follower read。这些系统中的事务完全可串行化——它们等价于某个串行顺序——但可以任意落后于真实时间。它们之所以存在，正是因为可串行化不要求新近性，而厂商把这道鸿沟卖成了延迟特性。

这个实践教训可以推广到这个特殊角落之外：一个团队把报表查询迁移到副本时，削弱的是*新近性*，而不是隔离性；无论配置了什么隔离级别，仪表盘都可能与主库相矛盾。两条轴彼此独立，也必须彼此独立地推理。

### 5.3 精确的边界：HAT、I-Confluence 与 CALM

ACID 与 CAP 之间真正深刻的联系在于，近年的理论精确告诉了我们：在要求完全可用的情况下，哪些事务保证仍然存在。

**高可用事务（Highly Available Transactions）** [Bailis 等，2013] 询问：一个即使在分区期间也从不拒绝请求的系统，能够提供哪些隔离级别？答案如下：

| **HAT 可实现** | **无法实现（要求牺牲可用性）** |
|---|---|
| Read uncommitted（读未提交） | Serializability（可串行化） |
| Read committed（读已提交） | Snapshot isolation（快照隔离） |
| Monotonic atomic view（单调原子视图） | Repeatable read（可重复读，如游标稳定性等） |
| Item cut isolation（项目切分隔离） | Linearizable / strong session guarantees（线性一致性 / 强会话保证） |
| Read-your-writes（读己之写）* | Unique constraints（唯一约束） |
| Causal consistency（因果一致性）* | Foreign keys with cascading delete（带级联删除的外键） |
| Atomic visibility of transactions（事务的原子可见性） | <code>AUTO_INCREMENT</code> / global counters（全局计数器） |

（*需要“粘性可用性”——客户端必须持续与同一个副本通信。）

这就是“ACID 与 CAP 有什么关系”的定理化答案，而不是凭感觉得出的结论：大多数系统默认运行的隔离级别，恰好与 CAP 可用性兼容；而人们为了正确性真正想要的那些级别，恰好无法在该条件下实现。

**不变量合流（Invariant confluence）** [Bailis 等，2015] 把问题从隔离级别进一步细化到了单个不变量。如果两个分别满足不变量的状态，在合并之后仍然满足该不变量，那么这个不变量就是 *I-confluent* 的。I-confluent 不变量可以用**零协调**维护；非 I-confluent 不变量则被证明不可能在零协调下维护。

| 不变量 | I-confluent？ | 原因 |
|---|---|---|
| <code>balance ≥ 0</code>，只允许存款 | 是 | 合并两个增量仍然保持该性质 |
| <code>balance ≥ 0</code>，允许取款 | **否** | 两次合法取款合并后可能变成透支 |
| 插入时的外键 | 是 | 先插入父项再插入子项；合并仍保持该性质 |
| 带级联删除的外键 | **否** | 一侧删除父项，另一侧插入子项 |
| 用户名唯一 | **否** | 两个副本可能分别接受同一个名字 |
| 向集合追加 | 是 | 集合并集就是合并操作 |
| <code>AUTO_INCREMENT</code> 唯一性 | **否** | 需要全局序列 |

这套理论给出的实践流程很具体：*枚举应用的不变量并为它们分类*。在大多数真实应用中，绝大多数不变量都是 I-confluent 的；少数不是的——唯一性、非负库存、货币守恒——才是需要购买协调的地方。仅仅因为“我们需要 ACID”，就对每一个操作全局购买协调，是按数量级过度付费。

**CALM 定理**（Hellerstein 于 2010 年提出猜想，Ameloot、Neven 和 Van den Bussche 证明；见 Hellerstein & Alvaro 2020）进一步推广了这一点：*一个程序存在一致且无协调的分布式实现，当且仅当它是单调的*——也就是增加更多输入时，不会撤回此前已经推导出的输出。单调逻辑（并集、连接、追加、CRDT 合并）不需要协调；非单调操作（否定、计算最终结果的聚合、“这个集合是否已经完整？”、唯一性检查）需要协调。它告诉我们，“我们是否已经看到了全部内容？”才是最根本的非单调问题，而每一种协调协议归根结底都是在回答它。

### 5.4 CAP 也适用于你的 ACID 数据库

最常见的实践错误，是以为 CAP 只和 NoSQL 有关。CAP 讨论的是复制，而每一个投入生产的关系数据库都在做复制。

**PostgreSQL 同步复制。** 设置 <code>synchronous_standby_names = 'standby1'</code>，并设置 <code>synchronous_commit = on</code>。现在你得到的是一个 CP 系统：如果 <code>standby1</code> 被分区隔离，提交就会**无限期阻塞**。这正是“零数据丢失”的正确行为；但如果你本来没打算用可用性换它，那么你已经在不知不觉中选择了 CP。

缓解方式是法定人数提交。这里的历史值得准确理解，因为这两个特性经常被混为一谈。PostgreSQL 9.6 开始支持*多个*同步备库，但采用的是优先级语义：<code>synchronous_standby_names = '2 (s1, s2, s3)'</code> 会等待当前可用、优先级最高的两个备库。**真正的法定人数提交——<code>ANY n (...)</code> 语法，以及明确表示旧优先级行为的 <code>FIRST n (...)</code>——是在 PostgreSQL 10 才加入的。** 使用 <code>ANY 1 (s1, s2, s3)</code> 时，一次提交只需得到三个备库中任意一个的确认，因此丢失一个备库不会拖住主库。正是这个配置把脆弱的 CP 设置变成了稳健的方案；它是版本 10 的特性，不是 9.6 的。

**MySQL 半同步复制**有一个更隐蔽的陷阱。半同步复制会等待至少一个副本确认，然后才向客户端返回。但超时后，它会**静默降级为异步复制**并继续工作。因此，系统对外宣称 CP，却在最需要 CP 的条件下悄悄变成 AP；之后任何一次故障切换都可能丢失已经确认的提交。设置 <code>rpl_semi_sync_master_wait_point = AFTER_SYNC</code>（无损半同步）可以关闭“提交在复制完成前就已经可见”的窗口，但“超时后降级”这一行为是必须有意识做出的策略选择，也必须受到监控。

**故障切换是藏在关系数据库里的共识问题。** 要决定哪个节点是主节点，并且永远不产生两个主节点，本质上就是 Paxos 和 Raft 解决的问题。这也是生产环境的 PostgreSQL 高可用方案（Patroni、Stolon）会把领导者选举交给 etcd、Consul 或 ZooKeeper 的原因。“ACID 数据库”和“共识系统”并不是两个互不相干的世界；后者是前者赖以工作的基础设施。

## 6. 机制：法定人数、Gossip、Paxos 与 Raft

这四者经常被作为“CAP 的实现方式”列在一起，但它们并不是同一层次的东西。法定人数是一种*原语*；Gossip 是一种*传播与故障检测*基础设施；Paxos 和 Raft 则是构建在法定人数之上的*共识协议*。理解每一种机制能提供什么、不能提供什么，是掌握整个主题的大半。

### 6.1 法定人数

**交集原则。** 假设有 <code>N</code> 个副本、写法定人数 <code>W</code>、读法定人数 <code>R</code>，如果满足

~~~text
R + W > N
~~~

就能保证任意读集合和任意写集合至少共享一个副本，因此每次读取至少会接触到一个保存最新写入的节点。此外，

~~~text
W > N/2
~~~

可以防止两个并发写入在没有重叠的情况下同时成功。这个思想可以追溯到 Thomas 的多数派共识 [1979] 和 Gifford 的加权投票 [1979]。

<code>N = 3</code> 时的常见配置：

| R | W | 性质 |
|---|---|---|
| 1 | 3 | 读很快，但任一副本宕机都会导致写入失败 |
| 3 | 1 | 写很快，但任一副本宕机都会导致读取失败 |
| 2 | 2 | 平衡；读写两条路径都能容忍一次故障 |
| 1 | 1 | **最终一致性**——不保证交集 |

**一个关键而常被遗漏的事实：仅有法定人数读写，并不能得到线性一致性。** 交集只能保证读取*看到*最新的已完成写入。设一次写入正在进行，并且已经到达三个副本中的一个；一个 <code>R = 2</code> 的读取可能联系到这个副本并返回新值，而它之后的一次读取可能联系另外两个副本并返回旧值。值先向前、再向后——尽管满足 <code>R + W > N</code>，仍然不是线性一致的。

解决办法是 **ABD 算法** [Attiya、Bar-Noy、Dolev，1995]：它通过两个阶段，在消息传递系统上实现线性一致的读写寄存器：

1. **读取阶段**——查询一个法定人数，取时间戳最高的值。
2. **回写阶段**——在返回这个值之前，把它写回一个法定人数。

回写使读操作观察到的值持久化，因此之后的读取不可能倒退。这就是为什么“只用法定人数”不能得到线性一致性，也是需要线性一致性的系统要么实现 ABD 式回写、要么把读取路由到共识领导者的原因。

**松散法定人数与提示移交（hinted handoff）** [DeCandia 等，2007] 则有意破坏交集保证，以换取可用性。如果某个键的 <code>N</code> 个“归属”节点不可达，写入就改为发送到环上前 <code>W</code> 个可达节点，每个节点都保存一份指向目标节点的*提示*。归属节点恢复后，再把提示移交过去。可用性上升了；<code>R + W > N</code> 不再意味着存在交集；系统明确进入 AP 阵营。这正是 Dynamo 这一脉系统的关键旋钮。

**解决分歧。** 一旦允许副本分歧，就需要一种合并策略：

| 策略 | 行为 | 风险 |
|---|---|---|
| **最后写入获胜** | 时间戳最高者获胜 | 时钟偏差会静默丢弃写入 |
| **向量时钟** | 检测并发；把兄弟版本交给应用 | 客户端复杂度；向量增长 |
| **点版本向量** | 紧凑的版本向量，不产生错误并发 | 更复杂 |
| **CRDT** | 合并在数学上有明确定义，并且总能收敛 | 数据类型受限 |

无冲突复制数据类型 [Shapiro 等，2011] 是一种原则化答案，而且它与 CALM 直接相连：CRDT 的合并是半格上的 join，是单调的，也正是无需协调的条件。计数器、集合、寄存器，甚至类 JSON 文档和协同编辑文本，都可以有 CRDT 形式。

**可调一致性**，就是把法定人数理论暴露为 API。Cassandra 允许对每个操作选择 <code>ONE</code>、<code>QUORUM</code>、<code>LOCAL_QUORUM</code>、<code>EACH_QUORUM</code>、<code>ALL</code>；DynamoDB 则提供最终一致读与强一致读。在多区域部署中，<code>LOCAL_QUORUM</code> 的意义，正是 PACELC 的“否则”分支：在常见情况下避免跨区域往返，同时接受区域故障切换可能丢失最近写入。

**值得了解的改进：**

- **Flexible Paxos** [Howard、Malkhi、Spiegelman，2016] 证明，法定人数交集只需跨阶段成立，而不必在每个阶段内部成立。如果领导者选举法定人数与复制法定人数相交，它们就不必各自都是多数派。<code>N = 5</code> 时，可以使用大小为 2 的复制法定人数来加速写入，只要选举法定人数为 4。这是对沿用了二十年的假设非常令人意外的放宽。
- **见证副本**参与投票但不保存数据，提供廉价的故障容忍能力。
- **法定人数租约**授予副本在有限时间内提供本地读取的权利，以时钟假设换取读取延迟。

### 6.2 Gossip 与反熵

Gossip 不是一致性协议，把它当作一致性协议是类别错误。它是一种具有出色鲁棒性的**传播机制**，但完全不提供顺序保证。

**流行病式算法** [Demers 等，1987] 有多种变体：

- **反熵（Anti-entropy）**——节点周期性地随机选择一个对等节点，对双方的完整状态进行协调。可以采用 push、pull 或 push-pull。它可靠但昂贵，通常以较慢的周期运行，作为最后一道保障。
- **谣言传播（Rumor mongering）**——掌握新信息的节点把它告诉随机对等节点，在从足够多的其他节点听到同一个谣言后停止。它快速而便宜，但有小概率无法触达所有节点，因此底层仍要运行反熵作为安全网。

Gossip 无处不在，原因在于它背后的数学性质：信息以很高的概率在 **O(log N)** 轮内到达全部 <code>N</code> 个节点；没有领导者或瓶颈；节点故障时协议会优雅退化。无论集群规模如何，每个节点承担的消息负载大致均匀。

**生产环境中 Gossip 真正承担的工作：**

| 用途 | 系统 |
|---|---|
| 集群成员管理与故障检测 | Cassandra、Consul/Serf、Redis Cluster、Riak、Akka |
| 元数据传播（模式、环拓扑） | Cassandra、Dynamo |
| 修复分歧副本的反熵 | Dynamo、Cassandra、Riak |
| 负载与健康信息 | Consul、Serf |

**SWIM** [Das、Gupta、Motivala，2002] 是现代最标准的成员管理协议。每个节点周期性地直接探测一个随机对等节点；超时后，请求另外 <code>k</code> 个节点进行间接探测，以区分真正死亡的节点和暂时不可达的路径。成员更新会搭载在普通协议消息上，而不是单独广播。**怀疑机制和世代编号反驳机制**——先把节点标记为*可疑*而非*确认死亡*，再允许被指控者通过增加自己的世代编号进行反驳——都属于原始 SWIM 论文，并非后来的补充；它们的存在就是为了降低误报率。HashiCorp 的 Serf 和 Consul 在此基础上贡献的是 **Lifeguard** 扩展 [2018]：引入本地健康感知，使一个怀疑自身已经降级的节点在指责其他节点时更加谨慎；同时增加 buddy system，以更快地传递反驳。

**Phi 累积故障检测** [Hayashibara 等，2004] 被 Cassandra 和 Akka 使用。它不再给出简单的生/死二元判断，而是根据近期心跳间隔的统计分布，持续计算一个怀疑等级 <code>φ</code>。应用自行选择阈值，因此故障检测器与“快速检测”还是“减少误报”的取舍解耦了。

**Merkle 树反熵**是 Dynamo 系统谱系高效修复分歧的方式。每个副本都在自己的键范围上维护一棵哈希树；两个副本比较根哈希，只向下遍历那些不一致的子树。这样可以通过对数次比较定位分歧，而无需扫描完整范围。正是这个后台过程，让最终一致性中的“最终”真正到来。

最重要的定位是：**Gossip 是 AP 的工具箱。** 它不提供顺序、原子性或线性一致性；它提供的是收敛性、可扩展性和韧性。在 Cassandra 这样的系统中，它与法定人数数据路径并行工作：法定人数处理每个请求的一致性，Gossip 处理成员关系和后台收敛。

### 6.3 Paxos

Paxos 解决的是**共识**：一组进程必须对一个值达成一致，而且只能选出某个被提出的值，最多只能选出一个值，进程也只能学习到确实被选出的值。Lamport 的原始论文 [1998] 以晦涩著称；《Paxos Made Simple》[2001] 才是易读的版本。

**单决议 Paxos** 有三个角色（通常部署在同一组进程中）和两个阶段：

~~~text
阶段 1（Prepare）：
  提议者 -> 接受者：PREPARE(n)          n = 唯一且递增的提案编号
  接受者：          如果 n > 之前见过的任意编号：
                      承诺永不接受 < n 的编号
                      回复 PROMISE(n, (n_acc, v_acc)，若此前接受过某个值)
                    否则忽略

阶段 2（Accept）：
  提议者：收到多数派的 PROMISE 后：
            如果有接受者报告了一个已接受的值，
               v := n_acc 最高的那个值      <-- 关键规则
            否则
               v := 自己提出的值
          -> 接受者：ACCEPT(n, v)
  接受者：如果尚未承诺更高的编号：接受，并回复 ACCEPTED(n, v)

  当多数派接受了 (n, v) 时，该值被选出（chosen）。
~~~

上面标出的规则值得反复咀嚼，因为安全性论证就藏在这里。看一个具体例子：

~~~text
图 3——单决议 Paxos，以及为何必须采用“继承”规则

初始状态：A 已经接受 (3, "x")
          B 和 C 尚未接受任何值

阶段 1
  P -> A、B、C：PREPARE(5)
  A -> P       ：PROMISE(5，accepted = (3, "x"))
  B -> P       ：PROMISE(5，accepted = none)
  C           ：（不可达）
                -- 多数派 {A, B} 已经作出承诺

继承规则
  在这些承诺中，编号最高的已接受值是 (3, "x")。
  P 现在必须提出 "x"——不能提出自己的值。
  原因：更早的多数派可能已经选出了 (3, "x")，
  而 P 看不到那个多数派。提出其他值就可能导致两次选出不同的值。

阶段 2
  P -> A、B：ACCEPT(5, "x")
  A -> P   ：ACCEPTED(5, "x")
  B -> P   ：ACCEPTED(5, "x")
              -- 多数派已经接受；"x" 被选出

安全性完全建立在两个事实之上：任意两个多数派必然相交，
以及继承规则迫使新提议者延续任何可能已经被选出的值。
去掉其中任意一个，就可能选出两个不同的值。
~~~

**活性并没有保证**，这正是 FLP 所要求的结果。两个提议者可能无限期地争斗，每一个都用更高的提案编号使另一个的承诺失效。实践中的解决方式是选出一个固定的提议者，并使用随机退避；这也是 Raft 采用的同一条逃生通道。

**Multi-Paxos** 才是实际部署时采用的形式。为每条命令完整运行一次 Paxos 需要两次往返；因此先选出一个稳定的领导者，随后所有日志位置都可以跳过阶段 1，把稳态成本降为**每条命令一次往返**。到了这里，Multi-Paxos 和 Raft 看起来非常相似；这就是对二者关系最诚实的概括。

**值得注意的变体：**

| 变体 | 思路 | 取舍 |
|---|---|---|
| **Fast Paxos** | 客户端直接向接受者发送请求，省去一次消息延迟 | 需要更大的法定人数；发生冲突时需要恢复 |
| **Generalized Paxos** | 只对真正冲突的命令排序 | 冲突跟踪更复杂 |
| **EPaxos** | 完全无领导者；为每条命令跟踪依赖 | WAN 延迟最优；恢复复杂 |
| **Flexible Paxos** | 只要求跨阶段交集 | 法定人数大小可调 |
| **Vertical Paxos** | 通过外部主节点完成重配置 | 成员变更更简单 |
| **Cheap Paxos** | 只在故障时使用辅助接受者 | 活跃机器更少 |

**《Paxos Made Live》** [Chandra、Griesemer、Redstone，2007] 是 Google 构建 Chubby 的实践报告，工程师必读，因为它记录了算法与系统之间的鸿沟。它的核心观察是：发表出来的算法或许只描述了工作量的十分之一。剩下的工作包括处理磁盘损坏、为本地读设置主节点租约、处理原始论文几乎没有说明的成员变更、管理快照、以可测试的形式表达状态机，以及构建能够发现罕见并发 bug 的确定性测试框架——普通测试发现不了这类问题。

**部署实例：** Chubby、Google Megastore（每个实体组一个 Paxos，并跨数据中心同步复制）、Spanner（每个分片一组 Paxos）、Ceph monitor、Cassandra 的轻量级事务（每个分区键运行一组 Paxos 以实现 compare-and-set）、Azure Cosmos DB。

### 6.4 Raft

Raft [Ongaro 与 Ousterhout，2014] 的设计目标明确是*可理解性*。它解决的问题与 Multi-Paxos 相同，但把问题拆成三个彼此独立的部分——领导者选举、日志复制和安全性——并有意限制状态空间，以减少实现者需要推理的情形数量。

**强领导者。** 日志条目只能从领导者流向跟随者。领导者永远不会覆盖或删除自己日志中的条目。这比 Paxos 更严格——Paxos 允许乱序提交和日志空洞——也正是让 Raft 变得可处理的简化。

**把任期当作逻辑时钟。** 时间被划分为任期，每个任期从一次选举开始。每个 RPC 都携带任期号；服务器看到更高的任期后会立即退回跟随者状态。一个任期最多只有一个领导者，也可能没有领导者（例如发生平票）。

**领导者选举。** 如果跟随者在*随机化*的选举超时时间内什么都没听到，就会变成候选者，增加任期号、投票给自己并请求投票。随机化是防止活锁的机制：平票会很快解决，因为超时时间很少会连续两次发生碰撞。

**选举限制——安全性的关键思想。** 只有当候选者的日志“不落后于”自己的日志时，投票者才会投票给它；比较时先看最后一条日志的任期，再看最后一条日志的索引。由于任意选举法定人数都会与任意提交法定人数相交，赢得选举的候选者必然持有所有已提交条目。这个单一限制取代了 Paxos 的阶段 1 值恢复机制，并产生**领导者完整性性质（Leader Completeness Property）**：某个任期中提交的任何条目，都会出现在之后各任期的所有领导者日志中。

**日志匹配。** <code>AppendEntries</code> 携带 <code>prevLogIndex</code> 和 <code>prevLogTerm</code>；除非跟随者在该位置拥有匹配条目，否则拒绝请求。被拒绝时，领导者向前回退并重试（生产实现会使用冲突提示进行优化）。这在归纳意义上保证：*如果两个日志在相同索引上包含相同任期的条目，那么它们在此前的所有条目都完全相同*。

**提交的微妙之处**是大多数重新实现最容易出错的地方，值得用具体例子走一遍：

~~~text
图 4——Raft 的提交规则（论文中的图 8）

五台服务器 S1..S5。日志条目以 [任期] 表示。

（a）S1 在任期 2 中担任领导者。它把一个条目追加到索引 2，
    只复制给 S2，随后崩溃。
      S1 [1][2]   S2 [1][2]   S3 [1]   S4 [1]   S5 [1]

（b）S5 得到 S3、S4 以及自己的选票，在任期 3 赢得选举，
    并在索引 2 追加一个不同的条目。随后它崩溃。
      S5 [1][3]

（c）S1 重启，并在任期 4 赢得选举。它继续复制原来的任期 2 条目，
    该条目现在已经到达多数派 {S1, S2, S3}。
      S1 [1][2]  S2 [1][2]  S3 [1][2]  S4 [1]  S5 [1][3]

    >>> 假设 S1 此时因为多数副本已经拥有该条目，
        就宣布索引 2 已提交。看看（d）会怎样处理它。

（d）S1 崩溃。S5 得到 S2、S3、S4 的选票，在任期 5 赢得选举——这是合法的，
    因为 S5 的最后日志任期 3 高于它们的任期 2。然后 S5 用自己的任期 3 条目，
    在所有地方覆盖索引 2。
      -> 一个此前已经报告为提交的条目被抹掉了。

RAFT 的规则：在（c）中，S1 不能仅凭副本数量提交任期 2 的条目。
领导者只有在条目属于自己当前任期时，才能按副本数量提交它。
实践中，领导者会在当选时追加一条 no-op；提交这条 no-op 就会间接提交索引 2，
一旦这一点完成，S5 就不再可能赢得选举，因此（d）也就不可能发生。
~~~

**成员变更**有两种方式。*联合共识（Joint consensus）*会先经过一个包含旧、新配置的组合配置 <code>C_old,new</code>；在该阶段，每个决定都需要旧配置和新配置各自的多数派，从而保证不存在两个互不相交的多数派。*单服务器变更*则每次只添加或删除一个服务器，更简单，也是大多数实现采用的方式；但要注意，安全性论证要求领导者在开始配置变更前，先提交一条属于当前任期的日志条目——这是论文发表后发现、并在 Ongaro 博士论文勘误中修正的问题。

**日志压缩**使用状态机快照，并通过 <code>InstallSnapshot</code> RPC 为落后太多的跟随者安装快照。

**线性一致读不是免费的**，这也是实现中常见的 bug。领导者不能简单地从本地状态回答请求：它可能已经被一个尚未察觉的分区废黜，此时继续提供的就是旧数据，违反线性一致性。正确方式有三种：

| 技术 | 机制 | 成本 | 假设 |
|---|---|---|---|
| **日志读（Log read）** | 把读取追加为一条日志条目 | 完整复制轮次 | 无 |
| **ReadIndex** | 记录提交索引，通过心跳轮次确认领导权，等待状态机追上该索引 | 一次往返，不写磁盘 | 无 |
| **租约读（Lease read）** | 领导者依靠基于选举超时的租约在本地提供读取 | 零次往返 | 时钟偏移有界 |

ReadIndex 是标准选择；租约读更快，但把安全性性质转移到了时钟行为上。同一个 ReadIndex 值也可以转发给跟随者，从而支持线性一致的**跟随者读取**；TiKV 等系统正是这样扩展读吞吐的。

**部署实例：** etcd、Consul、TiKV/TiDB、CockroachDB（每个数据范围一个 Raft 组）、YugabyteDB、Kafka 的 KRaft 模式、Redpanda、RethinkDB、MongoDB 的复制协议（受 Raft 启发，并针对 oplog 模型做了适配）、Neo4j causal clustering、Elasticsearch 的 Zen2（类似 Raft，但有自己的适配）。

### 6.5 共识协议家族对比

| | Paxos（Multi） | Raft | ZAB | Viewstamped Replication |
|---|---|---|---|---|
| 起源 | Lamport，1998 | Ongaro，2014 | Junqueira 等，2011 | Oki 与 Liskov，1988 |
| 领导机制 | 可选，是一种优化 | 必须，是结构的一部分 | 必须 | 必须（主节点） |
| 日志空洞 | 允许 | 禁止 | 禁止 | 禁止 |
| 领导者追赶 | 新领导者继承编号最高的已接受值 | 新领导者必须已经最为先进 | 领导者把自己的历史同步给跟随者 | 视图变更转移日志 |
| 重新配置 | 原始论文没有充分说明 | 联合共识 / 单服务器变更 | 自 3.5 起支持动态变更 | VR Revisited 中有明确说明 |
| 主要用途 | Chubby、Spanner、Megastore | etcd、Consul、TiKV、CockroachDB | ZooKeeper | 很少直接部署 |

**ZooKeeper 值得特别说明**，因为它的一致性模型经常被误解。写入是线性一致的（通过 ZAB 排序）。**读取由任意副本本地提供，因此只有顺序一致性——可能读到旧值。** 需要线性一致读的客户端必须先发出 <code>sync()</code>。ZooKeeper 还额外保证客户端请求的 FIFO 顺序。它的设计者有意削弱读取语义，以换取读吞吐量；这是 PACELC“否则”分支被主动牺牲的典型例子。

### 6.6 两阶段提交不是共识

2PC 经常和 Paxos、Raft 被归在一起，但它们解决的是不同的问题。共识让一组*副本*通过多数派法定人数对一个值达成一致；**原子提交**则让一组*参与者*（每个参与者持有不同的数据）共同决定提交还是中止，而且要求*全体一致*，因为任意一个参与者都可能有理由中止。

由此产生一个众所周知、也非常严重的限制：**2PC 会阻塞。** 如果协调者在参与者投票“是”之后、发送决定之前发生故障，参与者就会持有锁，无法安全地继续——它们不能提交（因为可能有人投了否），也不能中止（因为可能有人已经提交）。三阶段提交加入一个预提交轮次，可以减少阻塞，但在网络分区下并不安全，实践中基本没有使用。

现代修复方式具有组合性，而且很优雅：**让协调者本身成为复制状态机。** Spanner 在 Paxos 组之间运行 2PC，同时用 Paxos 复制协调者的决定日志，于是协调者故障可以被容忍，整个协议事实上不再阻塞。这种组合——用共识实现复制，用 2PC 实现跨分片原子性——是分布式 ACID 的标准架构。

### 6.7 关于拜占庭容错

Paxos 和 Raft 假设的是*崩溃停止*（或崩溃恢复）模型：节点可能停止或变慢，但不会说谎。拜占庭容错则去掉了这个假设，要求使用 <code>3f + 1</code> 个节点来容忍 <code>f</code> 个任意故障；PBFT [Castro 与 Liskov，1999] 和线性通信的 HotStuff [2019] 等协议被区块链系统使用。对数据中心数据库而言，这几乎总是错误的模型——成本很高，而校验和、身份认证和运维控制更适合应对相应威胁。这里保留它，是为了明确崩溃故障假设的边界，而不是把它默认为理所当然。

## 7. 两者交汇之处：分布式 ACID

想要在复制、分片的数据上提供可串行化事务，系统必须组合本文两半的机制。这些方案大致分成几种不同的架构家族。

### 7.1 共识 + 2PC + 时间戳权威：Spanner

Google 的 Spanner [Corbett 等，2012] 在全球分布式数据库上提供**外部一致性**——也就是严格可串行化。它的组合方式如下：

- 数据被分片；每个分片都是一个跨数据中心复制的 **Paxos 组**。
- 单分片事务通过该组的 Paxos 日志提交。
- 跨分片事务在多个 Paxos 组之间运行 **2PC**，并且协调者自身的状态也通过 Paxos 复制，因此经典的阻塞问题被消除了。
- 读写事务使用 2PL；只读事务则在某个时间戳上执行无锁的快照读取。

Spanner 的独特贡献是 **TrueTime**：这是一个由 GPS 接收器和原子钟支持的 API，返回一个必然包含真实时间的区间 <code>[earliest, latest]</code>，并带有有界的不确定性 <code>ε</code>。Spanner 利用它实现**提交等待（commit wait）**：选择提交时间戳 <code>s</code> 后，事务会一直等待，直到 <code>TT.after(s)</code> 成立——也就是直到可以确定 <code>s</code> 已经在所有地方成为过去——然后才释放锁。等待成本大约是 <code>2ε</code>（Google 的部署中是几毫秒），换来的则是全局时间戳顺序蕴含真实时间顺序。这是少数通过*时钟基础设施*而不是消息交互来购买一致性保证的案例。

这里的通用教训是：跨区域实现严格可串行化，需要某种全局排序来源；你可以从通信中获得它（增加网络往返），也可以从物理世界中获得它（高度同步的时钟）。Spanner 选择了物理世界，因为 Google 承担得起相应的硬件。

### 7.2 混合逻辑时钟：CockroachDB、YugabyteDB

没有原子钟的系统，会用**混合逻辑时钟** [Kulkarni 等，2014] 近似实现同一目标。它把物理时间与 Lamport 计数器结合起来，使存在因果关系的事件无论时钟如何偏移，都能获得递增的时间戳。

CockroachDB [Taft 等，2020] 为每个数据*范围*使用一个独立的 Raft 组进行复制，用 HLC 作为事务时间戳；由于没有硬件提供的有界不确定性保证，它不是等待不确定窗口过去，而是遇到窗口内的值时*重启*事务。它的“并行提交”优化通过让事务记录的提交状态可以从写入是否存在中推断出来，省去了一次往返。最终得到的是可串行化隔离，但有一个文档明确说明的前提：正确性依赖时钟偏移保持在配置的 <code>max_offset</code> 以内；超过该值的节点会将自己移出集群。

### 7.3 基于客户端的 2PC：Percolator

Google 的 Percolator [Peng 与 Dabek，2010] 在不修改 BigTable 的前提下，为它增加了快照隔离事务。它使用时间戳预言机提供全局有序时间戳，在每个数据列旁增加用于保存锁和写指针的列，并采用由客户端驱动的 2PC，其中任意选定的一个单元格充当*主锁*。提交就是一次原子写入：让主锁记录变为可见；其他锁则由后来遇到它们的事务惰性清理。

TiDB 采用了这一设计，只是底层换成了由 Raft 复制的 TiKV，而不是 BigTable。它值得研究，因为它展示了如何在一个只提供逐行原子性的存储之上，叠加出事务语义。

### 7.4 用确定性替代共识：Calvin

Calvin [Thomson 等，2012] 反转了通常的顺序。它不是先执行事务、再对结果达成一致，而是通过复制的排序层，**先对事务的全序达成一致**，然后让每个副本按照这个顺序确定性地执行。给定相同的顺序，执行就是确定性的，副本不可能发生分歧，因此**完全不需要两阶段提交**——因为共识已经提前完成。

代价是真实存在的：事务必须预先知道自己的读写集合（交互式事务需要先进行一次侦察步骤），而长事务可能拖慢确定性调度。FaunaDB 是这一家族中最知名的生产系统。

### 7.5 在层之间共同设计：TAPIR

上面的架构都是把事务协议堆在复制协议之上；因此它们会为排序付两次钱：复制层建立一个全序，事务层又在其上建立另一个全序。**TAPIR** [Zhang 等，2015] 追问这种重复是否必要，答案是不必要。它在**不一致复制**之上构建线性一致、严格可串行化的事务协议——底层复制只提供容错和持久性，有意不提供任何排序保证；排序只在事务层通过乐观的、按时间戳排序的验证恢复一次。

这样做的收益是：已提交事务可以在最近的法定人数处用一次往返完成，路径中不需要领导者。这篇论文清楚表达了本文反复出现的一条原则：**在一个层次支付过的协调成本，往往会在下一层再次支付；而这两层通常由从不核对账单的不同团队设计。**

### 7.6 AP 存储中的单对象共识：Cassandra LWT

Cassandra 是一个 AP 系统，但应用有时只需要一个线性一致的操作——通常是“如果没有人占用，就抢占这个用户名”。轻量级事务通过对**每个分区键运行 Paxos**，提供 <code>IF NOT EXISTS</code> / <code>IF &lt;condition&gt;</code> 语义。它的成本大约是普通法定人数写入的四次往返，而后者只需要一次；Cassandra 自己的文档也警告不要把它作为常规手段使用。

这个模式值得推广，也值得强调：**针对真正需要它的不变量，按操作购买协调，而不是全局购买。** 这正是不变量合流理论在工程中的直接表达。

### 7.7 主流中间地带：MongoDB

MongoDB 值得单独讲一段，因为它是大多数读者真正会被要求讨论的系统，也因为它已经发生了相当大的变化。副本集使用一种受 Raft 启发的协议；多文档事务在 4.0 版本为副本集引入，在 4.2 版本为分片集群引入，后者在分片之间使用两阶段提交。事务隔离基于快照，真正有意思的是：这些保证是由客户端组合 <code>readConcern</code> 和 <code>writeConcern</code> 得到的。<code>writeConcern: majority</code> 加上 <code>readConcern: majority</code>，提供持久且不会回滚的读；<code>readConcern: linearizable</code> 为单文档读取增加真实时间保证；因果一致会话则无需每次操作都进行法定人数读取，就能提供读己之写和单调读。

这个教训不只适用于 MongoDB：现代系统越来越多地把一致性/延迟取舍暴露为*每个操作的参数*，而不再是整个部署范围的模式。这是实实在在的进步——它让 §8.3 的按工作负载分析可以直接落地；但这也意味着，“我们使用 MongoDB”几乎不能说明当前启用了什么保证。真正的保证取决于配置。

### 7.8 关于 Kafka

Kafka 不是数据库，但它的复制设置是一个很有启发性的法定人数实例。复制因子为 3 时，<code>acks=all</code> 配合 <code>min.insync.replicas=2</code>，意味着只有当足够多的同步副本持有这条记录后，生产请求才会得到确认——这正是 CAP 形状的可用性/持久性取舍。设置 <code>unclean.leader.election.enable=true</code>，允许一个不同步副本在故障期间成为领导者；它通过*允许已确认数据丢失*来恢复可用性。Kafka 从 ZooKeeper 迁移到 KRaft，则是用内部 Raft 实现替代外部共识依赖，把同一架构收拢到系统内部。

## 8. 工程实践

### 8.1 协调的延迟成本

一旦把下面这些数字内化，设计直觉会明显改善。它们是近似值，也取决于硬件；但它们之间的*比例*相当稳定：

| 操作 | 近似延迟 |
|---|---|
| 主内存访问 | 约 100 ns |
| 带断电保护的 NVMe SSD 执行 <code>fsync</code> | 约 0.1–1 ms |
| 同一数据中心内的网络往返 | 约 0.5 ms |
| 跨可用区网络往返 | 约 1–2 ms |
| 跨区域网络往返（例如美国东西海岸） | 约 60–70 ms |
| 洲际网络往返 | 约 150–250 ms |

直接看这些数字带来的后果：

- 单节点 ACID 提交的主要成本是一次 <code>fsync</code>：小于 1 ms；每个连接每秒可以提交数千次，使用组提交后还会更多。
- 数据中心内的同步复制大致会使提交延迟翻倍。这在几乎所有场景中都可以接受。
- **跨区域同步复制会让每次提交付出几十毫秒**，使单条顺序事务流的上限只有每秒几十次。任何工程技巧都无法消除这一点；它受光速限制。

这就是多区域强一致系统要把数据放在写入者附近的原因（Spanner 的 placement directives、CockroachDB 的 <code>REGIONAL BY ROW</code>），也是 <code>LOCAL_QUORUM</code> 存在的原因。地理位置是模式设计的一部分。

### 8.2 无法靠购买摆脱的成本：争用

延迟是人们最常谈起的协调成本，但它反而是*最不危险*的一种，因为延迟可以用常规技巧处理：流水线、批处理、组提交和并发。即使一万条相互独立的事务各自等待 60 ms，只要并发运行，也能在远少于一秒的墙上时间里完成。

**争用则不同，因为同一数据项上的冲突操作按定义无法重叠。** 这是协调账单中任何硬件采购、任何并行度都无法降低的那一栏；在实践中，它比原始延迟更常成为真实系统的上限。

算术不会留情。在两阶段锁下，单个热点行的最大吞吐量，是每次持锁时间对应的一次更新；而持锁时间包括从获取锁到提交之间的一切——包括提交的往返通信。因此，在跨区域同步复制下更新一行，吞吐量大致被限制为：

~~~text
1 / (60 ms) ≈ 每秒 16 次更新
~~~

不管配置多少核、多少副本或多少连接，结果都一样。全局计数器、热门商品的库存行、租户级序列号，或者高交易量商户的账户余额，都会撞上这堵墙，而墙的位置不会移动。

乐观方案并没有逃脱这个界限；它们只是改变了界限的形状，而且在接近饱和时通常更糟。在 SSI 或 OCC 下，争用会从等待变成中止；中止的事务会重试，重试增加负载，负载提高冲突概率，冲突概率上升又产生更多中止。超过某个阈值后，这个反馈回路会使吞吐量随着请求负载增加而**下降**——这是自 20 世纪 80 年代锁管理器中就很典型的抖动曲线。它在性质上比阻塞更糟：饱和的 2PL 系统只是排队，而饱和的 OCC 系统会白白消耗工作。也正因此，PostgreSQL 的 <code>SERIALIZABLE</code> 不仅需要重试循环，还需要带退避和最大尝试次数限制的重试循环。

有两条推论值得牢记：

**永远不要跨网络调用或用户思考时间持有锁。** 持锁时间是吞吐量上限公式中的分母，而外部调用会让它膨胀几个数量级。这一条规则预防的争用事故，比任何调优参数都多。

**争用是数据建模问题，不是数据库调优问题。** 所有缓解手段，都是改变“争用的对象”：

- **拆分热点对象。** 把一个计数器换成 <code>k</code> 个计数器，随机递增其中一个，读取时再求和。吞吐量增加 <code>k</code> 倍；代价是读取更昂贵。这是 §8.3 中 escrow 最简单的形式。
- **通过单一写者批处理。** 把某个热点键的所有更新路由给分区日志的一个消费者，由它批量应用。并发消失了，争用也随之消失。
- **把冲突移出事务。** 现在预留，稍后确认；预留操作很短，确认操作则触碰另一行。

因此，设计问题不只是“我们需要多强的保证？”，还包括“冲突操作会命中多少个不同的数据项？”。一个在一百万个独立键上提供严格可串行化的系统，完全可以非常快；同一个系统如果只有一个热点键，那么无论一致性级别多弱都会很慢，削弱一致性并不能解决它。

### 8.3 一套决策流程

为新系统做设计时，可以按下面的顺序推进：

**第一步——枚举不变量，而不是枚举“一致性要求”。** “我们需要强一致性”不是需求；“一个座位不能卖给两个人”才是。把它们写成状态上的谓词。

**第二步——按不变量合流性分类。** 合并两个分别有效的状态后，性质是否仍然成立？大多数不变量会通过。那些通不过的，就是你的协调预算。

**第三步——尝试把失败情形重构为合流形式。** 杠杆就在这里：

| 非合流模式 | 合流式改写 |
|---|---|
| 有上限的全局计数器 | **Escrow**：预先把配额分成各节点的份额，只在重新分配时协调 |
| 库存扣减 | **预留**：先占住，再确认；自动让预留过期 |
| 用户名唯一 | 只在唯一性检查处协调（单键 CAS），不要让整个事务都参与协调 |
| “原子地删除父项及其所有子项” | 软删除，加上单调的墓碑传播 |
| 允许删除的共享可变集合 | 采用 add-wins 或 remove-wins CRDT，并明确策略 |

**第四步——按工作负载选择隔离级别，而不是按系统选择。** 分析型读取可以在滞后副本上使用读已提交；真正维护资金不变量的那条工作流，可以使用带重试循环的 <code>SERIALIZABLE</code>。数据库允许按事务设置隔离级别，就应该利用它。

**第五步——显式设计分区模式。** 对每一种降级模式下的操作，提前决定：拒绝它、返回旧数据，还是乐观接受，同时记录足够的信息以便之后补偿。然后把补偿写出来。允许有限离线取款、并以透支费参与对账的 ATM，是一个设计正确的 AP 系统；透支费就是补偿。Amazon 购物车通过集合并集解决分歧，这会让已经删除的商品重新出现——这是一个经过选择、且代价低廉的“允许出错”策略。

**第六步——让重试安全。** 在任何存在超时的系统中，“我的写入到底成功了吗？”往往没有答案。幂等键、去重窗口和事务性 outbox 模式不是可有可无的附加项；它们决定了系统得到的是至少一次投递，还是正确性。

### 8.4 反复出现的反模式

- **“我们使用 PostgreSQL，所以我们就是 ACID。”** 如果启用了异步复制并从副本读取，那么实际保证弱于主库标签所暗示的保证；而且副本上甚至无法使用 <code>SERIALIZABLE</code>（§3.2）。
- **默认隔离级别下的读—改—写。** 读已提交和快照隔离都允许开发者心智模型之外的结果（§2.3）。应使用 <code>SELECT ... FOR UPDATE</code>、原子地原地更新，或带重试的 <code>SERIALIZABLE</code>。
- **应用层唯一性检查。** <code>SELECT ... IF NOT FOUND THEN INSERT</code> 是多走几步的写偏斜。应使用唯一约束；它是少数真正需要协调的东西之一，而数据库已经正确实现了它。
- **把分布式锁想当然地当作互斥。** Redis 或 ZooKeeper 中基于租约的锁，可能在持有者 GC 停顿期间过期，而持有者还以为锁在自己手里。正确用法需要**栅栏令牌（fencing token）**：由受保护资源检查一个单调递增的数字。
- **把墙上时钟时间戳当作合并规则。** 时钟未同步时，最后写入获胜会静默且不确定地丢弃写入。
- **没有序列化失败重试循环。** PostgreSQL 中的 <code>SERIALIZABLE</code> 如果没有重试，会把正确性功能变成可用性问题；如果没有退避，还会变成抖动问题（§8.2）。
- **把半同步复制在超时后的状态当成可信保证。** MySQL 静默回退到异步复制，恰恰在最需要保证的时候让保证消失。应监控这种回退，不要假设它不会发生。

## 9. 验证

从“我们实现了 Raft”到“我们的系统是线性一致的”，中间隔着很远的距离；要跨过这段距离，仅靠测试是不够的。

**Jepsen**（Kyle Kingsbury）是这个领域最重要的实证工作之一：对真实集群生成并发操作，注入分区、时钟偏移和进程暂停，记录执行历史，然后检查该历史是否符合系统宣称的一致性模型。Jepsen 曾在成熟且广泛部署的系统中反复发现真正的安全性违反，其中一些案例甚至与厂商自己记录的保证相矛盾。与其用一个统计数字概括这些工作，不如针对计划部署的具体系统和版本，阅读相应的分析报告；jepsen.io 按系统索引报告，而且对方法及其局限的说明异常坦诚。

**Elle** [Kingsbury 与 Alvaro，2020] 是 Jepsen 的事务检查器。它不去测试线性一致性（一般情况下这是 NP-hard 问题，而且线性一致性本身也无法描述事务），而是从针对列表和寄存器精心设计的操作中推断依赖图——也就是 §2.4 中 Adya 定义的 ww、wr 和 rw 边——并报告能够证明异常的具体环。它会生成可供人阅读的反例，这正是它不仅正确、而且真正可用的原因。

**线性一致性检查器**，例如 Porcupine 和 Knossos，会为观测到的历史寻找一个有效的顺序化见证。由于这个问题是 NP-complete，它们只适用于规模不大的历史；但它们非常擅长发现 bug。

**形式化规约。** TLA+ 已被用于规约 Raft（原始工作就包含对其安全性质的机器检查处理），AWS 也发表过关于将其应用于 S3、DynamoDB 和其他核心服务的工作，并发现测试无法触及的设计级 bug [Newcombe 等，2015]。相关实践反复表明，价值很大一部分来自被迫写下规约本身，而不仅仅来自模型检查器的输出。

**确定性模拟。** FoundationDB 的方法是：运行整个分布式系统，包括一个注入故障的模拟网络，并让所有东西以单线程、确定性的方式执行；这样，任何发现的 bug 都能由一个种子精确复现。从实践角度看，这可能是这类系统最强的测试方法。它是《Paxos Made Live》中测试框架的成熟后继。

如果只从本节带走一条运维规则，那就是：**把一致性声明当作针对特定配置的假设，并测试你实际运行的那套配置。** 许多已发表的违反案例，并非算法本身有问题，而是由默认设置、降级模式和重配置路径造成的。

## 10. 结论

标题中的两个框架回答的是不同问题。ACID 问的是：面对并发事务和不可靠的机器，数据库能对结果作出什么承诺？CAP 问的是：面对副本和不可靠的网络，复制出来的寄存器能对新近性作出什么承诺？字母有所重叠，主题却并不相同。

把它们统一起来的，是正在被消耗的资源。可串行化要求事务了解与自己冲突的其他事务；线性一致性要求副本彼此了解。二者都要用协调来购买，而账单会以延迟、被拒绝的请求，以及所有人都想访问的那个热点数据项上的争用形式到来。隔离级别和一致性模型，是针对同一笔购买提供的两张折扣菜单；真正有用的能力，是知道账单上的哪些项目确实需要。

三个结果合在一起，标出了这条边界。**CAP** 表明，分区发生时，线性一致性和完全可用性不能共存。**HAT** 表明，哪些隔离级别可以在完全可用的要求下存活——这个清单比大多数人以为的更短，而且远未达到可串行化。**不变量合流和 CALM** 则精确定位了要求：只有当一个不变量无法在合并后继续保持，或者等价地，一个计算不是单调的地方，才需要协调。

最后一项结果之所以具有实践意义，是因为它把一场架构争论转换成了一套工程流程。大多数应用不变量都是合流的，根本不需要协调；少数不合流的——唯一性、守恒量、有界资源——才值得为之付费。成熟的系统既不是到处购买最强保证的系统，也不是为了吞吐量放弃所有保证的系统；它知道自己的哪些不变量确实需要共识，精确地为这些地方购买协调，缩小争用集合，并且写下网络断开时其他部分将如何处理。
