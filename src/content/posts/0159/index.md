在 Cache-Aside 模式中，常见写路径是：

```text
UPDATE DB
    ↓
DELETE Cache
```

而不是：

```text
UPDATE DB
    ↓
UPDATE Cache
```

一个自然的问题是：**更新数据库和操作缓存明明是两个独立动作，既然没有原子性保证，删除缓存失败同样会导致不一致，那么「删除缓存」究竟好在哪里？**

DDIA 第二版恰好为这个问题提供了一套完整的概念框架。先给结论：

> **删除缓存并没有解决原子性问题。它解决的是故障和并发情况下的状态收敛问题。**

## 1. 原子性上，两种方案没有本质区别

DDIA 第 12 章「保持系统同步」（Keeping Systems in Sync）一节把这类写法称为**双写**（dual writes），而且它举的例子几乎就是 Cache-Aside 本身：

> 应用代码在数据变更时显式写入每个系统——例如先写数据库，再更新搜索索引，再使缓存条目失效。

无论是：

```text
UPDATE DB + DELETE Cache
```

还是：

```text
UPDATE DB + UPDATE Cache
```

本质上都是一次跨两个独立系统的双写，都可能出现：

```text
DB 操作成功
Cache 操作失败
```

例如：

```text
DB    = 20
Cache = 10
```

DDIA 对此的定性是：一个写成功而另一个失败，这是容错问题；要保证「要么都成功、要么都失败」，就属于**原子提交问题**——而跨异构系统的原子提交（2PC/XA，第 8 章）代价高昂，实践中很少有人为了让缓存和数据库同步去引入分布式事务。

因此，单纯采用「更新 DB 后删除缓存」，**并不能提供强一致性，更不能让两个操作自动具有原子性**。生产环境通常还需要结合重试、TTL、Transactional Outbox、MQ、CDC / Binlog / WAL，确保「缓存失效」这个动作最终不会永久丢失。

所以：

> **Cache-Aside 的正确性并不建立在 DB 与 Cache 的原子事务之上，而建立在最终能够使缓存失效并重新从 DB 构建之上。**

## 2. 真正的差异在并发语义

DDIA 第 12 章图 12-4 展示了双写的一个竞态：两个客户端并发更新条目 X，一个要设为 A，一个要设为 B。两个客户端都先写数据库、再写搜索索引。由于时序不巧，请求交错执行——数据库先看到 A 后看到 B，最终值是 B；而索引先看到 B 后看到 A，最终值是 A。书里的结论值得记住：

> **两个系统现在永久地彼此不一致——即使整个过程中没有发生任何错误。**

把这个竞态套到「更新缓存」方案上。假设两个并发写请求：

```text
W1: x = 1
W2: x = 2
```

如果采用：

```text
UPDATE DB
UPDATE Cache
```

可能发生：

```text
W1: UPDATE DB = 1
W1:                 pause

W2: UPDATE DB = 2
W2: SET Cache = 2

W1: SET Cache = 1
```

最终：

```text
DB    = 2
Cache = 1
```

数据库的最终状态已经是 `2`，但较早的请求因为较晚执行缓存写入，把旧值重新覆盖了缓存。问题根源在于：

> **数据库能够确定事务的提交顺序，但缓存并不知道这些写操作在数据库中的版本关系。**

`SET Cache=value` 携带了业务状态，它的正确性依赖于写入顺序——这正是 DDIA 图 12-4 里搜索索引陷入永久不一致的同一个机制。

而如果采用：

```text
UPDATE DB
DELETE Cache
```

同样的乱序变成：

```text
W1: UPDATE DB = 1
W1:                 pause

W2: UPDATE DB = 2
W2: DELETE Cache

W1: DELETE Cache
```

最终只是：

```text
DB    = 2
Cache = MISS
```

下一次读请求：

```text
Cache MISS
    ↓
SELECT DB → 2
    ↓
SET Cache = 2
```

系统重新收敛到正确状态。这就是两种方案最重要的区别：

> **更新缓存携带「值」，旧操作可能覆盖新状态；删除缓存只表达「当前缓存不可相信」，旧删除不会制造一个旧业务值。**

## 3. DELETE 天然适合重试

DDIA 术语表对幂等的定义是：**可以安全重试的操作——执行多次与执行一次效果相同**。第 13 章则指出，最有效的容错手段之一就是让操作幂等；只是天然不幂等的操作要做到幂等，往往需要额外元数据（如操作 ID 集合）和 fencing 机制，成本不低。

缓存删除恰好是天然幂等的：

```text
DEL key
DEL key
DEL key
```

最终状态仍然只是：

```text
key 不存在
```

因此删除失败时，可以安全地通过重试、消息队列、Outbox 或 CDC 再次执行。

而缓存更新：

```text
SET key = v1
SET key = v2
```

结果取决于操作顺序。要可靠地「更新缓存」，往往必须引入：

```text
version
timestamp
CAS
sequence number
```

来判断哪个值更新，否则旧请求可能覆盖新请求。换句话说，**删除缓存只是传播一个失效事件；主动更新缓存则要求系统正确维护另一份业务状态**——后者的一致性问题明显更复杂。

这也呼应了 DDIA 第 13 章的一个对比：分布式事务用原子提交协议保证变更原子地应用，而基于日志的系统通过**确定性重试和幂等性**达到同样的正确性目标。当数据跨越不同技术的边界时，带有幂等写入的异步事件日志，比标准化事务协议健壮、实用得多。

## 4. 核心思想：Cache 是派生状态

因此，Cache-Aside 真正重要的不是「删除缓存能够解决原子性」——它解决不了。它采用的是另一种设计思路，即 DDIA 第 13 章反复强调的**记录系统与派生数据**（system of record and derived data）：

> 某些系统被指定为记录系统，其他数据通过转换从它们派生而来——索引、物化视图、统计摘要，也包括缓存。书里明确把「由原始数据派生出的缓存」列为派生数据的典型例子。

即：

```text
          Source of Truth
                │
                ▼
               DB
                │
             derive
                ▼
              Cache
```

DB 决定：

```text
正确的数据是什么
```

Cache 只负责：

```text
加速读取
```

派生状态有一个关键性质：**可以随时丢弃、随时重建**。DDIA 第 13 章谈到数据系统演进时说，如果想改变索引或缓存的结构，只需在整个输入数据集上重新运行转换代码即可重新派生输出；出了问题，也可以修复代码、重新处理数据来恢复。

所以写路径最自然的语义不是：

```text
DB 更新成 v2
Cache 也必须精确更新成 v2
```

而是：

```text
DB 更新成 v2
旧 Cache 已经不可信 → 删除
```

下一次读取再从 Source of Truth 重建。

## 5. 工程上还要补的一块：别让失效事件丢失

「删除缓存」把难题从「维护两份值的一致性」降维成了「可靠地传播一个失效事件」，但这个事件仍可能丢失——比如应用进程在 UPDATE 成功、DELETE 未发出时崩溃。常见补救手段，与 DDIA 第 12 章的工具箱一一对应：

* **重试**：DELETE 幂等，直接重试是安全的；
* **TTL**：给缓存设过期时间，为一致性兜底，界定了不一致窗口的上限；
* **Transactional Outbox / MQ**：把失效意图和业务写入放在同一个本地事务里持久化，再异步投递；
* **CDC / Binlog / WAL 订阅**：把数据库的变更日志当作唯一事实流，由它驱动缓存失效——这正是 DDIA 推崇的方式：如果 CDC 是更新派生数据的唯一途径，就可以确信派生数据完全由记录系统派生而来，与之一致。

## 6. 最终结论

`UPDATE DB + DELETE Cache` 和 `UPDATE DB + UPDATE Cache` 在**跨系统原子性**上没有本质区别，两者都可能部分成功——这就是 DDIA 所说的双写问题。

真正的差异在于故障和并发语义：

```text
UPDATE Cache
```

要求维护两份状态值的一致性，存在旧写覆盖新写的问题（DDIA 图 12-4 的竞态）。

而：

```text
DELETE Cache
```

只是声明缓存失效：操作天然幂等、容易重试，乱序执行也只会收敛到 MISS，缓存缺失后可以重新从 DB 恢复。

因此，Cache-Aside 的核心设计原则可以概括为一句话：

> **不要努力让 Cache 成为 DB 的另一份精确副本，而应该让 Cache 成为 DB 的可丢弃、可重建派生状态。**

「更新 DB，再删除缓存」的优势从来不是解决了原子性，而是：

> **在无法避免跨系统非原子性的前提下，它让失败更容易恢复，让并发乱序更容易收敛，并始终保持 DB 作为唯一的 Source of Truth。**
