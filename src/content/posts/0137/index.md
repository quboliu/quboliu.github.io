读 DDIA 容易记住一串名词：B 树、LSM-tree、复制、分片、事务、共识、批处理、流处理。难的是解释：为什么需要它们，彼此替代了什么，又有哪些问题谁也没有替你解决。

可以用一个问题贯穿整本书：**当数据持续变化、资源有限，而故障不可避免时，系统怎样以可承受的成本兑现它的承诺？** 分布式进一步增加困难：参与者只掌握局部信息，却可能需要共同执行一条约束。

这不是书中的定理，而是本文对 [DDIA 第二版](https://learning.oreilly.com/library/view/designing-data-intensive-applications/9781098119058/)十四章的归纳。

推理从需求开始：为了降低访问成本，我们改变数据表示；为了扩展容量和容忍故障，我们把数据放到多处；为了让多处变化仍然合法，我们限制执行；为了恢复和派生结果，我们保留历史；当这些工作拆给不同系统，最后必须重新检查它们的保证能否衔接。

## 1. 正确性先于实现：系统必须明确承诺什么 # 架构权衡、非功能性需求、数据责任（第 1、2、14 章）

“数据已经保存”“操作已经成功”“读取的是最新值”，都不是足够精确的承诺。保存到进程内存，还是磁盘和副本？成功之后能否在故障切换中消失？最新是请求发出前，还是某个历史快照中的最新？

技术选择的起点，是把这些问题说清楚：允许什么结果，禁止什么结果，在什么负载、故障范围与时间预算下成立。正确性定义可接受的行为；性能与成本决定怎样负担这些行为。

**性能优化应当在约定的语义内进行；改变语义也是一种选择，但必须明说。** 异步复制可以降低提交等待，却可能扩大故障时的数据损失窗口；历史读取可以减少协调，却不是最新读取的同义词。

需求还包括人的理解和操作能力。恢复流程没人能正确执行，架构图上的高可用就没有落实。可观测性、可维护性和演进成本，不是功能实现之后才补的装修。

第 14 章同样属于起点：数据是否该收集，允许保留多久，错误预测会伤害谁，会反过来决定数据模型、日志保留与删除流程。技术上能长期保存，不等于业务上就该无限保留。

## 2. 没有一种表示适合所有访问：优化往往是在提前做工作 # 数据模型、存储与索引、物化与派生（第 3、4、11、13 章）

逻辑上，同一份事实可以表示为关系、文档、图或事件；物理上，又可以按行、按列、按键排序或按到达顺序保存。前者影响哪些关系和操作容易表达，后者影响完成这些操作需要访问多少数据。

为什么需要索引？因为反复扫描太贵，值得预先维护查找结构。为什么需要物化视图？因为反复计算太贵，值得预先保存结果。它们都把一部分读取工作提前到写入或后台处理阶段，并付出空间与维护成本。

LSM-tree 也体现这种时间上的安排：先积累写入，再成批组织、合并文件，换取不同的读写与空间放大。它不是凭空消除了工作，而是改变工作的形态与发生时机。列式布局则让只读少数列的扫描少碰无关数据。

从数据库内部的索引，到外部搜索系统、缓存和报表，贯穿其中的是同一个设计问题：**是否值得额外保存一种表示，来降低未来访问的成本？**

一旦保存了多种表示，新的责任随之出现：谁是事实来源？其他表示怎样更新？落后多久可接受？丢失后能否重建？所谓“派生数据”，不是不重要，而是其正确性必须相对于来源来定义。

这解释了第 4 章与第 13 章的深层联系：数据库内部替你维护多种表示；把它们拆成多个系统后，更新与恢复的责任不再自动留在一个事务边界内。

## 3. 分布式的困难不只是机器多，而是信息与控制不再集中 # 复制、分片、网络、暂停与时钟（第 6、7、9 章）

复制与分片是两个方向。复制让同一份数据存在多处，以获得冗余或分担读取；分片把不同数据分开放置，以分担容量和负载。两者可以组合，但不能互相替代。

它们都让某些工作更局部，也让另一些操作必须跨节点。按某个键分片有利于这个键上的访问，却可能让其他查询变成跨分片汇总；增加副本有利于容错，却带来传播延迟和副本选择。

**局部性不是免费且普遍的：你必须说明哪些操作被放到一起，哪些操作因此需要通信。** 一个分片键不可能仅凭“分得均匀”就解决所有查询与约束。

通信又不是即时且可靠的。没收到回复，可能是请求没到、处理没完成、回复丢失，也可能是进程暂停。超时给出的是“该采取恢复行动了”的信号，不是“远端肯定没有执行”的证据。

因此，分布式协议除了处理数据，还必须处理知识不足：我知道哪些写入？凭什么相信某个节点仍有权做主？有没有尚未到达的更早请求？

时间戳可以给收到的事件排序，却不能让缺失的消息自动出现；两个时钟相近，也不能自动证明一份快照已经完整。**数字可比较，与系统掌握了足够信息作决定，是两种能力。**

## 4. 执行业务约束，需要合法历史，不只是排序 # 事务、隔离、一致性、共识（第 8、10 章）

只有一份数据也会有并发问题；有了多个副本，又增加故障与接管问题。这些问题相互影响，却有不同的正确性要求。

约束至少会被两种情况破坏：多个操作交错，分别合理的判断合在一起却不合法；一个操作包含多项修改，失败后只完成其中一部分。前者需要并发控制，后者需要原子性。再把执行者复制到多台机器，就要解决谁有权决定、接管者能否推翻既有决定的问题。

| 机制或保证 | 主要回答什么 | 不自动保证什么 |
| --- | --- | --- |
| 原子提交 | 一组修改能否同成同败？ | 并发事务的读取一定合法 |
| MVCC | 保留哪些版本，读取怎样选择版本？ | 一定可串行化 |
| 可串行化 | 并发事务的读写能否由某个串行执行解释？ | 串行顺序一定遵守实时先后 |
| 线性一致性 | 操作能否表现为调用与返回之间瞬间生效，并尊重实时先后？ | 多条独立操作自动组成原子事务 |
| 共识 | 节点怎样在给定故障模型下形成不冲突的决定？ | 所有分片、外部副作用自动属于同一事务 |

排序为什么不够？因为合法顺序必须能解释实际读取。两个事务各自读到对方写入之前的旧状态，可能形成相互矛盾的依赖；给它们补上大小不同的时间戳，并不能修复已经读错的历史。

共识为什么也不够？因为它可以确定某个日志中的顺序，但业务可能跨越多个日志、分片或服务。每个部分各自有可靠顺序，不等于多个部分的修改已经同成同败。

锁、条件写入、冲突检测和重试，都在限制哪些执行可以成功；共识协议则可以为复制状态机提供可靠的共同决定。实际系统把这些机制组合起来，而不是选中其中一个，就获得其余所有保证。

也不是每种业务都必须先选唯一赢家。如果允许并发更新按规则合并，某些操作就可以减少同步协调；但前提是合并结果仍符合业务约束，不能把“最后会收敛”当作“过程中不会超卖”。

**应当协调的是会破坏约束的决定，而不是为了整齐给全世界的操作排一条队。** 约束只在一个键上，就先在这个范围内解决；约束跨分片，就不能假装它仍是局部问题。

## 5. 状态是变化积累的结果：批与流是两种计算历史的方式 # 编码与演进、日志、批处理、流处理（第 5、11、12 章）

状态告诉你现在是什么，日志保留一段变化过程。从固定输入重新计算，得到批处理；随着新输入更新已有结果，得到流处理。两者共享转换、分组、连接等计算问题，区别主要在输入边界、状态维护和何时确认输出。

增量计算避免每次从头开始，但必须维护状态、处理乱序和恢复进度。全量重算可以修复算法或派生结果，却要支付重新读取和计算的成本。它们不是新旧替代关系，而是不同的成本与恢复选择。

没有自然终点的流，必须显式定义何时认为一个窗口足够完整。watermark 是协议和策略给出的进度信息，不是对未来消息的无条件预言；超出预期的迟到事件，需要明确的修正或舍弃规则。

“能重放”也不等于“能正确重建”。你需要足够的历史、确定的输入范围、适配的代码和可解释的数据语义。旧事件的字段已经变了、外部依赖无法复现、必要数据已经删除，都可能使重放得到错误结果。

这使编码与演进成为时间上的接口问题：滚动升级时，新旧程序要能交换数据；重建历史时，新程序要能解释旧记录。**只要数据活得比一次部署更久，兼容性就是长期正确性的一部分。** 字节能解码，不代表新代码理解了旧数据的含义。

## 6. 局部保证不会自动相加：端到端正确性要闭合每个交接点 # 数据集成、流处理系统、隐私与伦理（第 13、14 章）

一个数据库提交成功，另一个系统并不会因此自动收到消息。消息至少送达一次，外部扣款并不会因此只执行一次。每个组件分别兑现承诺，组合起来仍可能留下“这边已成功、那边尚未知晓”的空隙。

解决办法通常不是再加一句“最终一致”，而是明确交接规则：哪些状态同一事务提交？失败后凭什么重试？重复如何识别？消费进度与输出怎样对应？旧执行者恢复后，怎样阻止它继续产生副作用？

Outbox、幂等键、去重表、事务性输出、fencing 和恢复检查点分别处理这些不同空隙。它们不是可以互换的“可靠性开关”；每一种都有作用范围和依赖前提。

这就是第 13 章“解耦数据库”的代价：拆开后可以独立选择存储和计算方式，但原先由数据库内部维护的关系，需要跨组件重新建立。一个系统的输出，是另一个系统的输入，责任不能在交接处消失。

第 14 章把同样的追问扩展到数据用途：一份个人信息复制、索引、备份、派生之后，原库删除一行并不意味着所有副本都已按约定处理。删除、保留、恢复与审计也必须跨系统闭合。

**数据系统的整体承诺，取决于完整路径，而不是功能最强的那个组件。** 一个事务边界之外的副作用，不能借用事务内部的保证；一个用途之外的数据保留，也不能借用原始收集时的理由。

## 7. 把十四章压缩成一套推理方法 # 需求、机制、代价与边界

看到任何技术，先问四个问题：

1. **它解决哪项具体需求？** 降低读取成本、容忍故障、维护不变量，还是支持重建？
2. **它依赖什么条件？** 唯一写入者、事务边界、完整历史、稳定身份，还是多数节点可通信？
3. **它把成本放在哪里？** 空间、写入维护、通信等待、后台计算，还是人工恢复？
4. **条件不成立时会怎样？** 阻塞、重试、读旧值、丢失数据，还是返回不允许出现的结果？

由此可以得到三条贯穿全书的总结：

- **更多表示换取更便宜的访问，也带来更新与恢复责任。** 这连接模型、索引、复制、缓存与派生数据。
- **更强保证需要相应的信息和执行约束，不能仅靠命名或时间戳获得。** 这连接并发控制、故障模型、一致性与共识。
- **拆分提高独立性，也扩大保证之间的交接面。** 这连接分片、服务拆分、批流处理、数据集成与治理。

这不是三条无条件定律，而是一套检查架构的办法。DDIA 的价值，在于让你不再问“这个组件先进吗”，而是能够说清：**在这些前提下，它以这些代价，守住了这条承诺。**

## 8. 示例：用一笔订单验证上面的逻辑 # PostgreSQL、TiKV、Kafka 与数据流

下面是教学场景，不是某家公司的完整部署记录；所列机制来自真实系统，也不要求把它们全部装进同一个项目。

**先定义成功。** 下单响应的延迟预算、库存不能超卖、已确认订单在约定故障范围内不丢失，是三项不同要求。销售报表可以晚一分钟，不代表库存判断也可以晚一分钟。

**再选择表示。** 订单事务使用适合点查和更新的布局；历史分析可以导出 Parquet，用 DuckDB 的列裁剪与过滤下推减少扫描。分析结果是派生表示，需要明确输入范围与重建方法。[DuckDB：Parquet](https://duckdb.org/docs/current/data/parquet/overview)

**约束落到原子操作。** 在 PG 中，假设商品键唯一，可以在同一事务里条件扣库存，仅当更新一行时创建订单：

```sql
UPDATE inventory
SET stock = stock - 1
WHERE sku = $1 AND stock > 0;
```

默认读已提交级别下，遇到并发更新会等待；对方提交后在新版本上重新检查条件。它依赖内部行锁，并非无锁。多行不变量还需另外分析，不能把这个单行办法推广到所有业务约束。[PostgreSQL：事务隔离](https://www.postgresql.org/docs/18/transaction-iso.html)

**跨机器后重新核对保证。** PG 异步备库可能落后，安全接管不由 WAL 传输自动提供。TiKV 将键空间分为 Region，每个 Region 使用 Raft 复制；跨 Region 事务仍需事务协议。这里分别是数据传播、局部日志裁决与跨范围原子性。[PG 流复制](https://www.postgresql.org/docs/18/warm-standby.html)、[TiKV 架构](https://docs.pingcap.com/tidb/stable/tikv-overview/)

**把数据库成功连接到消息。** 订单和 outbox 事件同事务落库，再由 Debezium 传播，避免“订单已提交、发送意图却丢了”。消费端仍需处理重复，outbox 不自动消除重复投递。[Debezium：Outbox](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html)

**把消息处理连接到输出。** Kafka 事务能共同提交 Kafka 内的输出与消费位置，下游还应使用 `read_committed`。外部支付不在这份事务内；Stripe 的幂等键是处理重试的一种真实机制，但有保留期限和参数约束。[Kafka 事务](https://kafka.apache.org/41/design/design/)、[Stripe 幂等请求](https://docs.stripe.com/api/idempotent_requests)

**最后验证可修复与可删除。** 实时统计用 Flink 处理事件时间与迟到数据，离线重算用于核对和修复派生结果。重算需保留足够且可解释的输入；个人信息则按用途与保留策略处理，删除传播与备份恢复流程不能遗漏。[Flink：Watermark](https://nightlies.apache.org/flink/flink-docs-stable/docs/dev/datastream/event-time/built_in/)

这一笔订单的技术链条，最终仍落回同一个问题：数据经过不同表示、机器、时间和系统之后，我们承诺的“成功”，是否始终还是同一个意思？
