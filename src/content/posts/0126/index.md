本文是对《Designing Data-Intensive Applications》第二版第 8 章 “Problems with XA transactions” 一节的释疑和解惑。

这一节有两句话很容易让人困惑：为什么“应用代码仍会成为单点故障”？为什么 XA“没有提供协调者与事务参与者直接通信的方式”？

疑问很自然：如果协调者已经复制成高可用服务，参与者也把 `PREPARED` 状态写入了磁盘，应用进程宕机为什么还会妨碍事务完成？

答案不在 2PC 的投票规则本身，而在 XA 把哪些事情标准化了、又把哪些事情留给应用服务器、驱动和厂商实现。

## 一、先给出结论

DDIA V2 所说的“应用代码成为单点故障”，主要不是指应用一崩溃就会破坏原子性，而是指原应用进程经常同时承载协调器、驱动和通信上下文；它消失后，已准备事务可能仍然安全，却无法继续推进。

“没有直接通信方式”也不是说协调者永远不能向数据库发送请求，而是说 XA 首先是一组事务管理器调用资源管理器的接口，不是一套让参与者能够主动发现、定位和询问协调者的通用网络协议。

因此，这一段需要同时区分两组概念：

| 维度 | 问题 |
| --- | --- |
| 安全性 | 多个参与者会不会一部分提交、一部分回滚？ |
| 活性 | 协调者或应用故障后，事务还能不能自动完成？ |
| 决策状态 | Commit/Abort 决定是否已经可靠保存？ |
| 恢复执行能力 | 谁能够重新发现、连接参与者并落实这个决定？ |

“恢复执行能力”是本文为了分析而使用的说法，并非 XA 规范中的术语。2PC 和 XA 首先保护的是安全性；复制协调者可以保护决策状态，但系统还要有活着的恢复管理器和可重建的资源连接，才能恢复活性。

## 二、先分清 XA 中的四类角色

XA 使用几类容易混淆的角色：

- 应用程序（Application Program，AP）发起业务操作。
- 事务管理器（Transaction Manager，TM）承担 2PC 协调者角色。
- 资源管理器（Resource Manager，RM）管理数据库或消息队列等事务资源。
- JDBC、JMS 或其他 XA 驱动，把事务管理器的调用转换成参与者能够理解的请求。

在常见的 Java EE/Jakarta EE 架构中，它们大致组成下面的结构：

```text
                   应用服务器进程
        ┌────────────────────────────────┐
        │ 业务代码                       │
        │ JTA 事务管理器 / XA 协调者     │
        │ JDBC XA 驱动、JMS XA 驱动      │
        └──────────┬────────────┬────────┘
                   │            │
                 JDBC          JMS
                   │            │
             数据库参与者    消息队列参与者
```

协调者在逻辑上是一个独立角色，但在很多实现里，它只是加载在应用服务器进程中的一个库。协调者日志也可能保存在这台应用服务器的本地磁盘上。

这里的“应用代码”应当宽泛地理解为应用侧执行环境：它不仅包含业务函数，还包括事务管理器、驱动、连接配置和恢复任务，而不是单指某几行业务代码。

## 三、XA 标准化了什么

X/Open XA 的目标，是让一个事务管理器能够协调不同厂商的资源管理器。数据库和消息队列内部实现完全不同，但都可以向事务管理器暴露相似的事务操作。

抽象地看，事务管理器可以要求每个资源管理器执行：

```text
start(XID)
end(XID)
prepare(XID)
commit(XID)
rollback(XID)
recover(...)
```

`XID` 由全局事务标识和分支限定符等部分构成，用于标识一个事务分支；同一全局事务的各分支共享全局事务标识。协调者依靠它把数据库和消息队列中的本地事务关联起来。

但是，XA 主要规定的是事务管理器与资源管理器之间的接口语义。它不是一种规定了稳定服务地址、节点发现、领导者选举、故障转移和双向消息格式的端到端网络协议。

应用通常通过资源对应的驱动访问参与者。JDBC 驱动了解数据库协议，JMS 驱动了解消息代理协议；XA 本身不要求所有参与者再共同实现一套独立的 XA 网络协议。

## 四、“不能直接通信”究竟是什么意思

不要把“不能直接通信”理解成所有网络字节都必须经过某段用户业务代码。事务管理器当然可以通过驱动向数据库和消息队列发送 `prepare`、`commit` 或 `rollback`。

DDIA 的论述包含两层意思：第一，XA 本身不是线路协议，实际网络通信由应用侧客户端库和驱动承载；第二，数据库服务器不能绕过这条路径，依据 XA 提供的通用机制主动联系协调者。一个参与者通常只知道某个 `XID` 已经进入 `PREPARED`，却不一定知道以下信息：

- 协调者位于哪台机器；
- 当前哪个协调者副本是主节点；
- 协调者的认证信息和网络协议；
- 事务还有哪些其他参与者；
- 全局 Commit/Abort 决定是否已经产生。

因此，XA 没有普遍定义下面这条路径：

```text
资源管理器 ──标准 XA 网络协议──> 协调者
              “XID 42 最终是什么结果？”
```

常见路径是反过来的：事务管理器通过应用侧驱动主动调用资源管理器。若要继续遵守 2PC 的原子性承诺，参与者处于存疑状态时，不能仅凭超时猜测结果，也不能根据本地情况自行提交或回滚。

## 五、正常情况下，事务如何完成

假设应用需要同时更新数据库并确认一条消息。正常执行过程如下：

```text
1. 应用向事务管理器申请全局 XID
2. 数据库和消息队列加入该全局事务
3. 应用执行数据库写入和消息操作
4. 协调者向两个参与者发送 Prepare
5. 两个参与者持久化 PREPARED 状态并回复 Yes
6. 协调者持久化全局 Commit 决定
7. 协调者向两个参与者发送 Commit
8. 参与者完成本地提交并释放锁和资源预留
```

在第 5 步之后，参与者不能自行回滚。在第 6 步之后，协调者也不能改变决定。2PC 正是用这两类不可撤销的承诺换取跨系统原子性。

## 六、应用崩溃如何留下存疑事务

现在让故障发生在最麻烦的位置：

```text
数据库 A：Prepare Yes
消息队列 B：Prepare Yes
协调者：已经决定 Commit，并写入日志
应用服务器：在发送全部 Commit 前崩溃
```

参与者重启或检查本地日志时，只能确认事务已经准备好。它们不能从“尚未收到 Commit”推出“全局决定是 Abort”，因为 Commit 消息可能只是丢失或延迟了。

为了不破坏原子性，它们只能保留 `PREPARED` 状态，继续持有必要的锁、写入意图或资源预留，等待有权威的恢复者重发最终决定。

严格地说，许多 XA 实现还提供“启发式决定”作为灾难情况下的逃生门：参与者可以在没有权威决定时单方面提交或回滚。但这相当于退出 2PC 的承诺体系，可能破坏原子性，只适合在严重故障下显式处置，不能视为正常的协议进展。

如果原应用进程同时承载协调者库和驱动，这条重发路径也随进程消失。事务没有产生错误结果，却停在了中间状态。

这就是 2PC 的阻塞性质：故障时优先保持“不做错”，代价是可能“什么也做不了”。

## 七、“单点故障”主要损害的是活性

“单点故障”容易被理解为应用崩溃后数据库会损坏，或者两个参与者立刻出现不同结果。这里通常不是这个意思。

参与者拒绝自行决定，反而保护了原子性。真正受损的是事务的活性：只要负责恢复通信的应用侧组件没有回来，事务就无法结束，锁也无法释放。

这还会进一步损害可用性：存疑事务持续占用热点数据或资源，其他事务即使与它毫无业务关系，也可能因等待同一把锁而被阻塞。

即使应用部署了十个无状态副本，新副本能够接收新请求，也不代表它能接管旧的 XA 事务。第二阶段通常不需要恢复旧调用栈，但接管者必须能够读取完整的 TM 恢复日志，装载同一组 XA 资源配置，并承担恢复责任。

因此，这里的单点更准确地说是“每个存疑事务的推进单点”。如果它持有热点资源，这个局部问题还可能扩散为大范围阻塞。

## 八、为什么复制决策状态仍不等于恢复能力

复制协调者首先解决的是决策状态的耐久性。例如，主协调者已经决定 Commit，即使主节点崩溃，副本仍能读取这个决定。

成熟事务管理器的完整恢复日志通常不只保存 Commit/Abort，还会包含参与者清单和事务分支元数据。不过，“知道应该 Commit”和“能够完成 Commit”仍是两件事：日志记录的是历史，参与者当前是否仍处于 `PREPARED`，必须连接资源管理器后才能确认。

新的恢复管理器还需要：

- 从完整 TM 日志恢复参与者和事务分支元数据；
- 找到各个资源管理器的网络地址；
- 取得连接凭据并装载正确驱动；
- 对已配置的资源管理器调用 `recover()`，核对当前分支状态；
- 使用原来的 `XID` 对未完成分支落实最终决定；
- 幂等地重发 Commit 或 Rollback，直到全部完成。

如果只复制 Commit/Abort 决定值，而完整 TM 日志、资源配置、凭据或恢复管理器仍依赖已经崩溃的应用进程，那么事务依然无法恢复。

所以，真正高可用的方案复制的不只是“一个布尔决定”，还必须让完整恢复日志、资源配置和恢复管理器能够被其他节点接管。

## 九、XA 并非完全没有恢复能力

这里需要给 DDIA 的表述加上一条重要限定：XA 并不是完全没有恢复接口。

`XAResource.recover` 允许事务管理器扫描资源管理器，取得仍处于已准备或启发式完成状态的事务分支。Jakarta Transactions 也要求恢复期间的事务管理器能够连接应用使用的资源管理器，并执行这种扫描。

这意味着一个成熟的事务管理器可以在重启后：

```text
读取自己的决策日志
        ↓
连接已配置的资源管理器
        ↓
recover() 找到 PREPARED XID
        ↓
依据日志重发 commit() 或 rollback()
```

PostgreSQL 的 `PREPARE TRANSACTION` 也展示了这个原则：事务准备后不再绑定原会话，之后可以由其他会话执行 `COMMIT PREPARED` 或 `ROLLBACK PREPARED`。不过，PostgreSQL 也明确警告，准备事务会持续持锁并妨碍 `VACUUM`，因此不应长时间停留在该状态。

因此，恢复第二阶段并不必然要求重新运行原来的业务函数，也不必然要求恢复原来的 TCP 连接。

## 十、那么 DDIA 的批评还成立吗

成立，但应理解为对 XA 标准边界和常见部署方式的批评，而不是“XA 在逻辑上绝对无法故障恢复”的定理。

XA 提供了事务分支操作和恢复扫描接口，却没有替所有异构系统统一解决：资源发现、网络传输、协调者选主、日志复制、凭据管理、参与者配置以及应用执行状态恢复。

成熟的 Java 应用服务器、独立事务管理器或厂商产品可以补充这些能力。但是这些能力来自具体实现和部署架构，不是只要声明“支持 XA”就自动拥有。

即使存在 `recover()`，自动恢复也不是绝对完备的：如果协调者日志丢失、损坏，或无法与参与者的 `XID` 对账，仍可能留下必须由管理员处理的孤儿存疑事务。

如果事务在 Prepare 之前失败，通常可以安全中止，不需要恢复原业务流程。如果所有参与者已 Prepare 且全局决定已经持久化，一个独立恢复器通常只需落实决定。

真正需要“应用代码可恢复”的，是那些还依赖应用控制流才能确定下一步、参与者集合或外部副作用的场景。这时问题开始接近持久化执行，而不只是 2PC 日志恢复。

## 十一、三个故障时刻必须分开

| 故障时刻 | 已知状态 | 通常处理 |
| --- | --- | --- |
| Prepare 之前 | 尚无参与者作出不可撤销承诺 | 中止事务并重试业务操作 |
| 参与者已 Prepare，全局决定未知 | 参与者不能自行判断结果 | 保持存疑并等待协调者恢复 |
| 全局决定已持久化，但尚未送达所有参与者 | 决定不可更改 | 恢复器反复重发最终决定 |

第二种状态是经典 2PC 最棘手的阻塞窗口。第三种状态原则上更容易恢复，因为权威答案已经存在，剩下的是可靠送达和幂等执行。

## 十二、数据库内部事务为什么通常更容易处理

在数据库内部的分布式事务中，协调者和参与分片由同一个系统设计。它们可以共享事务协议、成员发现、认证方式、日志格式和故障恢复机制。

参与分片通常知道如何找到协调者或权威决策日志；协调者状态也可以通过共识复制。新协调者接管后，可以直接使用数据库内部协议继续驱动参与者。

XA 面对的却是数据库、消息队列等异构系统，只能采用共同支持的接口。它获得了兼容性，却很难统一利用每个系统内部更丰富的故障检测、死锁检测和串行化冲突信息。

这也是“数据库内部的分布式事务”和“跨异构系统的 XA 事务”不能只因为都使用 2PC 就视为同一种工程问题的原因。

## 十三、一个更稳固的心智模型

理解这一节，可以连续追问四个问题：

1. 最终决定保存在哪里，是否经过复制？
2. 每个参与者如何持久保存 `PREPARED` 状态？
3. 故障后，谁负责读取完整 TM 日志，并连接所有已配置的参与者？
4. 这个恢复者是否拥有足够状态，能够继续原事务而不是重新猜测？

前两个问题主要决定安全性，后两个问题主要决定活性。只回答“协调者已经复制”只覆盖了第一个问题。

最终可以把 DDIA V2 的两句话压缩为：

> XA 规定了事务管理器如何通过资源驱动协调事务分支，却没有单独提供一套让异构参与者主动寻找高可用协调者的通用网络与接管机制；如果完整 TM 日志、资源配置和恢复责任仍寄存在某个应用进程中，该进程就会成为事务推进路径上的单点故障。
